# 커뮤니티 Swagger 전환 및 UX 재설계

- 상태: 사용자 설계 확정
- 작성일: 2026-07-27
- 대상: BossPickSeoul 프론트엔드 커뮤니티
- 기준 브랜치: `develop`

## 1. 배경

현재 커뮤니티 화면은 이전 NowDoBoss의 API와 데이터 구조를 바탕으로 구현되어 있다. 저장된 최신 Swagger와 비교하면 API 경로, 게시글 타입, 카테고리, 이미지, 댓글 기능이 서로 맞지 않는다.

대표적인 차이는 다음과 같다.

- 현재 프론트엔드는 `/community`, `/community/popular`, `/firebase/upload` 등 구 API를 호출한다.
- 최신 Swagger는 `/api/v1/community/posts`를 중심으로 목록, 검색, 좋아요, 댓글, 대댓글, 신고 API를 제공한다.
- 기존 카테고리와 이미지 필드는 최신 Swagger에 없다.
- 최신 Swagger는 게시글을 자치구, 행정동, 상권과 연결하는 `targetType`, `targetCode`를 제공한다.
- 게시글과 댓글 응답에는 작성자 `memberId`만 있고 닉네임과 프로필 이미지가 없다.

이번 작업은 기존 백엔드를 변경하지 않고, 저장된 Swagger를 API 정본으로 사용해 커뮤니티를 다시 연결한다.

## 2. 목표

- 전체 게시글과 지역·상권 맥락을 결합한 혼합형 커뮤니티를 제공한다.
- 목록과 상세는 비로그인 사용자도 열람할 수 있게 한다.
- 로그인 사용자는 글쓰기, 수정·삭제, 좋아요, 댓글·대댓글, 신고를 사용할 수 있게 한다.
- 최신, 인기, 좋아요한 글, 검색, 지역 필터를 지원한다.
- 데스크톱, 태블릿, 모바일에서 기존 디자인 시스템과 `/status`, `/recommend`의 UX 언어를 유지한다.
- 로딩, 부분 오류, 빈 데이터, 비로그인 상태를 각각 명확히 처리한다.
- 백엔드가 실행되지 않는 로컬 환경에서도 명시적인 개발용 mock 모드로 UI와 상호작용을 검증할 수 있게 한다.

## 3. 제외 범위

- 백엔드 API 또는 응답 스키마 변경
- 패키지 버전, lockfile, 빌드·배포 설정 변경
- 이미지 업로드 구현
- 댓글 수정
- 분석 결과 첨부 메타데이터 영속화
- 운영자 신고 처리 화면
- 커뮤니티 외 페이지의 리팩터링
- 분석 화면에서 커뮤니티로 직접 이동시키는 공유 버튼

상권 분석 공유는 이번 작업에서 글쓰기의 지역·상권 선택 구조까지만 준비한다. Swagger의 초안 생성 응답에는 분석 참조 정보가 있지만 게시글 생성 요청에는 이를 저장하는 필드가 없으므로, 실제 분석 첨부 카드는 후속 백엔드 계약 이후 구현한다.

## 4. 확정된 제품 방향

### 4.1 정보 구조

커뮤니티는 전체 피드를 기본으로 하는 혼합형 구조를 사용한다.

- 게시글이 첫 번째 정보다.
- 자치구, 행정동, 상권은 게시글 태그와 필터로 제공한다.
- 기존 `이모저모`, `인테리어`, `상권공유`, `동업제안`, `창업고민` 카테고리는 제거한다.
- 목록 상단에 `최신`, `인기`, `좋아요한 글` 보기를 제공한다.
- 지역·상권 연결은 글쓰기에서 필수다.
- 작성 요청은 선택한 범위의 `targetType`, `targetCode`를 항상 전송한다.

### 4.2 라우트와 인증

| 라우트 | 용도 | 접근 |
| --- | --- | --- |
| `/community/list` | 전체 피드 | 공개 |
| `/community/[postId]` | 게시글 상세 | 공개 |
| `/community/register` | 새 글 작성 | 로그인 필요 |
| `/community/register?postId={id}` | 본인 글 수정 | 로그인 필요 |

현재 `/community` 전체를 보호하는 미들웨어는 `/community/register`만 보호하도록 축소한다. 공개 화면의 로그인 필요 액션은 현재 URL을 `redirect`로 보존해 로그인 화면으로 이동한다.

로그인 필요 액션은 다음과 같다.

- 글쓰기
- 게시글 수정·삭제
- 게시글 좋아요
- 댓글·대댓글 작성
- 댓글·대댓글 좋아요
- 댓글·대댓글 삭제
- 게시글·댓글 신고
- 좋아요한 글 조회

## 5. 화면 설계

### 5.1 목록

목록은 피드 중심 단일 컬럼을 기본으로 한다.

상단부터 다음 순서로 배치한다.

1. 커뮤니티 소개 문구와 글쓰기 버튼
2. 게시글 검색
3. `최신`, `인기`, `좋아요한 글`
4. 지역·상권 필터
5. 게시글 목록

게시글 카드는 다음 정보만 표시한다.

- 지역·상권 태그
- 제목
- 본문 미리보기
- 좋아요 수
- 댓글 수
- 작성 시각
- 작성자 표기 `사장님`

작성자 닉네임과 프로필 이미지는 Swagger에 없으므로 노출하지 않는다. `memberId`는 소유권 판별에만 사용하고 화면에 표시하지 않는다.

모바일에서는 필터를 가로 스크롤로 제공하고 글쓰기 버튼을 하단 고정 액션으로 제공한다. 데스크톱에서는 본문 너비를 제한해 긴 문장의 가독성을 유지한다.

### 5.2 상세

상세는 고유 URL을 사용하는 전체 페이지다.

- 모바일: 본문과 댓글을 한 흐름으로 읽는 단일 컬럼
- 태블릿 이상: 본문과 지역 사이드바의 2열 구조
- 사이드바: 현재 게시판 대상과 같은 지역의 다른 게시글
- 본문 하단: 게시글 좋아요, 댓글 수, 신고
- 댓글 뒤 최하단: 이전 글과 다음 글

이전 글·다음 글은 목록에서 상세로 이동할 때 저장한 인접 글 정보가 있는 경우에만 표시한다. 직접 URL 진입이나 새로고침으로 인접 정보가 없으면 영역 전체를 숨긴다.

### 5.3 댓글

댓글은 1단계 대댓글까지만 시각적으로 들여쓴다. Swagger 응답의 `replies` 배열 이상으로 중첩하지 않는다.

각 댓글과 대댓글은 다음 액션을 제공한다.

- 좋아요
- 답글
- 본인 댓글 삭제
- 신고

Swagger에 수정 API가 없으므로 댓글 수정 UI는 제공하지 않는다. 신고는 대상 종류와 대상 ID를 고정한 뒤 500자 이내 사유를 입력하는 다이얼로그로 처리한다.

### 5.4 글쓰기와 수정

글쓰기는 별도 페이지의 한 화면 폼이다.

1. 지역·상권 선택
2. 제목
3. 본문
4. 비활성 이미지 첨부
5. 게시하기

제목과 본문은 앞뒤 공백을 제거한 값이 한 글자 이상일 때만 제출할 수 있다. 제목은 120자, 본문은 5,000자로 제한한다. 이미지 첨부는 `준비 중` 문구와 함께 노출하지만 포커스와 클릭을 받을 수 없는 비활성 상태로 제공한다.

게시글 수정 Swagger는 제목과 본문만 받는다. 수정 화면에서는 기존 대상 지역을 읽기 전용으로 보여주고 제목과 본문만 변경한다.

## 6. URL과 조회 상태

목록의 공유 가능 상태는 URL 쿼리를 정본으로 사용한다.

| 쿼리 | 값 | 의미 |
| --- | --- | --- |
| `view` | `latest`, `popular`, `liked` | 목록 종류 |
| `keyword` | 문자열 | 검색어 |
| `targetType` | `DISTRICT`, `ADMINISTRATION`, `COMMERCIAL` | 지역 대상 종류 |
| `targetCode` | 문자열 | 지역 대상 코드 |

최신과 인기는 게시글 목록 API의 `sortType`을 사용한다. 좋아요한 글은 전용 API를 사용한다. 검색어가 존재하면 검색 API를 사용한다.

검색 API에는 `targetType`, `targetCode`가 없으므로 검색 시작 시 지역 필터를 URL에서 제거하고 “검색 결과는 전체 지역 기준입니다”라고 안내한다. 현재 페이지 결과만 프론트에서 필터링하지 않는다.

커서 페이지네이션 규칙은 다음과 같다.

- 최신순: 마지막 항목의 `postId`를 `lastPostId`로 전달
- 인기순: 마지막 항목의 `postId`와 `likeCount`를 각각 `lastPostId`, `lastLikeCount`로 전달
- 좋아요한 글: 전용 목록의 동일 커서 규칙 사용
- `hasNext`가 `false`이면 추가 요청 중지

## 7. API 데이터 흐름

저장된 `frontend/docs/api/openapi/community.json`을 커뮤니티 API 정본으로 사용한다.

| 기능 | Method | Swagger 경로 |
| --- | --- | --- |
| 목록 | GET | `/api/v1/community/posts` |
| 검색 | GET | `/api/v1/community/posts/search` |
| 좋아요한 글 | GET | `/api/v1/community/posts/liked` |
| 상세 | GET | `/api/v1/community/posts/{postId}` |
| 작성 | POST | `/api/v1/community/posts` |
| 수정·삭제 | PATCH, DELETE | `/api/v1/community/posts/{postId}` |
| 게시글 좋아요 | POST | `/api/v1/community/posts/{postId}/likes` |
| 댓글 목록·작성 | GET, POST | `/api/v1/community/posts/{postId}/comments` |
| 댓글 좋아요 | POST | `/api/v1/community/posts/{postId}/comments/{commentId}/likes` |
| 댓글 삭제 | DELETE | `/api/v1/community/posts/{postId}/comments/{commentId}` |
| 신고 | POST | `/api/v1/community/reports` |

지역 선택은 `region-map.json`의 지역 API와 현재 프로젝트의 지역 선택 패턴을 재사용한다. 자치구에서 행정동, 행정동에서 상권으로 좁히며, 최종 선택 결과를 커뮤니티의 `targetType`, `targetCode`로 변환한다.

상세 진입 시 게시글과 댓글을 병렬 조회한다. 태블릿 이상 사이드바는 게시글의 `targetType`, `targetCode`로 같은 지역 목록을 별도 조회하고 현재 게시글을 제외한다. 이 요청의 실패는 본문과 댓글을 막지 않는다.

현재 회원 정보가 있으면 응답 `memberId`와 비교해 수정·삭제 권한을 표시한다.

## 8. 클라이언트 구조

기존 React Query 공급자와 API 클라이언트를 유지한다. 새 상태 관리 패키지는 추가하지 않는다.

책임 경계는 다음과 같다.

- 계약 타입: Swagger 요청·응답, 커서, 필터 타입
- API 모듈: HTTP 요청과 응답 반환
- 쿼리 모듈: 커뮤니티 쿼리 키, 목록 커서, 캐시 무효화
- 목록 뷰: URL 필터와 피드 조합
- 상세 뷰: 본문, 지역 사이드바, 인접 글 조합
- 댓글 스레드: 댓글·대댓글 액션
- 작성 폼: 입력 검증과 생성·수정 분기
- 공통 UI: 로그인 유도, 신고 다이얼로그, 로딩·오류·빈 상태
- 개발 mock: Swagger 형태 fixture와 개발 환경 전용 어댑터

기존 500~700줄 규모 페이지 컴포넌트는 위 책임 경계로만 분리한다. 커뮤니티 작업과 관계없는 추상화나 공통 컴포넌트 재작성은 하지 않는다.

## 9. 좋아요와 캐시 처리

게시글과 댓글 상세 응답에는 현재 사용자의 `liked` 여부가 없다.

- 좋아요 수는 서버 응답 값을 표시한다.
- 상세 최초 진입 시 버튼은 중립 상태로 표시한다.
- 토글 성공 응답의 `liked`, `likeCount`로 해당 버튼과 관련 캐시를 갱신한다.
- 좋아요한 글 목록에서는 목록 자체가 좋아요 상태를 의미하므로 활성 상태로 표시한다.
- 서버 오류 시 낙관 상태를 남기지 않고 기존 값으로 복원하거나 응답 전까지 변경하지 않는다.

댓글 좋아요도 동일하게 처리한다. 초기 활성 여부를 추측하거나 `localStorage`를 서버 정본처럼 사용하지 않는다.

게시글 작성·수정·삭제와 댓글 작성·삭제가 성공하면 영향받는 목록, 상세, 댓글 쿼리만 무효화한다.

## 10. 인접 글

인접 글 API가 없으므로 목록 카드에서 상세로 이동하기 직전에 현재 렌더링된 순서의 이전·다음 항목을 `sessionStorage`에 저장한다.

저장 데이터는 현재 게시글 ID, 목록 조건 식별자, 이전·다음 게시글의 ID와 제목으로 제한한다. 목록에서 상세로 이동할 때 상세 URL의 `from` 쿼리에 같은 목록 조건 식별자를 넣는다. `from` 값은 내부 일치 검사용이며 사용자 데이터를 포함하지 않는다.

- 목록 조건이 다르면 기존 인접 정보를 사용하지 않는다.
- 상세 URL의 `from` 값이 없거나 저장된 목록 조건과 다르면 사용하지 않는다.
- 현재 게시글 ID가 다르면 사용하지 않는다.
- 직접 URL 진입, 새 탭, 새 세션에서는 숨긴다.
- 이 데이터는 탐색 편의 정보이며 API 정본으로 취급하지 않는다.

## 11. 로딩·오류·빈 상태

### 로딩

- 목록: 게시글 카드 스켈레톤
- 상세: 제목, 본문, 액션 영역 스켈레톤
- 댓글: 댓글 행 스켈레톤
- 지역 선택: 선택 목록 로딩 표시

### 오류

- 목록 기본 조회 실패: 설명, 재시도, 홈 이동
- 검색 실패: 검색 조건 유지, 해당 영역 재시도
- 상세 실패: 목록 복귀와 재시도
- 댓글 실패: 본문 유지, 댓글 영역 재시도
- 같은 지역 글 실패: 사이드바만 축소
- mutation 실패: 입력값 유지, 액션 주변에 재시도 가능한 오류 표시

### 빈 상태

- 전체 피드: 첫 글 작성 유도
- 검색: 검색어 초기화
- 지역 필터: 지역 필터 해제
- 좋아요한 글: 전체 또는 인기 글 탐색
- 댓글: 첫 댓글 작성 유도

## 12. 개발용 mock 모드

`process.env.NODE_ENV !== 'production'`인 개발 환경에서만 `?mock=1`을 인식한다. 운영 빌드에서는 해당 쿼리를 무시하고 실제 API를 사용한다.

mock 모드는 다음을 제공한다.

- Swagger 형태의 게시글 목록, 상세, 댓글, 대댓글
- 최신, 인기, 좋아요한 글
- 검색과 지역 필터
- 임시 로그인 사용자
- 글쓰기, 수정·삭제, 좋아요, 댓글·대댓글, 신고의 세션 내 상호작용

mock은 API 실패 시 자동으로 켜지지 않는다. 실제 API 모드의 네트워크 오류가 fixture로 숨겨지지 않도록 명시적으로 분리한다.

## 13. Swagger로 검증하기 어려운 부분

- 게시글과 댓글의 작성자 닉네임·프로필 표시
- 상세 최초 진입 시 게시글·댓글 좋아요 활성 여부
- 직접 URL 진입 시 이전 글·다음 글
- 이미지 업로드와 게시글 이미지 표시
- 댓글 수정
- 분석 결과 첨부 메타데이터 저장과 상세 카드 재구성
- 검색어와 지역 필터의 동시 적용
- 백엔드가 꺼진 로컬 환경에서 실제 성공 응답과 권한 오류 검증

이 항목은 프론트에서 임의 데이터를 만들어 실제 API처럼 처리하지 않는다. 개발용 mock은 UI 검증 수단으로만 사용한다.

## 14. 구현 순서

1. Swagger 타입, API 함수, 쿼리 키 교체
2. 미들웨어와 로그인 복귀 경로 수정
3. 목록 검색, 정렬, 지역 필터, 좋아요 목록, 커서 페이지네이션
4. 상세 반응형 레이아웃, 같은 지역 글, 인접 글
5. 게시글과 댓글 액션
6. 작성·수정 폼
7. 개발 전용 mock
8. 단위 테스트와 브라우저 검증

## 15. 검증 기준

자동 검증은 프론트엔드 디렉터리에서 실행한다.

- `pnpm format:check`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`
- `pnpm build`

단위 테스트 대상은 다음과 같다.

- 목록 URL 파라미터 직렬화와 파싱
- 최신·인기·좋아요 목록 커서 계산
- 제목과 본문 입력 제한
- 인접 글 저장·복원 조건
- 개발 환경 밖에서 mock 모드가 비활성화되는 조건
- `/community/list`, `/community/[postId]` 공개와 `/community/register` 보호

브라우저는 3000이 아닌 `3100` 포트에서 검증한다.

- 데스크톱, 태블릿, 모바일 레이아웃
- mock 정상 피드, 검색, 지역 필터, 빈 상태
- 상세, 댓글, 대댓글, 좋아요, 신고
- 글쓰기와 수정
- 실제 API 모드의 백엔드 연결 실패 상태
- 비로그인 공개 열람과 로그인 필요 액션의 복귀 URL

백엔드가 실행되지 않으면 실제 성공 응답 연동은 검증 결과에 `확인 필요`로 명시한다.

## 16. 완료 조건

- 구 커뮤니티 API 경로와 지원되지 않는 카테고리·이미지 전송이 제거된다.
- 목록과 상세가 공개되고 글쓰기와 mutation 인증 경계가 동작한다.
- Swagger가 제공하는 사용자 기능이 화면에서 접근 가능하다.
- 확정된 반응형 목록·상세·글쓰기 UX가 구현된다.
- 로딩, 오류, 빈 데이터, 비로그인 상태가 구분된다.
- 자동 검증과 3100 포트 브라우저 검증 결과가 기록된다.
- 백엔드, 패키지 버전, lockfile, 빌드·배포 설정은 변경되지 않는다.
