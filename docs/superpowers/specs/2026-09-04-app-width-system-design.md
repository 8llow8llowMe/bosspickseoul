## 1. 문제

헤더 콘텐츠 폭을 전 라우트 `calc(100% - 40px)` 하나로 통일한 결과(PR #207,
DESIGN.md §Navigation), 본문에 상한이 있는 페이지에서 로고와 메뉴가 콘텐츠 바깥에
떠 있게 됐다.

**1920 폭 `/status` 실측: 헤더 좌 20 / 우 1885, 본문 좌 253 / 우 1653 — 좌·우 각각
233px 어긋난다.** 홈(1120px 본문)은 380px로 더 크다.

조사해 보니 헤더 하나의 문제가 아니었다. **컨테이너 폭이 전부 파일마다 박힌 리터럴이고

## 2. 진단

**두 개의 서로 다른 것이 리터럴 하나로 뭉개져 있다.**

- **셸 폭** — 헤더·본문이 공유하는 최외곽 테두리. **정렬은 오직 이것으로 결정된다.**
- **컬럼 폭** — 셸 안에서 콘텐츠 유형별 최적 폭. **가독성은 이것으로 결정된다.**

홈이 1120인 것은 「읽기 컬럼이 그쯤」이라서고 `/status`가 1400인 것은 「지도가 커야
해서」인데, 둘 다 셸 폭으로 표현돼 있어 헤더와 충돌한다.

## 3. 채택안 — 단일 전폭 셸 + 컬럼 토큰

셸은 전 라우트 `calc(100% - 40px)`, 상한 없음(= 헤더와 동일). 그 안에서 컬럼 토큰으로
좁힌다.

### 대안과 기각 사유

| 안 | 내용 | 기각 사유 |
| --- | --- | --- |
| B. 고정 셸 1400 | 셸·헤더 모두 1400 상한 | 홈에서 140px 어긋남이 남고, 2560에서 `/status` 지도가 못 커져 원래 요구에 「아니오」로 답하게 된다 |
| C. `/status`만 개방 | 범위 최소 | 리터럴 9종이 그대로 남는다. 성공 기준(토큰 체계 정리)을 못 채운다 |

**A를 고른 결정적 이유**: 기준 화면 크기를 특정할 수 없다(1440~2560 모두 상정).
셸에 상한을 두면 어떤 값을 골라도 한쪽 끝에서 틀린다. 상한을 요소 레벨로 내리면
화면 크기 가정 자체가 불필요해진다.

### A가 하지 못하는 것

**A는 어긋남을 모든 화면에서 0으로 만들지 못한다.** 읽기 폭 720짜리 화면을 헤더에
맞출 방법은 없다. §5의 「중앙」 그룹에는 어긋남이 남는다.

A가 없애는 것은 **근거 없는 어긋남**이고, 남기는 것은 **읽기를 위해 지불한 어긋남**이다.
지금은 둘이 구분되지 않는다는 것이 문제의 본질이다.

## 4. 토큰

`src/styles/global-styles.ts`의 `:root`에 `--radius-*` · `--motion-*`과 같은 층위로
넣는다.

```css
/* 셸 — 헤더·푸터·모든 라우트 본문이 공유하는 최외곽 테두리. 상한 없음. */
--shell-gutter: 20px;
--w-shell: calc(100% - var(--shell-gutter) * 2);

/* 컬럼 — 셸 "안"에서 콘텐츠 유형별 상한 */
--w-read: 720px;  /* 읽기 텍스트 · 커뮤니티 글 · 긴 카피 */
--w-form: 880px;  /* 등록 · 설정 폼 */
--w-wide: 1400px; /* 밀도 높은 대시보드 블록 */

@media (max-width: 640px) { :root { --shell-gutter: 16px; } }
```

세 개뿐인 것은 의도다. §5의 판정 결과 실제로 쓰이는 폭이 셋이라 그만 정의한다.
**새 폭이 필요해지면 리터럴을 쓰지 말고 토큰을 추가한다** — 리터럴 9종의 표류가
이 작업을 부른 원인이다.

거터를 토큰으로 올리면 헤더·푸터·프로필·커뮤니티가 각자 들고 있던 거터 미디어쿼리
7개(6개 파일)가 사라진다.

### 셸 공유 방식

공유 컨테이너 컴포넌트는 존재하지 않는다. `css` 헬퍼로 만든다.

```ts
// src/styles/layout.ts
export const shellWidth = css`
  width: var(--w-shell);
  margin: 0 auto;
`
```

`<PageShell>` 컴포넌트가 강제력은 높지만, 기존 13개 컨테이너가 각자 grid·flex·padding을
이미 들고 있어(특히 `/status`의 `DesktopGrid`는 셸이자 그리드다) 감싸면 두 겹이 된다.
헬퍼는 있는 것 안에 합성된다.

### 핵심 규칙 — 이것을 어기면 A가 조용히 B로 퇴화한다

> **셸은 페이지의 최외곽 컨테이너다. 컬럼 토큰은 페이지 컨테이너가 아니라 그 안의
> 요소에 건다.**

홈의 페이지 컨테이너를 `min(1120px, var(--w-shell))`처럼 두면 1920에서 헤더 좌 20 /
본문 좌 400 — 지금과 똑같이 380px 어긋난다. 리터럴이 토큰으로 바뀔 뿐 문제는 그대로다.

정렬은 **글이 아니라 박스로 판정된다.** 홈을 셸 전폭으로 열고 벤토 카드의 왼쪽 모서리가
로고와 같은 x=20에서 시작하면, 히어로 카피가 가운데 있는 것은 어긋남이 아니라 의도된
중앙 배치로 읽힌다.

## 5. 라우트별 적용

3분류로 판정한다.

- **개방** — 셸 전폭. 넓어질 때 이득인 요소가 지배. 어긋남 0
- **채움** — 셸 전폭으로 열되 남는 자리를 사이드바로 채움. 어긋남 0
- **중앙** — 좁은 컬럼 유지, 어긋남 수용. **읽기·폼에 한정**

| # | 대상 | 현재 | 판정 | 근거 |
| --- | --- | --- | --- | --- |
| 1 | 헤더 | `100%-40` | 기준 | `--w-shell` 토큰화만 |
| 2 | 푸터 | 1120 | 개방 | 링크 열 — 넓으면 열을 늘린다. 헤더와 위아래 틀을 이룬다 |
| 3 | 홈 hero | 1120 | 개방 | 카피만 `--w-read`, 데모 패널 현행 |
| 4 | 홈 인기지역 | 1120 | 개방 | `1fr 1fr` → `auto-fit`으로 열 증가 |
| 5 | 홈 벤토 | 1120 | 개방 | `1.4fr 1fr` 벤토, 넓으면 열 추가 |
| 6 | 홈 스토리 | 1120 | **중앙 `--w-wide`** | 아래 5.1 |
| 7 | `/status` | 1400 | 개방 | 지도가 이득. 상세카드 `auto-fit` 열 상한 필수 |
| 8 | 분석 결과 | 1320 | 개방 | 세로막대·도넛 다수. 가로막대·미터는 이미 상한 보유 |
| 9 | AI 리포트 | 1080 | 중앙 `--w-read` | AI 생성 산문 = 읽기 |
| 10 | 시뮬 빌더 | 1320 | 개방 | `1fr 380px` — 좌측 폼이 넓어지면 이득 |
| 11 | 시뮬 비교 | 1000 | 개방 | `repeat(2,1fr)` — 열이 시나리오 수 |
| 12 | 시뮬 리포트 | 800 | 중앙 `--w-read` | 읽기 |
| 13 | 추천 비교 | 1120 | 개방 | 비교표 |
| 14 | 커뮤니티 등록 | 880 | 중앙 `--w-form` | 폼 |
| 15 | 커뮤니티 목록 | 880 | **중앙 `--w-form`** | 아래 5.2 |
| 16 | 커뮤니티 상세 | 1180 | 개방 | 이미 `1fr 300px` 사이드바. 본문에 `--w-read` |

중앙 그룹(6 · 9 · 12 · 14 · 15)의 잔여 어긋남은 **페이지 상단 전폭 배경 밴드**로
처리한다. 좁은 카드가 넓은 판 위에 놓인 것으로 읽혀 어긋남이 아니게 된다.

### 5.1 홈 스토리를 개방하지 않는 이유

스티키 스텝목록 `360px` + 패널 `minmax(0,1fr)` 구조인데, 지난 세션에 **패널을
`flex: 0 1 600px`로 늘어나지 않게 못박았다**(R5 가로 스택 바가 세로 막대보다 짧아
데모가 헐렁해지기 때문). 셸 전폭으로 열면 그 결정 때문에 우측이 크게 빈다.

개방하려면 패널 확장 결정을 뒤집고 데모 내부를 재설계해야 하므로 이번 범위 밖이다.
**열린 질문으로 남아 있던 04단계 패널 여백(명세 D8-11 · D9-5)과 한 덩어리**라 함께
다뤄야 한다.

### 5.2 커뮤니티 목록을 개방하지 않는 이유

글 목록 행이 `minmax(0,1fr) auto`라 넓히면 제목과 메타가 멀어져 **손해다.**

셸 전폭 + 우측 사이드바(인기글·필터)로 채우면 어긋남 0이 되고 상세(#16)와 구조도
같아지지만, **그것은 폭 체계 작업이 아니라 커뮤니티 기능 기획이다.** 범위 밖으로 둔다.

**감수하는 것**: 상세는 사이드바가 있고 목록은 없어 두 화면의 폭이 달라진다.

## 6. 넓어질 때의 규칙

셸에 상한이 없으므로 **상한은 요소가 진다.** 이것이 이 설계의 유일한 방어선이라
DESIGN.md에 명시한다. 지금 Charts 절에 흩어져 있는 것(가로막대 560, 미터 360, 15:1)을
§5 Layout Principles로 끌어올려 일반 규칙으로 만든다.

| 넓어질수록 좋아짐 — 셸 전폭 허용 | 무관 | 넓어질수록 나빠짐 — 상한 필수 |
| --- | --- | --- |
| 지도 | 아이콘 · 배지 | 가로 막대 → 560px |
| 세로막대 · 꺾은선 · 도넛 | 버튼 | 미터 행 → 360px |
| 비교표 (열 = 비교 항목) | | 읽기 텍스트 → 720px (`--w-read`) |
| 카드 그리드 (열 증가, 상한 있음) | | 리스트 행 (제목↔메타가 멀어짐) |
| | | 폼 필드 → 880px (`--w-form`) |

### 6.1 `auto-fit` 금지 조항

`/status` 상세카드(`status/status-detail.tsx:364`)에서 실제로 발견한 함정이다.

```css
/* 지금 — 2560px 칸에서 18열까지 간다 */
grid-template-columns: repeat(auto-fit, minmax(140px, 1fr));
```

`auto-fit`은 열 수에 상한이 없고 CSS에 `max-columns`가 없다.

> **규칙: 상한 없는 `auto-fit`은 금지한다.** `auto-fit`은 반드시 폭 상한(컬럼 토큰)과
> 짝을 이룬다. 최소 트랙 폭만으로는 열 폭주를 막지 못한다.

`/status` 상세카드는 최소 트랙을 140px → 200px로 올리고 그리드에 `--w-wide` 상한을
건다. 지표 카드가 커져 가독성도 함께 오른다.

> 참고: 핸드오프는 이 카드가 「넓은 칸에서 대부분 빈 공간이 된다」고 적었으나
> **틀렸다.** `auto-fit`이라 반대로 열이 폭주한다. 손볼 방향이 반대다.

### 6.2 DESIGN.md에 남길 원칙

> **반응형은 좁아질 때를 다루지만, 넓어질 때는 요소마다 따로 정해야 한다.** 셸은
> 상한이 없으므로 상한은 요소가 진다. 「반응형이니까 괜찮다」는 좁아지는 방향에만
> 참이다.

## 7. 검증

### 7.1 토큰 회귀 — vitest

기존 `src/styles/global-styles.test.ts` 규약(`ServerStyleSheet`로 CSS를 뽑아 문자열
단언)을 그대로 쓴다. 캡션 토큰을 못박은 것과 같은 방식으로 폭 토큰이 리터럴로
되돌아가는 것을 막는다.

### 7.2 정렬 불변식 — 브라우저 실측 (주 증거)

> **개방 라우트에서 헤더 Inner의 `left`/`right` == 본문 셸의 `left`/`right`**

`getBoundingClientRect`로 1440 · 1920 · 2560 세 폭을 순회한다. **1440 이상에서
스크린샷이 백지로 나오므로 수치가 유일하게 믿을 수 있는 근거다.**

| 라우트 | 실측 | 비고 |
| --- | --- | --- |
| `/` | 가능 | |
| `/status` | 가능 | 핵심 케이스 |
| `/community/list`, `/community/[id]` | 가능 | 목록은 중앙이라 어긋남 허용값 검증 |
| `/recommend`, `/recommend/compare` | 가능 | |
| `/simulation`, `/simulation/compare` | 가능 | |
| `/analysis/result` | **불가** | 선택 상태 없이 열리지 않는다 |
| `/profile/*` | **불가** | 미들웨어 보호 (`middleware.ts:17`) |

### 7.3 실측 못 하는 2곳

이 계획의 정직한 약점이다.

- **`/analysis/result`(개방 대상 #8)** — 분석 흐름을 실제로 태워 진입 경로를 먼저
  찾는다. 안 되면 SSR 테스트 + 코드 검토로 대체하고 **미검증으로 명시**한다.
  지난 세션에 B2 · B4 · B5를 미검증으로 머지한 전례가 있으므로, 반복한다면 최소한
  목록으로 남긴다.
- **`/profile/*`** — 로그인이 필요하다. 사람 검증 항목으로 넘긴다.

### 7.4 `auto-fit` 소스 스캔 테스트 (선택)

규칙을 문서에만 두면 다음 사람이 또 밟는다. `src`에서 `repeat(auto-fit`을 찾아 같은
styled 블록에 폭 상한이 있는지 확인하는 테스트. 거칠지만 이 저장소는 이미 문자열 단언
테스트를 쓰고 있어 이질적이지 않다. **과하다고 판단되면 뺀다.**

## 8. 커밋 분할

지난 세션에 `scrollbar-gutter`를 별도 커밋(`27b6b7db`)으로 뺀 것과 같은 이유다.
라우트별로 쪼개면 한 화면이 잘못돼도 그 커밋만 되돌릴 수 있다.

1. 토큰 + `shellWidth` 헬퍼 도입 — **동작 변화 0이어야 한다. 첫 검증 지점이다.**
2. 헤더·푸터를 토큰으로 전환
3. 라우트별 커밋 — `/status`, 홈, 커뮤니티, 분석, 시뮬, 추천, 프로필
4. DESIGN.md 규칙 갱신

## 10. 작업 환경

```bash
rm -rf .next && PORT=5173 pnpm dev
```

- `qa:verify`가 `.next`를 프로덕션 산출물로 채우므로 dev 전에 지운다
- HMR이 끊겨 옛 CSS가 보이면 **dev 서버를 재시작**한다
- `pnpm dev -- -p 5173`은 실패한다(`--`가 그대로 넘어가 `-p`를 디렉터리로 읽는다)
- 숨겨진 브라우저 pane에서는 하이드레이션·rAF·scroll이 죽는다
- `$prop` 기반 styled CSS는 마크업 문자열에 나오지 않는다 — `ServerStyleSheet().getStyleTags()`에서 읽는다
- styled 템플릿의 CSS 주석 안에 백틱을 쓰면 템플릿이 거기서 끊긴다
- PR 라벨 `frontend-web`이 배포 게이트다. base는 `develop`, 머지는 merge commit
- `jenkins/branch` 컨텍스트는 여러 서비스 잡이 공유한다 — `target_url`에
  `bosspickseoul-frontend-web`이 들어갔는지 확인한다
