### 순서 — 보드를 문장 **앞**에 둔다 (열린 질문 1의 답)

설계 §4 표는 문장 뒤(2,160)로 적었으나 **산술이 성립하지 않는다.**

- 앵커는 `position: sticky` + `min-height: 100dvh` 다. 트랙이 100dvh 면 **핀 구간이 0** 이라
  단어 채우기 효과가 아예 돌지 않는다. 효과를 남기려면 트랙 > 100dvh 여야 한다
- 트랙을 150dvh(1,620)로 줄여도 문장이 끝나는 지점은 `1,080 + 1,620 = 2,700`(2.5 화면)이라
  보드는 그 뒤가 된다 — **목표(≤2.0 화면)를 못 맞춘다**

보드를 앞에 두면 보드가 `y=1,080`(**1.0 화면**)에서 시작해 목표를 넘어서 달성하고, 앵커의
스크롤 효과도 그대로 남는다. 읽는 순서도 「무엇을 하는 서비스인가(히어로) → 어떤 도구로
이루어져 있나(보드) → 왜 그렇게 하나(문장) → 각 단계는 어떻게 도나(스토리)」로 자연스럽다.

## 최종 배치

```
Hero (0.9)  →  네 도구 보드 (1.0)  →  앵커 문장 (1.5)  →  판단 흐름 (4.0)  →  인기 지역 (3.0)  →  벤토 (1.0)
```

문서 높이는 **줄어든다**: 12,205 → 약 11,400 (앵커 −756, 보드 +~800 중 상쇄).

## 역할 경계 — 보드와 스토리 (열린 질문 2의 답)

D9-1 이 「카운터 vs 스텝 목록」 중복으로 겪은 실수를 반복하지 않기 위해 **문서로 못박는다.**

| 요소       | 말하는 것                                   | 말하지 않는 것                     |
| ---------- | ------------------------------------------- | ---------------------------------- |
| **보드**   | **무엇을 · 어디로** — 네 단계의 이름과 링크 | 각 단계가 어떻게 도는가(데모·수치) |
| **스토리** | **어떻게** — 단계별 데모, 좁혀지는 수치     | 도구 목록(보드가 이미 말했다)      |

두 요소는 `story-steps.ts` **한 정본**을 공유한다. 문구가 갈라지면 같은 단계가 두 이름을 갖는다.
