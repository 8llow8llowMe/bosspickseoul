## D1. 기능 개요

창업 조건 5개(프랜차이즈 여부·자치구·업종·매장 면적·층 구분)를 단계적으로 수집해 단일 POST로 예상 창업 비용을 계산하고, 비용 구성·권리금·유사 프랜차이즈·상권 참고 지표를 렌더한다. 로그인 사용자는 결과를 저장해 이력으로 다시 볼 수 있다.

```
마법사 입력 → 요청 정규화 → POST /simulations/reports (동기) → 리포트 렌더 → (인증) 저장 → 이력 목록
```

## D4. 상세 동작 정의

> **API 문서**: [simulation-frontend-guide](../../../../backend/docs/simulation-frontend-guide.md) · Swagger `commercial-service/v3/api-docs`

### D4-1. 입력 마법사 → 요청 정규화

| 사용 엔드포인트                             | 용도                 | 응답 → 내부 모델 매핑                                       | 비고                  |
| ------------------------------------------- | -------------------- | ----------------------------------------------------------- | --------------------- |
| `GET /simulations/store-sizes?serviceCode=` | 소/중/대 프리셋 제시 | `small/medium/large` → `SimulationSizeItem`, `dataBaseYear` | 공개. 404=미지원 업종 |

단계 순서: ① 프랜차이즈 여부 → ② 자치구 → ③ 업종 → ④ 브랜드(프랜차이즈만) → ⑤ 매장 크기·층(개인 창업은 ④). ③이 ②보다 뒤에 오는 것은 화면 편의일 뿐이고, **③이 브랜드보다 앞서는 것은 계약상 강제**다.

`buildSimulationReportRequest`가 화면 상태를 요청 본문으로 정규화한다.

```
franchisee === false            → franchiseeId 키 제거
periodCode 가 빈 문자열/공백    → periodCode 키 제거 (서버가 적재 기준 최신 분기로 해석)
storeSize                        → ㎡ 정수, 1 이상 (프리셋은 힌트일 뿐 임의 양수 허용)
```

#### D4-1-1. 단계 노출 방식 — 한 번에 하나만 편다 (확정 2026-09-08)

D4-1 은 **순서**를 정의하지만 **한 화면에 몇 개를 보여줄지**를 정하지 않았다. 그래서
구현은 네 단계를 전부 펼친 채로 나왔고, 「마법사」라는 이름과 어긋났다.

##### 무엇이 문제인가 (실측, 1440x900)

| 항목                | 값                  |
| ------------------- | ------------------- |
| 한 화면에 놓인 버튼 | **59개**            |
| 페이지 높이         | 1301px              |
| 375px 모바일 스크롤 | **3.5화면**         |
| 선택 칩             | 자치구 25 + 업종 30 |

화면은 이미 마법사의 부품을 갖고 있다 — 카드에 1·2·3·4 번호가 붙어 있고, 매장 조건은
업종 전이면 잠기며, 우측 패널이 진행 상태를 보여준다. **전부 동시에 열려 있어서 그
구조가 드러나지 않을 뿐이다.**

##### 규칙

1. **펼쳐진 단계는 항상 하나다.** 나머지는 「번호 · 제목 · 고른 값 · 변경」 한 줄로 접는다.
2. **선택하면 다음 미완료 단계가 자동으로 펼쳐진다.** 단일 선택 단계(창업 형태 · 자치구 ·
   업종 · 브랜드)는 고르는 순간이 곧 완료다. **「다음」 버튼을 두지 않는다** — 누를 것이
   하나뿐인 화면에서 확인 버튼은 클릭 수만 늘린다.
3. **매장 조건만 예외다.** 크기와 층 둘 다 채워야 완료이므로, 둘째 값을 고른 순간 진행한다.
   **면적 직접 입력은 타이핑하는 동안 진행하지 않는다** — Enter 를 누르거나 입력칸을 벗어날
   때(blur) 진행한다. 한 글자마다 진행시키면 층을 먼저 고른 사람이 `66` 을 치려다 `6` 에서
   섹션이 접혀 6㎡ 로 확정된다(2026-10-01 실측). 입력하는 동안은 이 단계를 「사용자가 연
   단계」로 붙잡는다. 포커스가 같은 단계의 프리셋·층 칩으로 옮겨 가는 blur 는 진행으로 치지
   않는다 — 그 칩은 눌리는 순간 스스로 진행한다(Safari 는 클릭한 버튼에 포커스를 주지
   않으므로 pointerdown 으로 가린다).
4. **접힌 줄을 누르면 그 단계만 다시 펼쳐진다.** 뒤 단계의 상태는 그대로 둔다(무효화
   연쇄에 걸리는 경우는 아래 참조). 되짚어 통과하게 만들지 않는다.
5. **자동 진행의 대상은 「다음 미완료 단계」이지 「번호가 다음인 단계」가 아니다.** 재편집
   중이라 뒤가 이미 다 채워져 있으면 열 곳이 없으므로 **전부 접고 결과로 시선을 넘긴다.**
   이 규칙 하나로 첫 입력과 재편집이 같은 코드 경로를 쓴다.

   구현은 **「사용자가 연 단계가 이기고, 선택할 때마다 그 값을 비운다」** 하나로 이 규칙과
   무효화 연쇄를 함께 만족시킨다. gap 을 사용자 클릭보다 앞세우면 뒤가 비어 있는 동안 앞
   단계의 「변경」이 죽은 컨트롤이 된다.

6. **잠금은 기존 그대로다.** 매장 조건은 `serviceCode` 전이면 잠기고, 잠긴 줄은 펼칠 수
   없으며 「업종을 고르면 열려요」를 그 자리에 적는다.
7. **브랜드는 프랜차이즈일 때만 있는 독립 단계다. 단계 수는 개인 창업 4개, 프랜차이즈 5개다.**
   (2026-10-01 결정 Q4로 이전 규칙 「브랜드는 업종 단계 안, 단계 수는 항상 4개」를 뒤집었다.)
   업종 안에 두면 프랜차이즈는 실제로 6번을 고르는데 화면은 「조건 4개」라고 말해 끝이 보이지
   않았다. 모델은 `SIMULATION_CONDITION_SECTIONS` 에 `brand` 를 업종 뒤에 넣고, 지금 화면에
   놓이는 섹션은 `listSimulationConditionSections(state)` 로 얻는다. 번호·진행도(`n/N`)·남은
   조건·체크리스트가 모두 이 목록을 쓴다.
   - `service` 는 업종만으로 끝나고, `brand` 는 프랜차이즈면 **유효한 업종 + `franchiseeId`** 가 있어야 끝난다.
     업종 없이 남은 브랜드(손상된 링크)는 완료로 세지 않고, 링크 복원(`createSimulationConditionState`)에서도 버린다.
   - 브랜드는 업종 전에 **잠긴다**(규칙 6과 같은 모양). `franchisees` 가 `serviceCode` 필수다. 잠금 판정은
     `isSimulationSectionLocked` 하나를 화면의 `locked` 와 `resolveOpenSection` 이 같이 쓴다.
   - 오류 되돌리기: `SIMULATION_003`(없는 브랜드) · `SIMULATION_004`(브랜드 누락) · 필드 `franchiseeId` → `brand`.
   - 사용자가 연 단계가 **화면에 없거나 잠겼으면** 무시하고 첫 미완료 단계를 연다(`resolveOpenSection`).
     화면 조작으로는 생기지 않고(창업 형태를 고르면 연 값이 비워진다) URL 해시가 지목할 때 생긴다 —
     개인 창업 링크의 `#simulation-section-brand`, 업종 없는 링크의 `#…-brand`·`#…-store`.

##### 진입 시 어느 단계가 열리는가

| 진입 상황                                  | 열리는 단계                    |
| ------------------------------------------ | ------------------------------ |
| 빈 상태                                    | 1단계(창업 형태)               |
| 상권분석에서 넘어옴 (`variant='analysis'`) | **첫 미완료 단계**             |
| 이력·URL 에서 조건 복원 (B2)               | 전부 완료면 **모두 접은 상태** |

프리필과 복원이 따로 분기를 갖지 않는다 — **「첫 미완료 단계를 편다, 없으면 다 접는다」**
하나로 둘 다 처리된다. 이것이 위저드 대신 아코디언을 고른 실질적 이유 중 하나다.

##### 무효화 연쇄를 숨기지 않는다

`selectService`는 업종을 바꾸면 **`franchiseeId`·`brandName`·`storeSize`를 함께 비운다**
(업종별 값이라 남기면 근거 없는 입력이 된다). `selectFranchisee`도 브랜드를 비운다.

전부 펼쳐진 지금 화면에서는 비워진 칸이 눈에 보였다. **접으면 안 보인다.** 재편집으로
업종을 바꾼 사용자가 「다 골랐다」고 믿는데 매장 조건이 비어 있는 상태가 만들어진다.

> **규칙: 앞 단계를 바꿔 뒤 단계가 비워지면, 그 즉시 비워진 첫 단계를 펼치고 무엇이
> 다시 필요한지 그 자리에 적는다.** 사용자가 접힌 줄을 눌러 확인하게 두지 않는다.

##### 선택지가 많은 단계에는 검색을 붙인다

자치구 25개·업종 30개는 **단계를 나눠도 그 단계 하나를 그대로 채운다.** 단계 분리만으로는
고르는 일이 쉬워지지 않는다. 두 단계에 이름 검색 한 줄을 둔다.

- 입력과 동시에 필터링하고, 남은 개수를 `4/25` 형태로 보여준다
- 결과가 없으면 빈 격자 대신 문구로 대체한다
- 검색어는 그 단계를 벗어나면 버린다(다음에 다시 열면 전체 목록으로 시작)
- 업종 검색은 이름 부분 일치에 일상어 별칭(`카페` → 커피-음료, `술집` → 호프-간이주점, `빵` → 제과점 …)을
  더한다. 판정은 추천·분석과 같은 `matchesOption` 이고 별칭 표·한 글자 별칭 규칙은
  [condition-selector D4-4](../recommend/condition-selector.md) 에 있다(#571). 0건이면
  `"{검색어}" 검색 결과가 없어요. 자주 찾는 업종 목록을 대신 보여 드려요.` 와 함께 자주 찾는 업종 6개를 보여 준다.

**업종은 대분류로 묶는다**(2026-10-01, `SimulationServicePicker`). 검색만으로는 분류를 모르는
사람이 30개를 훑어야 한다. `simulation-catalog.ts` 의 6분류(음식점·학원·레저/오락·서비스·도소매·생활용품)를 쓴다.

- ≥1024: 여섯 묶음을 다 펼치고 소제목은 왼쪽 열에 둔다(칩 위에 얹으면 분류마다 한 줄씩 늘어 752px → 556px).
- ≤1023: 공용 탭(`ui/tabs`)으로 된 대분류 필터 줄에서 분류 하나만 펼친다. 소제목은 탭이 대신하므로 숨긴다.
  업종 단계 섹션 전체 실측: 375 최대 475px(가장 큰 음식점 10개), 768 375px, 1440 556px. 전에는 375 에서 칩 격자만 2열 15줄(약 770px)이었다.
- 처음 펼치는 분류는 고른 업종의 분류, 없으면 첫 분류(음식점)다. 섹션이 접히면 언마운트되어 다시 열 때 그 규칙으로 돌아간다.
- 검색어가 있으면 분류를 무시하고 30종 전체에서 거른 결과를 한 격자로 보여 준다(필터 줄을 내린다).

**브랜드는 검색이 먼저다.** 기본 목록 순서는 서버가 정하고 인기순이 아니다(정렬은 BE 문의 중 — 계획서 Q5).

- 자리표시자는 `브랜드명 일부만 입력해도 찾아요`, 첫 조회 동안 `브랜드를 불러오는 중이에요` 문구를 보인다(dev 실측 5.8초).
- **출구**: 목록 아래 `찾는 브랜드가 없나요? 개인 창업 기준으로 계산하기`, 검색 결과가 없을 때도 같은 버튼. 누르면 창업
  형태가 개인 창업으로 바뀌어 브랜드 섹션이 사라지고 다음 미완료 단계가 열린다. 비교 편집기는 창업 형태 필드가 옆에 있어 그리지 않는다.

##### 접근성

- 접힌 줄은 `<button aria-expanded>`, 펼친 내용은 그 버튼이 제어하는 영역이다
- **자동 진행 시 새로 펼쳐진 단계의 헤더 버튼으로 포커스를 옮긴다.** 옮기지 않으면
  키보드·스크린리더 사용자는 화면이 바뀐 것을 모른 채 사라진 요소 자리에 남는다
- 잠긴 단계는 버튼이 아니라 정적 요소로 둔다(누를 수 없는 버튼을 만들지 않는다)

##### 반응형

≥1024 는 우측 비용 패널이, ≤1023 은 하단 요약 바(`SimulationSummaryBar`)가 진행 상태와 `계산하기`를 맡는다.
**≤1023 에서는 계산 전 본문 결과 패널을 숨긴다**(2026-10-01) — 두 곳에 같은 버튼이 보이고 체크리스트가 아코디언
헤더를 반복했다. 그 대신 바가 진행도 `n/N` 을 숫자로 보여 준다. 결과·오류가 생기면 패널이 입력 아래에 나온다.

**하단 고정 바는 푸터를 가리지 않는다**(#605). 바는 `position: fixed` 라 문서 흐름에 자리가 없다. 본문(`main`)에 바 높이만큼
여백을 줘도 그 뒤의 푸터는 맨 아래에서 바 뒤에 깔려 375 에서 푸터 로고가 비쳤다. 그래서 바마다 `SimulationBottomBarSpacer` 가
**문서 끝(`body` 마지막, 푸터 뒤)**에 바를 잰 높이만큼 빈 칸을 둔다(커뮤니티 상세 하단 바와 같은 방식). 높이는 상수가 아니라
ResizeObserver 로 잰 값이다 — 리포트 바는 저장 결과 한 줄·오류 두 줄에 따라 71~119px 이고 safe-area 만큼 더 커진다.
≥1024 는 바가 숨어 0 이다. 입력·리포트 화면의 본문 하단 여백은 비교 화면과 같은 48px 로 돌렸다.

#### D4-1-2. 자동 계산과 조건 보존 (2026-10-10, #604·#568·#635)

##### 조건이 모두 정해지면 계산한다 (#604)

1023px 이하에서는 계산 전 결과 패널이 숨어 마지막 한 탭(「계산하기」)에서 멈추는 사용자가 생겼다. 조건이 모두 정해지는 순간
계산한다. 판정은 `src/lib/simulation/auto-calculate.ts` 의 `shouldAutoCalculate` 하나다.

- **「정해졌다」는 펼친 단계가 없다는 뜻이다**(`openSection === null`). 조건 완성(`gap === null`)만 보면 층을 먼저 고른 사람이
  면적 `66` 을 치다 `6` 에서 계산이 나간다. 입력 화면의 진행 시점(칩 선택·면적 Enter·blur, D4-1-1 규칙 3)이 그대로 계산 시점이다.
  끝난 단계를 들여다보려고 펼친 동안에도 계산하지 않는다.
- **같은 조건으로 두 번 보내지 않는다.** 마지막으로 보낸 조건의 키(`simulationConditionKey` — 표시용 `brandName`·분기 제외)와 같으면
  보내지 않는다. 오류가 나도 같은 조건이면 되풀이하지 않는다 — 다시 보내는 것은 「다시 계산」을 누를 때뿐이다.
- **300ms 디바운스**(`SIMULATION_AUTO_CALCULATE_DELAY_MS`). 그 사이 「계산하기」를 누르면 키가 이미 같아져 자동 계산은 나가지 않는다.
  요청 중에 조건이 바뀌면 끝난 뒤에 보낸다.
- **진입 때 이미 완성된 조건은 계산하지 않는다**(리포트에서 되돌아옴·새로고침·링크). 진입만으로 POST 를 보내지 않는다 —
  리포트에서 되돌아온 사람은 방금 그 결과를 봤다. 이때 버튼은 「계산하기」다.
- 버튼은 남는다. 지금 조건으로 이미 보냈으면(오류 뒤 등) 라벨은 「다시 계산」, 계산 중이면 패널 `고른 조건으로 예상 창업 비용을
계산하고 있어요`, 하단 바 `조건을 다 골랐어요. 비용을 계산하고 있어요` 와 버튼 로딩으로 알린다.
- **결과 카드에는 「다시 계산」을 두지 않는다.** 결과가 보이는 동안은 그 결과가 지금 조건의 결과다(조건을 고치면 결과를 내린다).
  같은 조건으로 다시 보내도 같은 값이 오므로 결과 위의 다시 계산은 누를 이유가 없는 버튼이다. 「다시 계산」이 쓰이는 곳은 결과가
  없는 상태, 곧 오류 뒤의 하단 바 버튼이다(결과 패널은 오류 안내의 재시도가 맡는다). #604 「버튼은 다시 계산으로 남긴다」의 범위가 여기다.
- **보조기기 알림.** 버튼을 누르지 않아도 계산이 시작·완료되므로, 입력 화면에 시각 숨김 `role="status"`(polite) 영역을 늘 두고
  글자만 바꾼다(`describeSimulationCalculationStatus`). 계산 중 `고른 조건으로 예상 창업 비용을 계산하고 있어요`, 완료
  `예상 총 창업 비용 2억 3,450만원`. 실패는 비운다 — 오류 안내가 `role="alert"` 로 제목부터 읽으므로 두 영역이 같은 오류를 겹쳐 읽지 않게.
  결과 열은 ≤1023 에서 계산 전에 숨으므로 이 영역은 그 밖에 둔다.

##### 입력 중인 조건을 주소창에 보존한다 (#568)

조건이 바뀔 때마다 주소창을 조건 코덱(`toSimulationConditionSearchParams`) 형식으로 맞춘다(`src/lib/simulation/builder-url.ts`).
새로고침하거나 「저장한 결과」를 보고 돌아와도, 계산 전 조건을 링크로 보내도 같은 조건으로 열린다. 읽는 쪽은 그대로
`parseSimulationConditionState` 다 — 리포트의 「조건 다시 고르기」 링크와 같은 키다.

- **`replaceState` 다.** 히스토리를 쌓지 않는다. 첫 인자로 `window.history.state` 를 넘긴다 — 추천 화면의 URL 거울과 같은 이유로
  Next 라우터가 내부 호출로 보고 RSC 왕복을 붙이지 않는다. 대가로 `useSearchParams` 는 진입 값에 머문다(이 화면은 초기값으로만 읽는다).
- **조건 키만 바꾼다.** 분석 컨텍스트의 `ctx…` 키처럼 코덱이 모르는 키와 해시(`#simulation-section-…`)는 남긴다.
  비워진 칸(업종을 바꿔 비워진 면적)은 주소에서도 지운다.
- **분석 경유 화면(`/analysis/simulation`)도 모든 조건 키를 싣는다(#635).** 분석 컨텍스트는 조건 키와 겹치지 않는 `ctx` 키로 따로 싣고,
  새 형식이라는 표식 `ctx=1` 을 늘 함께 싣는다(`src/lib/simulation/analysis-context.ts` 의 `SIMULATION_ANALYSIS_CONTEXT_PARAMS`·
  `SIMULATION_ANALYSIS_CONTEXT_MARKER`). 분석 결과 화면의 「이 상권 창업 비용 계산하기」는
  `buildSimulationAnalysisHref` 로 컨텍스트만 실어 보내고, 입력 화면은 비어 있는 자치구·업종을 컨텍스트로 채운 뒤 거울이 조건 키로도 적는다.
  그래서 자치구·업종을 바꾸고 새로고침하면 바꾼 값으로 열리고, 컨텍스트 카드는 여전히 분석 조건을 보여 주며 「조건을 직접 바꿨어요」와
  「분석 조건으로 되돌리기」를 띄운다. `/simulation` 과 같은 규칙이다.

  | 뜻                     | 지금 키(#635~)                | 옛 키(#635 이전)                         |
  | ---------------------- | ----------------------------- | ---------------------------------------- |
  | 새 형식 표식           | `ctx=1`(컨텍스트가 없어도 씀) | 없음                                     |
  | 분석 자치구            | `ctxDistrictCode`             | `districtCode`, 더 옛날 `gugun`(구 이름) |
  | 분석 행정동            | `ctxAdministrationCode`       | `administrationCode`                     |
  | 분석 상권              | `ctxCommercialCode`           | `commercialCode`                         |
  | 분석 업종              | `ctxServiceCode`              | `serviceCode`                            |
  | 시뮬레이션 자치구·업종 | `districtCode`·`serviceCode`  | 위와 같은 키(충돌)                       |
  - **옛 링크도 열린다.** 표식도 `ctx` 키도 없으면 옛 키를 컨텍스트로 읽는다(`parseSimulationAnalysisContext`). 표식이나 `ctx` 키가
    하나라도 있으면 옛 키를 읽지 않는다. 새 형식 주소의 `districtCode` 는 사용자가 고른 조건이기 때문이다.
  - **컨텍스트는 마운트 때 한 번 읽어 고정한다.** 입력 화면이 진입 주소에서 컨텍스트를 읽어 `useState` 초기값으로 고정하고, 거울은 그
    값만 새 형식으로 쓴다. 지금 주소에서 다시 읽지 않는다. 다시 읽으면 컨텍스트 없이 연 화면(빈 주소, 빈 코드 링크)에서 거울이 앞서 쓴
    `districtCode` 가 옛 형식으로 읽혀 `ctxDistrictCode` 로 굳고, 새로고침 뒤 카드가 사용자가 고른 자치구를 「분석 조건」이라고 말한다.
    표식은 같은 오독을 새로고침 쪽에서 막는다. 컨텍스트 없이 연 화면의 주소에도 `ctx=1` 이 남아, 새로고침해도 카드가 뜨지 않는다.
  - **옛 링크는 첫 거울 쓰기에서 새 형식으로 바뀐다.** 마운트 직후 거울이 고정한 컨텍스트를 표식과 `ctx` 키로 적고 조건이 아닌 옛 키
    (`gugun`·`administrationCode`·`commercialCode`)를 지운다. 조건을 처음 바꿀 때까지 미루지 않은 이유는, 거울이 마운트 때 어차피
    주소를 한 번 쓰기 때문이다.
  - **리포트·비교를 오가도 컨텍스트가 따라간다.** 분석 경유 화면의 링크(입력 화면의 결과 카드 리포트·비교, 리포트의 「조건 다시 고르기」·
    「조건 고르러 가기」·「다른 조건과 비교」, 비교의 주소 갱신·「조건 하나만 계산하기」·열별 리포트)는 표식과 `ctx` 키를 덧붙인다
    (`withSimulationAnalysisContext`). 리포트·비교는 그 키를 `readSimulationAnalysisContextParams` 로 **옮기기만** 한다 —
    `parseSimulationAnalysisContext` 로 읽으면 리포트 주소의 `districtCode`(계산 조건)를 옛 형식의 분석 조건으로 오독한다.
    `ctx` 키가 없는 옛 리포트 링크에서 돌아가도 표식은 붙어, 입력 화면은 카드 없이 열린다. 요청·캐시 키는 요청에서 만들므로 이 키는
    계산에 섞이지 않는다.

##### 위저드(화면 분리)를 고르지 않은 이유

「첫 사용자도 헤매지 않고, 재계산도 빨라야 한다」가 요구다. 화면을 분리하면 첫 입력은
가장 깔끔하지만 **하나만 고치려고 그 단계로 갔다가 확인 화면까지 다시 와야 한다.**
검토 목업에서 두 방식을 나란히 조작해 확인한 결과다. 아코디언은 접힌 줄 클릭 한 번으로
끝나고, 프리필·복원·URL 상태가 모두 지금 구조 그대로 유지된다.

#### D4-3-0. 비용 구성 — 총액과의 관계 (2026-10-01 확정)

BE `SimulationReportProcessor` 실물 기준으로 **원 단위에서** 총액 = 월 임대료 × 1 + 보증금 + 인테리어 + 가맹 부담금
(보증금 = 월 임대료 × 10, 비프랜차이즈면 가맹 부담금은 0 으로 더한다)을 계산한 뒤, **총액과 각 항목을 따로** 만원 미만에서
버려 내려준다. 그래서 응답의 만원 값끼리는 산식이 정확히 맞지 않을 수 있다(dev 실측: `rentPrice` 326 · `deposit` 3,265 —
326 × 10 = 3,260). 화면은 이 관계를 사용자가 검산할 수 있게 그리고, 어긋나는 이유를 늘 밝힌다.

- `rentPrice` 라벨은 **「첫 달 임대료」**다. 총액에는 한 달 치만 들어가므로 「월 임대료」라 적으면 매달 나가는
  돈이 일회성 총액에 섞인 것처럼 읽힌다. 행 설명에 `이후 매달 같은 금액이 나가요`, 보증금 행에 `월 임대료 10개월분`을 둔다.
  비교 화면도 같은 `toCostBreakdown` 라벨을 쓴다.
- 항목 아래 **`합계 · 예상 총 창업 비용`** 행에 `totalPrice` 를 둔다.
- **버림 안내는 항상 둔다**: 각주 첫 문장은 늘 `금액은 만원 미만을 버려 표시해요.`다. 보증금 설명(월 임대료 10개월분)을
  보고 만원 값끼리 곱하면 어긋날 수 있어서다. 항목 합은 총액보다 **0 ~ (항목 수 − 1)만원** 작을 수 있고(dev 실측: 항목 합
  24,001 · 총액 24,002), 차이가 그 범위면 `그래서 항목을 더하면 합계와 N만원 차이가 나요.`를 덧붙인다. 범위를 벗어난 차이는
  버림으로 설명되지 않으므로 버림 탓으로 돌리지 않는다(`describeCostRounding`).
- 차트 색은 항목에 묶는다(DESIGN.md S-SIM-2). 공용 도넛의 기본 2색 교대는 4조각에서 1·3, 2·4번째가 같은 색이 된다.
- **입력 화면 결과 카드도 같은 규칙으로 구성을 그린다**(2026-10-01). 계산 직후 사용자가 보는 것은 리포트가 아니라 이
  카드라, 총액만 두면 「무엇이 이만큼인가」를 알려면 화면을 옮겨야 했다. 카드에는 항목 행(색 점 · 라벨 · 금액 · 비중)과
  버림 안내만 두고, 행 설명·도넛·합계 행은 리포트 몫으로 남긴다(카드 맨 위 헤드라인이 총액이다). 행·비중·색은 리포트와
  **같은 함수**(`toCostBreakdown` · `toDonutSlices` · `COST_COLORS`)로 낸다 — 두 화면이 같은 값을 다르게 반올림하면
  어느 쪽이 맞는지 사용자가 알 수 없다.
- **결과 카드에도 권리금 제외와 보증금 근거를 둔다**(#554). 대부분은 카드에서 멈추므로, 리포트에만 적힌 「권리금 제외」는
  수천만 원이 빠진 금액을 필요 자금으로 읽게 했다. 카드 각주는 버림 안내 뒤에 `권리금은 예상 총 창업 비용에 포함하지 않았어요.`
  를 잇는다. 이 문장은 카드 · 리포트 비용 구성 각주 · 권리금 카드 각주가 **같은 상수**(`KEY_MONEY_EXCLUDED_NOTE`,
  `lib/simulation/report-presentation`)를 쓴다. 보증금 행에는 리포트와 같은 근거 `월 임대료 10개월분` 을 라벨 아래 12px
  캡션으로 둔다. 첫 달 임대료의 행 설명(`이후 매달 같은 금액이 나가요`)은 라벨이 이미 「첫 달」이라 리포트에만 둔다.
  권리금 **금액**은 여전히 카드에 넣지 않는다 — 총액 옆 금액은 합계로 읽힌다.

#### D4-3-1. `topAgeGroups[].salesAmount` — 집계 단위 제약 (확정)

**단위는 만원이 맞다.** `SimulationReportProcessor.java:196`이 `info.salesAmount() / TEN_THOUSAND`로 나눠 내려보낸다.

문제는 단위가 아니라 **"누구의 매출인가"**다. 원천이 `sales_district`(`DistrictSalesQueryPort` — "데이터 원천은 district 컨텍스트의 sales_district 테이블이다")이므로 이 값은 **자치구 × 업종 전체의 분기 매출**이지 사용자 점포의 예상 매출이 **아니다**. dev 실측 `2,733,782만원`(= 273억원)은 강동구 한식음식점 **업계 전체**의 50대 고객 분기 매출이므로 정상값이다.

UI 슬라이스에서 반드시 지킬 제약 두 가지:

| #   | 제약                                                                                                                                                                                                                                                                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **집계 범위를 라벨에 드러낸다.** "50대 273억원"처럼 두면 사용자가 자기 점포 예상 매출로 읽는다. 창업 비용을 계산하러 온 사용자에게 치명적인 오독이므로 "{자치구명} {업종명} 전체 기준" 같은 범위 문구를 섹션 제목·축 라벨에 붙인다.                                                                                                             |
| 2   | **억 단위 소수 한 자리로 축약한다**(`273.4억원`, 딱 떨어지면 `3억원` — 2026-10-01, 전에는 버림이라 1억 9,600만원이 `1억원`이 됐다). `2,733,782만원`을 축에 그대로 얹으면 읽히지 않는다. 저장소의 기존 억/만원 표기 관행(`src/lib/format.ts`의 `formatLargeWon`, `src/lib/status/status-formatters.ts`의 "N억 M만원" — 구별현황 Top10)을 따른다. |

> 주의: `formatLargeWon`은 **만원 단위 입력**을 받아 "N억 M만원"으로 만든다(`amount / 10000` = 억). `salesAmount`는 이미 만원이므로 그대로 넘기면 되고, `status-formatters`는 **원 단위 입력**을 받으니 둘을 바꿔 쓰면 1만 배 틀린다.

### D4-4. 저장 / 이력

| 사용 엔드포인트                             | 용도      | 응답 → 내부 모델 매핑                                | 비고                                |
| ------------------------------------------- | --------- | ---------------------------------------------------- | ----------------------------------- |
| `POST /simulations/histories`               | 결과 저장 | `history` → `SimulationHistoryItem`                  | **인증 필수**                       |
| `GET /simulations/histories?page=&size=`    | 이력 목록 | `histories[]` + `page/size/totalElements/totalPages` | **인증 필수**, size ≤ 50            |
| `DELETE /simulations/histories/{historyId}` | 이력 삭제 | `dataBody: null`                                     | **인증 필수**, 404 `SIMULATION_006` |

`buildSimulationHistorySaveRequest(request, totalPrice)`가 리포트 요청 + 총비용을 저장 본문으로 옮긴다. **`periodCode`는 저장 계약에 없어 버린다.** 서버가 명칭(자치구/업종/브랜드)과 `dataBaseYear`를 되채워 저장본을 반환하므로 FE는 명칭을 보내지 않는다.

**저장 CTA 는 한 화면에 두 벌이고 상태는 하나다**(2026-10-01). ≥1024 는 왼쪽 sticky 요약 열에, ≤1023 은 하단 고정 바에
저장 버튼이 있고 보이는 쪽은 CSS 로 고른다(SSR 과 결과가 같아야 한다). 버튼마다 mutation 을 들면 한쪽에서 저장해도 다른
쪽은 `결과 저장` 그대로라 창을 넓히거나 기기를 돌리면 같은 조건을 또 저장할 수 있다. 그래서 `useSimulationSave` 가 페이지
한 곳에서 상태를 들고 두 버튼에 내려준다. 저장하면 `role="status"` 로 `저장했어요 · 저장 목록 보기`(프로필 저장 목록)를 알린다.

이력 목록의 **뒷페이지가 비면**(다른 기기에서 지움 등) `아직 저장한 결과가 없어요`가 아니라 `이 페이지에는 결과가 없어요` + `이전`
페이저를 둔다 — 앞 페이지에는 결과가 남아 있다. 삭제 버튼은 ghost 로 「리포트 보기」보다 낮춘다. **되돌리기는 두지 않는다**:
삭제 후 복원하려면 다시 저장해야 하는데 저장 응답에 `franchiseeId` 가 없어 프랜차이즈 기록은 같은 조건으로 되살릴 수 없고,
지연 삭제는 분석 보관함 삭제와 규칙이 갈린다(두 보관함이 같은 프로필 화면에 있다).

이력 삭제는 **프로필의 저장 목록**에서만 한다(리포트 화면에는 두지 않는다 — "저장됨" 잠금과
겹쳐 무엇이 참인지 흐려진다). `historyId`는 문자열 그대로 경로에 싣고, `404 SIMULATION_006`은
미존재·타인 항목을 구분하지 않으므로 **재시도 버튼 없이** 목록만 다시 부른다.

## D5. 비즈니스 로직

### 마법사 진행 분기

브랜드 검색이 업종 선택 뒤에 있는 것이 핵심이다. `serviceCode` 없이 `franchisees`를 부르면 400이다.

### 비교 화면

V2에 비교 API가 없다. `createSimulationReportPair([left, right])`가 `POST /simulations/reports`를 **2회 병렬 호출**한다.

```
allSettled([reports(left), reports(right)])
  둘 다 성공 → 두 리포트를 나란히 렌더
  하나라도 실패 → 비교가 성립하지 않으므로 전체 실패(SimulationPairError(side))로 던지고 오류 UI 1개만 표시
```

부분 성공을 허용하지 않는 이유: 한쪽만 보이는 "비교"는 사용자를 오도한다. 한쪽이 404여도
**결과 0개 + 오류 정확히 1개**다. 한쪽 결과를 그리면 빈 칸이 "비용 0"으로 읽힌다. `allSettled` 는 **어느 쪽이
실패했는지 알아내려고** 둘 다 기다리는 데만 쓴다(2026-10-01, C5) — 금지 대상은 `allSettled` 가 아니라 부분 성공 렌더다.
재시도 판정·오류 분류는 래퍼를 벗긴 원래 오류로 한다(`unwrapSimulationPairError`) — 래퍼째 넘기면 5xx 도 `client` 로 읽혀 자동 재시도가 꺼진다.

#### URL 이 결과의 정본이다

좌우 조건은 `a.`/`b.` 접두사 쌍 코덱(`src/lib/simulation/compare-route.ts`)으로 쿼리스트링에
담기고, **결과도 그 URL 이 가리키는 것**이다. 리포트 화면과 같은 모양으로 `useQuery` +
`enabled`(양쪽 요청이 완성됐을 때만)를 쓴다. 새로고침·뒤로가기·링크로 들어와도 같은 화면이
나오고, 링크를 받은 사람이 `비교하기`를 다시 누를 일이 없다.

| 무엇           | 정본                       | 읽는 함수                             |
| -------------- | -------------------------- | ------------------------------------- |
| 조회할 조건 쌍 | 쿼리스트링                 | `parseSimulationComparePair`          |
| 편집기 초기값  | 쿼리스트링 (미완성도 읽음) | `parseSimulationCompareConditionPair` |
| 편집 중인 조건 | 편집기 상태                | `useSimulationConditions`             |

**자동 계산을 `useEffect`로 하지 않는다.** effect 는 "언제 한 번 쏠지"를 직접 지켜야 해서
라우트 재진입·프리렌더 타이밍마다 답이 달라진다(실제로 슬라이스 B3 에서 그렇게 흔들려
되돌렸다). `enabled`는 조건이 없으면 애초에 돌지 않고 같은 URL 이면 캐시를 집는다 — 판정이
쿼리 키 안에 있다.

**URL 은 `비교하기`를 누를 때만 갱신한다**(`router.replace`). 편집 중에 URL 이 따라 바뀌면
키 입력마다 재계산된다. 그래서 버튼은 계산을 직접 명령하지 않고 URL 을 편집기 상태와 맞추며,
그 URL 이 쿼리를 트리거한다. 조건을 고치지 않고 눌러 URL 이 이미 맞는 경우에는 재탐색할 것이
없으므로 `refetch()`로 같은 조건을 다시 계산한다 — **아무것도 하지 않으면 안 된다.** 활성인
버튼이 눌러도 반응하지 않는 상태가 되는데, 재시도 버튼이 없는 오류(404 는 `isRetryable`이
false 라 안내에 버튼이 붙지 않는다)에서는 화면 어디에도 응답이 없어 사용자가 다음에 무엇을
해야 하는지 알 수 없다. `push`가 아니라 `replace`인 이유는 조건을 고쳐 가며 여러 번 누르는
화면이라 매 계산이 히스토리에 쌓이면 뒤로가기가 이 화면 안에서만 맴돌기 때문이다.

**캐시 키는 한 곳에서 만든다** — `src/lib/simulation/report-query.ts`. 비교 키
(`simulationComparePairQueryKey`)는 단일 리포트 키의 직렬화를 **그대로 두 번** 쓴다. "같은
조건"의 정의가 두 벌이 되면 비교 화면이 시딩한 캐시를 리포트 화면이 빗나가고, 그건 화면을
봐서는 알 수 없는 종류의 어긋남이다. 좌우는 **자리로 구분한다** — 맞바꾼 URL 은 같은 비교가
아니다(라벨과 미러 막대의 좌우가 그 순서로 그려진다).

캐시 시딩은 `queryFn` **안에서** `queryClient.setQueryData`로 한다. v5 `useQuery`에는
`onSuccess`가 없고, effect 로 미루면 시딩이 렌더 한 번 늦어 그 사이에 `상세 리포트 보기`를
누른 사용자만 재호출을 맞는다.

#### 표시 규칙

- 중립 문구 `창업 비용만 비교한 결과예요. 매출·수익 지표는 계산하지 않아요.`는 강조와 **항상
  같은 컴포넌트에서 함께** 렌더한다. 비용 낮은 쪽에 강조만 붙으면 "더 나은 선택"으로 읽히는데,
  이 리포트에 매출·수익 지표가 없어 그 판단의 근거가 없다.
- 미러 막대 비율은 **두 값 중 큰 값** 기준이다. 합 기준이면 항목마다 축이 달라져 막대 길이가
  절대 크기를 잃는다.
- `levy`는 **양쪽 다 null일 때만** 행을 뺀다. 한쪽만 프랜차이즈인 비교가 이 화면의 주된 쓸모라
  그때 행을 빼면 가장 중요한 차이가 사라진다 → 없는 쪽은 `해당 없음`. `levy: 0`(부담금 0원)과
  `null`(비프랜차이즈 해당 없음)은 끝까지 구분한다.
- **행별 차액**(2026-10-01): `describeMirrorRowGap` — `B가 1,129만원 적어요` / `같아요`. 한쪽이 `null`(해당 없음)이면
  쓰지 않는다. 없는 비용과 0원 비용은 뺄 수 있는 값이 아니다.

#### B 는 A 의 복사본으로 시작한다 (2026-10-10, #567 · 결정 D-3)

비교는 보통 한 가지만 바꿔 본다(1층 → 1층 외, 강남 → 마포). B 를 빈 편집기로 열면 창업 형태·자치구·업종·(브랜드)·면적·층을 전부
다시 골라야 했다. 입력 화면 결과 카드와 리포트의 「다른 조건과 비교」는 `buildSimulationCompareHrefFromReport` 하나로 B 에 A 를
복사한 링크(`a.*` = `b.*`, 브랜드명 포함)를 만든다.

- **같은 계산이면 조회하지 않는다.** 복사 직후 URL 의 양쪽은 같은 계산이다. 조회하면 들어오자마자 같은 리포트를 두 번 POST 하고,
  「같아요」만 늘어선 결과가 그려지며, ≤767 에서는 그 결과 때문에 편집기가 접혀 B 를 고치려면 「조건 고치기」부터 눌러야 한다.
  그래서 URL 양쪽이 `isSameSimulationReportRequest` 면 `enabled: false` 이고, 편집기 양쪽이 같으면 `비교하기` 를 끄고
  `조건 B에서 하나 이상 바꾸면 비교할 수 있어요.` 를 보인다. 총비용이 같은 서로 다른 조건의 판정 문장은
  `두 조건의 예상 총 창업 비용이 같아요.` 그대로다.
- **「A와 다름」 배지.** B 편집기는 A 의 상태를 `reference` 로 받아 값이 다른 칸(창업 형태·자치구·업종·브랜드·면적·층) 이름 옆에
  배지를 단다(`listSimulationCompareDifferences`). B 칸이 비어 있으면 다르다고 하지 않는다 — 비운 뒤 모든 칸에 배지가 붙으면
  아무것도 가리키지 않는다. 배지는 `aria-describedby` 로 칸에 잇는다.
- **「조건 B 비우기」.** B 카드 제목 줄의 ghost 버튼(≤1023 히트 영역 44px). B 만 비우고(`useSimulationConditions().reset`) 편집기를
  다시 마운트해 면적 입력 원문·브랜드 변경 중 상태도 버린다. 포커스는 B 의 창업 형태로 옮긴다.
- 「조건 B 비우기」 뒤의 URL·옛 `a.*` 만 있는 링크는 그대로 빈 B 편집기로 열린다 — 한쪽만 있는 URL 은 여전히 오류가 아니다.

#### 편집기와 결과의 관계 (2026-10-01)

- **결과 무효화**: 편집기 요청이 URL 요청(결과의 정본)과 다르면 결과를 흐리고 `조건이 바뀌었어요. 다시 비교해 주세요.`를
  status 로 알린다(`isSameSimulationReportRequest` 좌우 모두). 입력 화면은 조건을 고치면 결과를 내리지만, 비교는 방금 본
  숫자와 견줄 수 있게 지우지 않는다.
- **비교 뒤 접힘(≤767)**: 지금 조건의 결과가 있고 사용자가 펼치지 않았으면 편집기를 CSS 로 접고 한 줄 요약을 둔다(파생값 —
  `hasBoth && !stale && !expanded`). CSS 로만 숨겨 입력 중 값을 잃지 않는다.
- **결과로 이동**: `비교하기`로 시작된 계산이 끝나면 결과 제목으로 포커스, 결과가 화면 아래쪽(60% 아래)이면 스크롤.
- **표시용 브랜드명**: `buildSimulationCompareHref(pair, variant, { left, right })` 가 `a.brandName`/`b.brandName` 을 덧싣는다.
  요청 파싱·캐시 키는 보지 않는다(리포트 경로의 `brandName` 과 같은 규칙). 입력 화면 결과 카드·리포트의 비교 링크도 싣는다.
- **실패한 쪽**: `createSimulationReportPair` 는 `allSettled` 로 둘 다 기다린 뒤, 하나라도 실패하면 `SimulationPairError(side)`
  (`left`·`right`·`both`)로 던진다. 화면은 오류를 하나만 그리되 `scope`(쪽 이름 + 편집기로 가는 CTA)를 넘긴다. 봉투 실패도
  어느 쪽 봉투인지로 쪽을 정한다.

### 오류 → 화면 분기

`@/lib/api/api-error`의 `kind`로만 분기한다. **상태 코드를 직접 비교하지 않는다.**

| `kind`         | 재시도 버튼 | 화면                                            |
| -------------- | ----------- | ----------------------------------------------- |
| `network`      | O           | 기본 문구 + 재시도                              |
| `server`       | O           | "잠시 후 다시 시도" + 재시도                    |
| `not-found`    | **X**       | 서버 `resultMessage` 그대로 + 조건 재선택 유도  |
| `unauthorized` | X           | 로그인 유도 (저장·이력에서만 발생)              |
| `client`       | X           | `fieldErrors[]`를 폼 필드에 매핑, 없으면 메시지 |

- `fieldErrors[]` 의 머리는 한국어 필드 이름이다(`describeSimulationField` — `storeSize` → `매장 면적`). 모르는 필드는 머리를 뺀다.
  BE 메시지(`SimulationValidationMessage`)는 이미 한국어라 그대로 쓴다.
- 오류 제목 수준은 `headingLevel`(기본 3). 리포트·비교는 h1 바로 아래라 2 를 넘긴다.

### D6-1. 백엔드 갭 — 요청 본문 enum 불일치 시 봉투 없는 400

`floorType`에 정의되지 않은 값을 넣어 dev에 실호출한 결과(2026-08-26, 코디네이터 재현 확인):

```
POST /api/v1/simulations/reports   body: { ..., "floorType": "BASEMENT" }
→ HTTP 400
{"timestamp":"2026-08-26T03:22:54.417+00:00","status":400,"error":"Bad Request","path":"/api/v1/simulations/reports"}
```

`dataHeader` 봉투가 **없다.** `CommercialExceptionHandler`의 `COMMERCIAL_102`는 `MethodArgumentTypeMismatchException`(쿼리·경로 파라미터 바인딩)만 잡는데, 요청 **본문** JSON의 enum 역직렬화 실패는 `HttpMessageNotReadableException`이라 핸들러에 걸리지 않고 Spring 기본 응답이 그대로 나간다.

- **영향**: 화면이 이 응답에서 서버 메시지를 얻을 수 없다. `normalizeApiError`가 봉투 없는 본문을 흡수해 `kind: 'client'` + 기본 문구로 처리하므로 크래시는 없지만, 사용자에게 원인을 알려줄 수 없다.
- **FE 완화책**: `floorType`을 자유 입력으로 두지 않고 `SIMULATION_FLOOR_TYPES` 피커에서만 제출해 이 경로에 애초에 들어가지 않게 한다. `buildSimulationReportRequest`의 타입이 `'FIRST_FLOOR' | 'OTHER'`로 좁혀져 있어 컴파일 단계에서도 한 번 막힌다.
- **BE 후속 요청**: 아래 "후속 요청 (백엔드)" 참조. **이 슬라이스에서 백엔드 코드는 건드리지 않았다.**
