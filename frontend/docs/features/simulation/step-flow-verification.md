# 시뮬레이션 「한 번에 한 단계」 전환 — 실측 결과

> **작성일**: 2026-09-08
> **대상**: `/simulation`, `/analysis/simulation`
> **연관 코드**: `src/lib/simulation/step-flow.ts`(`resolveOpenSection`), `src/lib/simulation/conditions.ts`(`SIMULATION_CONDITION_SECTIONS`), `src/components/simulation/simulation-builder-page.tsx`
> **연관 명세**: [simulation.md](./simulation.md) S3 #2, `simulation-report.md` D4-1-1

이 문서는 D4-1-1(「한 번에 한 단계」 전환)이 실제 화면에서 동작하는지 세 폭에서 실측한 기록이다.
측정 스크립트는 다음을 각 상태마다 `main` 기준으로 읽는다.

```js
const main = document.querySelector('main')
JSON.stringify({
  vw: window.innerWidth,
  pageH: Math.round(document.documentElement.scrollHeight),
  buttons: main.querySelectorAll('button').length,
  expanded: main.querySelectorAll('[aria-expanded="true"]').length,
})
```

1차 측정(1440·1024)은 dev 서버(`rm -rf .next && PORT=5173 pnpm dev`)에서 개인 창업 흐름을 기준으로
진행했다. **375 와 프랜차이즈 흐름은 2차 세션(2026-09-08, #250)에서 프로덕션 빌드로 다시 측정해
채웠다** — 아래 「2차 측정」 절에 방법과 결과를 적었다.

## 측정 방법상의 주의 — 375px 에서 `scrollHeight`가 신뢰할 수 없었다

375×812 에서는 페이지 이동 직후 `document.documentElement.scrollHeight`가 실제 콘텐츠 높이보다
훨씬 작은 값(뷰포트 높이와 같은 812)을 돌려주는 경우가 반복 관찰됐다. 같은 순간
`offsetHeight`를 함께 재거나 몇 차례 폴링하면 실제 값(예: 1228)으로 수렴했다 — 하이드레이션이
완전히 끝나기 전에 읽으면 생기는 값으로 보인다(`CLAUDE.md`가 경고하는 "숨겨진 pane 에서는
하이드레이션이 안 돈다"와 같은 계열의 함정).

2차 측정에서는 이 함정을 재지 않고 **먼저 배제**했다. 값을 읽기 전에 하이드레이션이 붙었는지
직접 확인하고(아래), `pageH` 는 250ms 간격 12회 폴링해 값이 흔들리지 않는 것만 적었다.

```js
// DOM 노드에 React fiber 키가 붙었는가. 0개면 클릭이 먹지 않는다.
const hydrated = () =>
  Object.keys(document.querySelector('main')).some(k => k.startsWith('__react'))
```

## 2차 측정 (2026-09-08, #250)

**서버**: `pnpm build` 후 `pnpm start -p 5173`. dev 가 아니라 프로덕션 빌드다 — dev 에서는 HMR
웹소켓이 끊기면 하이드레이션이 아예 붙지 않는다.

**포트가 5173 이어야 한다.** BFF 가 브라우저 `Origin` 을 상류로 그대로 넘기고 백엔드 CORS 허용
오리진이 5173·3000 뿐이라, 5174 에서는 `POST /simulations/reports` 가 **403** 이다. 화면은 이 403 을
「로그인이 필요해요」로 옮겨 보여주므로 인증 문제로 오해하기 쉽다 — 실제로 이번 세션에서
5174 로 먼저 띄웠다가 그 길로 빠졌다. (BFF·CORS 함정 자체는
`docs/handoffs/2026-08-27-131616` 에 이미 기록돼 있다.)

**클릭 주입**: 브라우저 pane 이 숨겨진 상태라 `computer` 액션이 30초 타임아웃으로 계속 실패했다
(1차 세션과 같은 증상). 그래서 상태 전이는 `element.click()` 으로 실제 DOM 이벤트를 발화시켜
진행했고 — React 합성 이벤트는 같은 경로를 탄다 — **눈 확인은 스크린샷으로** 했다. 스크린샷은
pane 이 숨겨져 있어도 정상이다. 포커스 이동은 `document.activeElement` 로 함께 읽었다.

이 방법의 한계를 적어 둔다: `element.click()` 은 실제 클릭과 달리 대상에 포커스를 주지 않는다.
그래서 마지막 칩을 누르는 시나리오에서는 `focus()` 를 먼저 부른 뒤 눌러 실제 클릭의 순서를
맞췄다 — 그러지 않으면 앞 단계에서 남은 포커스를 보고 「복구됐다」고 잘못 읽는다.

### 프랜차이즈 흐름

**2차 측정에서 375 라이브로 확인했다.** 프랜차이즈를 선택하면 업종 섹션의 완료 조건에 브랜드
선택(`franchiseeId`)이 추가되고, 업종을 고르면 그 섹션 안에 브랜드 검색이 열린다(한식음식점 →
10건). 업종 단계는 브랜드를 고르기 전까지 닫히지 않고, 브랜드(중국적식탁)를 고르면 업종 요약이
「한식음식점 · 중국적식탁」이 되면서 매장 조건이 자동으로 펼쳐진다 — 별도 섹션이 아니라 업종
섹션에 종속된 흐름이라는 구조가 화면에서도 그대로 보인다.

업종을 바꾸면 브랜드 선택이 함께 초기화되는 부분은 `conditions.ts` 의 `selectService` 로 코드
확인만 했다(라이브 재현은 하지 않았다) — 이 전이는 `conditions.test.ts` 가 단위로 고정하고 있다.

## 남은 미검증

- 업종을 바꿀 때 브랜드 선택이 초기화되는 전이의 **라이브** 재현(코드·단위 테스트로는 확인).
- 1024 에서 계산 결과 화면(1440·375 에서는 확인).
- CSS 레이아웃 회귀(펼친 설명이 잘리는지 등)는 jsdom 이 CSS 를 계산하지 않으므로 유닛으로 잡히지
  않는다. 이 항목은 폭별 실측이 계속 유일한 수단이다.
