# 상권 추천 — 조건 선택 UX 세부 명세서

> **작성일**: 2026-08-28
> **공통 명세**: 없음 — `recommend` 공통 명세는 아직 작성되지 않았다([\_index](../_index.md) 상태 ⬜). 현행 정본은 코드(`src/components/recommend/**`)이며, 이 문서가 조건 선택 영역에 한해 정본 역할을 한다.
> **연관 명세**: [지도 기반 분석 대상 탐색](../analysis/explorer.md), [모바일/태블릿 반응형 바텀시트](../analysis/mobile-responsive.md)
> **대상**: 웹 (Next.js App Router) — `/recommend` 전 뷰포트, `/analysis` 선택 패널 일부
> **작성자**: Claude
> **상태**: 초안 (구현 대기)

이 문서는 상권 추천(`/recommend`)의 **자치구·행정동·업종 선택 UX**를 재설계한다. 현재는 네이티브
`<select>` 세 개가 세로로 쌓여 지도를 가리고, 같은 선택을 지도 뱃지와 드롭다운이 두 벌로 제공한다.
이를 **조건 바 한 줄 + 선택 뷰 + 지도 지름길**로 바꾸고, 그 과정에서 뽑아내는 **공유 선택
컴포넌트**를 `/analysis` 선택 패널에도 끼워 두 화면의 선택 경험을 한 부품으로 모은다.

**핵심 원칙은 「목록이 정본, 지도는 가속기」다.** 지도 뱃지는 뷰포트에 들어온 영역만 표시하므로
구조적으로 불완전하다(D6-1 측정값). 지도는 목록을 **대체할 수 없고** 목록의 **지름길**일 뿐이다.

## D0. 배경 / 기획 의도

| 항목               | 내용                                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 충족 요구사항      | 상권 추천 — 「어디에 어떤 가게를 열까」 조건 3종(자치구·행정동·업종)을 지도를 가리지 않고 고르게 한다                                                                                                        |
| 해결하려는 문제    | 아래 「현재 문제 4가지」                                                                                                                                                                                     |

| 목표 동작 (to-be)  | 조건 바 한 줄(`강남구 › 역삼2동 › 커피-음료`) + 조각 클릭 시 **패널 내 선택 뷰** 전환 + 지도 뱃지 클릭 지름길. 선택 뷰 안에는 검색 가능한 완전 목록                                                          |
| 구현 제외 범위     | `/recommend` URL 상태 도입(D8-1), 분석↔추천 딥링크 배너(D8-2), 추천 프리셋 노출(서버 결정, 현재 UI 비노출), `/analysis` 선택 패널의 **레이아웃**(4단계 탭·좌측 고정 패널 구조는 그대로 둔다 — D4-5), 결과 뷰 |
| 연관 기능 / 의존성 | `drawAreaLabelLayer`(지도 뱃지, 구현 완료), `RecommendPanel` 뷰 전환, `AnalysisSelectionPanel` 칩 격자, `DESIGN.md` §Inputs & Forms·§영역 폴리곤                                                             |

### 현재 문제 4가지

**1. 지도와 폼이 같은 일을 두 벌로 한다.** 2026-08-28 에 `/recommend` 지도에 지역 이름 뱃지를
붙이면서(`drawAreaLabelLayer`) 자치구·행정동을 지도에서 직접 고를 수 있게 됐다. 드롭다운은 이제
같은 선택의 두 번째 경로다. 화면 상단 3분의 2를 중복 기능이 점유한다.

**2. 지도만으로는 도달할 수 없는 선택지가 있다.** 지도 영역 질의는 뷰포트 기반
(`GET /map/districts?lngSW=…`)이라 화면 밖 자치구는 로드되지 않는다. 그래서 **드롭다운을 그냥
없애면 안 된다** — 지금 드롭다운이 유일한 안전망이다. 실측은 D6-1.

**3. 세 조건의 성격이 다른데 한 덩어리로 다룬다.**

| 조건                | 성격       | 적합한 도구                                             |
| ------------------- | ---------- | ------------------------------------------------------- |
| 자치구(25)·행정동   | **공간**   | 지도(인접성·위치감) + 목록(완전성)                      |
| 업종(31, 6카테고리) | **비공간** | 목록 전용. 지도와 무관하고, 카테고리 그룹핑·검색이 필요 |

**4. 목록 탐색 수단이 없다.** 업종 31개를 네이티브 `<select>` 스크롤로 훑어야 한다. `/analysis`
선택 패널도 같은 문제를 갖는다 — 칩 격자에 검색이 없어 상권 수십 개·업종 31개를 눈으로 스캔한다.

### 왜 「모두 칩 격자」(분석 방식)가 아닌가

`/analysis` 는 좌측 **고정** 패널이라 칩을 펼쳐도 지도를 가리지 않는다. `/recommend` 는 패널이
지도 **위에 떠 있어** 펼치는 만큼 지도가 사라진다. 두 화면의 과업도 다르다.

| 화면         | 과업                                    | 조건 표시 | 근거                                            |
| ------------ | --------------------------------------- | --------- | ----------------------------------------------- |
| `/analysis`  | **검증** — 대상을 이미 안다             | 펼침      | 4단계를 다 밟아야 하고 현재 위치를 늘 알아야 함 |
| `/recommend` | **탐색** — 대상을 모른다. 지도가 주인공 | 접힘      | 지도를 가리면 탐색 자체가 불가능                |

**레이아웃을 통일하는 게 아니라 부품을 통일한다.** 같은 선택 컴포넌트를 분석은 펼쳐서, 추천은
접어서 쓴다.

## D1. 기능 개요

`/recommend` 조건 패널이 「조건 바(요약) ↔ 선택 뷰(목록)」 2단 구조가 되고, 지도 뱃지가 같은
선택 상태를 갱신하는 지름길로 동작한다.

```
조건 바 조각 클릭 | 지도 뱃지 클릭 → 선택 확정 → 조건 바 갱신 → 하위 조건 초기화 → 다음 단계
```

## D4. 상세 동작 정의

### D4-1. 조건 바

패널 헤딩 「어디에 어떤 가게를 열까요?」 바로 아래에 한 줄로 놓인다.

```
[ 강남구 ] › [ 역삼2동 ] › [ 업종 선택 ]
```

- 각 조각은 `<button type="button">`. 누르면 그 단계의 선택 뷰로 전환한다(R-2).
- 값이 있으면 지역/업종 이름, 없으면 `자치구 선택` 같은 플레이스홀더. 플레이스홀더는
  `--color-placeholder`(grey400), 확정값은 `--color-text-900` — `DESIGN.md` §Inputs 의
  플레이스홀더 규칙을 그대로 따른다.
- 상위 조건이 비어 선택할 수 없는 조각은 `disabled` 이고, 사유는 조건 바 아래 헬퍼 한 줄로
  남긴다(현행 `자치구를 먼저 선택해 주세요.` 문구 유지).
- 폭이 좁으면 조각 이름을 말줄임하고 `title` 로 전체 이름을 남긴다. **줄바꿈하지 않는다** —
  한 줄 유지가 이 부품의 존재 이유다.

### D4-2. 선택 뷰 (패널 내 뷰 전환)

**시트를 겹치지 않는다.** `RecommendPanel` 은 이미 `criteria ↔ results` 를 `transitionKey` 로
전환하고 있고, 모바일에서는 그 패널이 곧 바텀시트다. 선택 뷰는 **세 번째 뷰**로 들어간다.
`/analysis` 모바일이 「단일 바텀시트 + 뷰 전환」으로 정리된 것과 같은 판단이다
([mobile-responsive](../analysis/mobile-responsive.md) 참조).

- 뷰 헤더: `← 자치구 선택` + 우측에 항목 수(`25개`). 분석 패널의 `{단계} 선택 · {n}개` 표기와
  같은 형식을 쓴다.
- 본문: `OptionPicker`.
- 나가기: 헤더의 뒤로 가기, `Esc`, 항목 선택. 항목을 고르면 **조건 바 뷰로 자동 복귀**한다.
- 전환은 기존 패널 전이 토큰을 재사용하고 `prefers-reduced-motion` 을 존중한다(R-10).
- **포커스**: 뷰 진입 시 뷰 헤딩(`tabIndex={-1}`)으로 포커스를 옮기고, 복귀 시 열었던 조건 바
  조각으로 되돌린다. 결과 뷰가 `resultHeadingRef` 로 이미 쓰는 패턴과 같다.

### D4-3. 지도 뱃지 지름길

이미 구현돼 있다(`drawAreaLabelLayer`). 이 명세가 추가하는 것은 **규칙**뿐이다.

- 뱃지 클릭은 선택 뷰를 열지 않고 바로 확정한다(R-6).
- 선택 뷰가 열려 있는 동안에도 지도는 조작 가능하다. 뱃지로 고르면 선택 뷰가 닫힌다.
- 뱃지는 **지름길이지 정본이 아니다.** 뷰포트에 없는 지역은 뱃지가 없고, 그것은 결함이 아니라
  구조다(D6-1). 대신 조건 바가 항상 한 번의 탭 거리에 완전 목록을 둔다.

### D4-4. 검색

- 항목 수가 `searchThreshold`(기본 12)를 넘을 때만 노출한다. 자치구 25·업종 31·상권 수십은
  노출, 대부분의 행정동(~20)도 노출된다.
- 매칭은 `name` 에 대한 **부분 문자열**(대소문자 무시, 공백 trim). 초성 검색은 이번 범위 밖이다.
- 그룹 목록에서는 매칭된 항목이 있는 그룹만 남기고, 그룹 라벨 자체는 매칭 대상이 아니다.
- 0건이면 `emptyMessage`(예: `'검색 결과가 없어요.'`)를 보여준다. 검색어를 지우는 버튼을 둔다.
- 검색 입력은 `TextField`(채움형 규격)를 쓴다. 자체 입력 스타일을 새로 만들지 않는다.

### D4-5. `/analysis` 적용 — 레이아웃은 그대로

`AnalysisSelectionPanel` 의 **칩 격자 렌더 부분만** `OptionPicker` 로 교체한다.

- 4단계 탭, 좌측 고정 패널, 단계 헤더(`{단계} 선택 · {n}개`), 오류·재시도 UI는 **건드리지 않는다**.
- 얻는 것은 검색 하나다. 상권 단계 수십 개·업종 31개에서 즉시 효과가 있다.
- 업종 단계는 `simulationCatalog` 의 6카테고리를 `groups` 로 넘겨 그룹 렌더를 받는다. 지금은
  평면 격자라 카테고리 구분이 없다.
- 시각 회귀가 없어야 한다 — 칩 모양·간격·선택 상태는 현행 값을 그대로 옮긴다.

## D5. 비즈니스 로직

### D5-1. 하위 조건 초기화

상위가 바뀌면 하위는 무효다. 현행 `recommend-page` 동작을 규칙으로 고정한다.

| 바뀐 조건 | 초기화 대상 | 이유                   |
| --------- | ----------- | ---------------------- |
| 자치구    | 행정동      | 행정동은 자치구에 종속 |
| 행정동    | (없음)      | 업종은 지역과 독립     |
| 업종      | (없음)      | —                      |

업종은 지역을 바꿔도 유지한다. 「강남에서 카페 자리 찾다가 마포도 볼까」가 흔한 동선이고,
그때 업종을 다시 고르게 하면 손해다.

### D5-2. 목록 완전성 규칙

**모든 선택 뷰 목록은 완전 목록 출처에서만 온다.** 뷰포트 질의 결과(`/map/**`)를 선택 뷰
목록으로 쓰지 않는다.

| 조건   | 선택 뷰 출처 (완전)                             | 지도 뱃지 출처 (부분집합)         |
| ------ | ----------------------------------------------- | --------------------------------- |
| 자치구 | `@/data/districts` (정적 25)                    | `GET /map/districts?bounds`       |
| 행정동 | `GET /regions/districts/{code}/administrations` | `GET /map/administrations?bounds` |
| 업종   | `@/data/simulation-catalog` (정적 31 / 6그룹)   | 해당 없음                         |

이 규칙을 어기면 「지도에 안 보이는 지역은 아예 고를 수 없다」가 된다. 현행 드롭다운은 이미
완전 목록을 쓰고 있으므로, 이 재설계는 그 성질을 **유지**하는 것이지 새로 얻는 게 아니다.

## D6. 주의사항

### D6-1. 지도 뱃지는 구조적으로 불완전하다 (실측)

2026-08-28, `/analysis` 첫 진입(level 8 / 서울시청 중심)에서 측정했다.

| 항목      | 개수     |
| --------- | -------- |
| 칩 목록   | **25개** |
| 지도 뱃지 | **21개** |

지도에 없던 자치구: **강동구·관악구·금천구·도봉구**. 지도 영역 질의가 뷰포트 기반이라
가장자리 자치구가 로드되지 않는다. `/recommend` 에서도 같은 조건에서 22개가 관측됐다
(뷰포트 폭 차이).

**이 사실이 이 명세의 설계를 결정했다.** 지도만 남기고 드롭다운을 없애는 안은 여기서 탈락했다.

### D6-2. 지도 뱃지는 접근성 대체 경로가 될 수 없다

뱃지는 `<button>` 이라 키보드 접근 자체는 되지만, 25개를 탭으로 순회하는 것은 목록보다
나쁘고 뷰포트 밖 항목은 탭 순서에도 없다. **선택 뷰가 정식 경로, 뱃지는 포인터 사용자용
가속기**로 취급한다(R-8).

### D6-3. 호버·포커스로 레이어를 다시 그리지 않는다

`/recommend` 지도는 2026-08-28 에 증분 하이라이트(`setHighlight`)로 옮겼다. 그 전에는
`hoveredAreaCode` 가 레이어 이펙트 의존성이라 호버마다 폴리곤·뱃지를 전부 새로 그렸고, 뱃지가
`<button>` 이라 **키보드로 탭해 들어간 순간 포커스를 잃었다.** 선택 뷰를 붙이면서 이 경로를
되돌리지 않도록 주의한다.

### D6-4. `createGlobalStyle` 은 HMR 로 재주입되지 않는다

`.area-map-label` 처럼 전역에 둔 규칙을 고치면 dev 서버를 재시작해야 반영된다. 컴포넌트 변경만
반영된 화면을 보고 「적용됐다」고 판단하면 안 된다.

### D6-5. 모바일에서 시트를 겹치지 않는다

`RecommendMobileSheet` 는 `isRecommendationSheetInteractive(view)` 로 상호작용 가능 뷰를
판정한다. `'picker'` 를 추가할 때 이 헬퍼와 스냅 높이 규칙을 함께 갱신해야 한다. 선택 뷰는
목록이 길므로 **펼침 스냅**에서 열리는 것이 맞다.

## D8. 미결 사항

### D8-1. `/recommend` URL 상태 (이 명세 범위 밖, 선행 권장)

`/recommend` 는 선택을 React 상태로만 들고 있어 새로고침·링크 공유에서 조건이 사라진다.
[\_index](../_index.md) 의 share Feature 항목에도 「`COMMERCIAL_COMPARISON`(`/recommend` 가 URL
상태 없음)은 거짓 복원을 피하려 미지원」으로 이미 기록돼 있다.

`/analysis` 는 반대로 선택 전체를 URL 쿼리(`districtCode`·`administrationCode`·`commercialCode`·
`serviceCode`·`periodCode`)로 읽는다. 추천도 같은 규약을 채택하면 **화면 보관함 지원 + 딥링크
(D8-2) + 새로고침 복원**이 한 번에 풀린다. 조건 바가 조건을 정본으로 다루는 구조를 만드는
지금이 붙이기 좋은 시점이지만, 선택 UX 와는 다른 축이라 이 문서에서는 분리했다.

### D8-2. 분석 ↔ 추천 딥링크 (별도 슬라이스)

방향은 정해져 있다.

| 우선순위 | 동선        | 넘기는 값                         | 진입점                            |
| -------- | ----------- | --------------------------------- | --------------------------------- |
| **주**   | 추천 → 분석 | 자치구·행정동·**상권**·업종 (4개) | 추천 결과 카드 「이 상권 자세히」 |
| 보조     | 분석 → 추천 | 자치구·행정동·업종 (3개)          | 분석 보고서 **하단** 배너         |

`/analysis` 가 이미 URL 로 선택을 읽으므로 **추천→분석은 링크 한 줄로 오늘 구현 가능**하고,
분석→추천은 D8-1 이 선행돼야 한다. 배너는 보고서 상단에 두지 않는다 — 읽기도 전에 나가라는
신호가 된다.

### D8-3. 초성 검색

`ㄱㄴ` 으로 `강남구` 를 찾는 초성 검색은 한국어 목록에서 체감이 크지만, 이번 범위 밖이다.
`OptionPicker` 의 필터를 교체 가능한 함수로 두어 나중에 끼울 수 있게 한다.

### D8-4. 추천 기준 — 해결됨 (조건 바 대상 아님)

추천 API 의 `preset`(예: 「공격형」)·`priorityMetric`(예: 「기회도」)·`summary` 는 타입에만 있고
화면에는 전혀 그려지지 않았다. 순위를 정한 근거인데 사용자가 볼 수 없었고, 카드의
`selectionReason`("공격형 기준으로 …")에 그 말이 문맥 없이 튀어나왔다.

**사용자가 고르는 값이 아니라 서버가 정해 주는 값이므로 조건 바에 올리지 않는다.** 대신 결과
헤더에 「이 순서를 정한 기준」 블록으로 노출한다(2026-08-28 구현 완료). 사용자가 고른 조건
칩(`SubmittedSummary`)과 시각적으로 구분해 — 같은 칩으로 그리면 사용자가 고른 것처럼 읽힌다.

따라서 **조건 바는 3조각(자치구·행정동·업종) 한 줄을 유지한다.**
