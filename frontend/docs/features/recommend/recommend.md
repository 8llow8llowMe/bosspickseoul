## S1. 기능 개요

사용자는 자치구 → 행정동 → 업종을 고르고, 그 행정동의 상권 중 업종 기준 **상위 5곳**을 점수와 추천 이유로 받아 본다. 지도는 선택을 돕고 결과를 그려 주는 가속기이고, **목록·패널·URL 이 정본**이다. 결과에서 두 상권을 담아 비교하고, 비교 결과를 근거로 커뮤니티 글을 시작할 수 있다.

```text
조건 선택(자치구·행정동·업종) → 행정동 상권 목록 → 업종별 추천 Top 5 → 상권 프로필 → (두 곳 담기) 비교 → 비교 초안으로 글쓰기
```

| 단계        | 호출                                                                        | 인증     |
| ----------- | --------------------------------------------------------------------------- | -------- |
| 행정동 목록 | `GET /regions/districts/{districtCode}/administrations`                     | 불필요   |
| 상권 목록   | `GET /regions/districts/{d}/administrations/{a}/commercials`                | 불필요   |
| 추천        | `GET /commercials/recommendations/by-service` (`commercialCodes[]`·`topN`)  | 불필요   |
| 상권 프로필 | `GET /map/commercials/{commercialCode}/profile`                             | 불필요   |
| 지도 뱃지   | `GET /map/districts` · `/map/administrations` · `/map/commercials` (bounds) | 불필요   |
| 비교        | `GET /commercials/compare` (`leftCommercialCode`·`rightCommercialCode`)     | 불필요   |
| 북마크      | `GET/POST/DELETE /members/me/bookmarks`                                     | **필요** |

### S3-1. 추천 호출이 세 단계인 이유

추천 API 는 **후보 상권 코드 목록을 요구**한다(`commercialCodes[]`). 행정동을 넘기면 알아서 골라 주는 계약이 아니다. 그래서 화면은 행정동 상권 목록을 먼저 받아 전부를 후보로 넘기고, 응답 Top 5 각각의 프로필을 다시 받는다. 후보 목록은 `createStableCommercialCodes` 로 중복 제거·정렬해 **같은 조건이면 같은 쿼리 키**가 되게 한다 — 그렇지 않으면 순서만 다른 같은 요청이 캐시를 빗나간다.

홈 03단계 미리보기(`use-recommend-preview`)가 이 연쇄를 그대로 쓴다. 추천 규칙이 바뀌면 홈도 같이 움직여야 한다.

### S3-2. 지도 뱃지가 목록을 대체할 수 없는 이유 (실측)

지도 영역 질의는 뷰포트 기반이라 첫 진입에서 자치구 25개 중 **21개만** 뱃지가 뜬다(강동·관악·금천·도봉 누락). 그래서 뱃지는 지름길이고 선택 뷰 목록이 정본이다. 상권 경계도 `profile` 이 `centerLng: null`/`boundaryCoords: []` 를 주는 경우가 있어, 결과 폴리곤은 결과 중심점 bbox 로 뷰포트 질의해 우회한다 — 근본 해결은 백엔드가 경계를 채우는 것이다(ux-followups D8).

**상권 뷰포트 질의(`/map/commercials`)는 지도가 실제 화면 범위를 알린 뒤에만 보낸다.** 백엔드는 뷰포트 안 상권이
250개를 넘으면 `MAP_010`(400, 「지도를 확대해 주세요」)으로 거절한다(`backend/docs/map-api-frontend-guide.md`). 화면의
`viewportBounds` 초기값은 서울 전체(`SEOUL_MAP_BOUNDS`)라, 링크로 들어오면 첫 렌더에서 씨앗 행정동 때문에
`commercial` 단계가 되고 씨앗 자동 제출이 `results` 로 넘기기 전 **그 서울 전체 범위로 상권 질의가 한 번 나가 400**
이었다. 지도의 첫 `onViewportBoundsChange`(idle 300ms 디바운스) 전에는 상권 질의를 켜지 않는다. 자치구(상한 50,
서울 25)·행정동(상한 500, 서울 425) 질의는 서울 전체 범위로도 통과하므로 첫 화면을 늦추지 않도록 그대로 둔다.
카카오 지도는 생성 직후 `idle` 을 올리지 않으므로, 링크 카메라(`'url'`)로 들어와 카메라가 움직이지 않으면 범위를 영영
모른다(수정 전에는 서울 전체 bbox 400 으로 조건 링크의 상권 폴리곤이 뜨지 않았다). 그래서 지도는 생성 300ms 뒤
**범위만** 한 번 알린다 — 카메라(`c`)는 올리지 않는다(url-state §2-2 「`c` 는 카메라가 한 번 움직여야 붙는다」).

### S3-3. 지도 컨트롤 (2026-09-29)

- 자리는 **우측 상단**이다. 모바일은 바텀시트가 아래를 덮어 우측 하단이 가려진다.
  공용 부품은 `components/map/map-controls.tsx` 이고 `/analysis` 지도도 「내 위치」를 같이 쓴다.
- 「선택한 지역으로 돌아가기」는 예전 「선택 범위로 이동」 텍스트 버튼이다. 링크 복원·직접 팬으로
  카메라가 선택 영역을 떠났을 때 되돌리고 자동 맞춤을 다시 켠다(동작은 [url-state](./url-state.md) 그대로).
  문구가 무엇의 범위인지 읽히지 않아 아이콘 + 풀어 쓴 접근성 이름(툴팁 동일)으로 바꿨다.
- 「내 위치로 이동」은 **누를 때만** 위치 권한을 묻는다. 서울 밖(`SEOUL_MAP_BOUNDS`)이면 카메라를
  옮기지 않고 토스트로 이유를 말한다 — 데이터가 서울뿐이라 옮기면 빈 지도만 남는다. 권한 거부·시간
  초과도 토스트다. 성공하면 level ≤4 로 옮기고 내 위치 점(primary-600, 흰 테두리 + 맥박)을 그린다.
- 선택된 순위 마커는 먹색(`--color-grey-900`) 배경 + 흰 글자·테두리다. 예전 하늘색(primary-700)
  배경은 파란 폴리곤 채움과 겹쳐 선택이 눈에 띄지 않았다.

### S3-4. 실시간 많이 본 상권 (2026-09-29)

조건 카드는 짧아 데스크톱 좌측 아래가 비었다. 그 자리에 `GET /analysis-rankings?areaType=COMMERCIAL`
(최근 N시간 **조회 수** 순위) 상위 5개를 5초마다 한 줄씩 돌려 「살아 있는 화면」을 만든다.

- **추천 활동을 지어내지 않는다.** 「n분 전 다른 사용자가 ○○를 추천받았어요」는 백엔드에 추천 이벤트
  기록이 없어 근거가 없다. 문구는 「실시간 · 최근 24시간 많이 본 상권」이다. 추천 활동을 보여 주려면
  백엔드에 추천 이벤트 적재 + 최근 활동 API 가 먼저 필요하다(후속).
- 순위 API 만 따로 죽을 수 있다(RANKING_001 503). 실패·집계 비어 있음이면 띠를 **그리지 않는다**.
- 1분마다 다시 읽는다. 마우스·포커스가 들어오면 회전을 멈추고(WCAG 2.2.2), 동작 줄이기 설정이면
  돌리지 않는다. live region 이 아니다 — 포커스하면 현재 줄을 읽는다.
- 조건 뷰에서만 보인다. 결과·선택 뷰는 패널이 높이를 다 쓴다. 모바일 시트에는 넣지 않았다.

### S3-5. 조건 수정과 이전 결과 (#570, 2026-10-10)

예전에는 「조건 수정」을 누르는 순간 `submitted: null` 로 결과가 사라지고 비교 담기도 비었다.
업종 하나만 바꿔 보려던 사용자가 마음을 바꾸면 처음부터 다시 받아야 했다.

- **결과는 새로 제출할 때만 바뀐다.** `editRequested`·`districtSelected`·`administrationSelected`·
  `serviceSelected` 는 `submitted`·`selectedCommercialCode`·`resultSelectionSource` 를 그대로 둔다.
  비교 담기는 `submitted.requestKey` 가 바뀔 때만 비운다(기존 규칙) — 그래서 조건을 고치는 동안에도
  남는다. 선택은 그 선택을 담은 `requestKey` 와 함께 들고(`readCompareSelection`), 열쇠가 다르면
  **그 렌더에서** 빈 선택으로 읽는다. 예전처럼 이펙트로 비우면 새로 제출한 직후 한 프레임 동안
  이전 선택이 새 결과 위에 보인다. 예외는 링크가 들고 온 없는 행정동(`administrationRejected`)뿐이다.
- 조건 화면 머리에 「직전 추천 결과가 남아 있어요 · {자치구} {행정동} · {업종}」 줄과
  **「이전 결과로 돌아가기」** 버튼을 둔다. `submitted` 가 있을 때만 보인다.
- 돌아가면(`previousResultsRestored`) **고치던 초안은 버리고 마지막 제출 조건으로 되돌린다.**
  초안을 남기면 결과 헤더(제출 조건)와 조건 바·URL·지도(초안)가 서로 다른 조건을 말한다.
  고른 상권·비교 담기·지도 카메라 규칙(사용자가 고른 상권이면 그 상권)도 그대로 돌아온다.
  버튼이 사라지므로 포커스는 결과 제목으로 옮긴다.
- **결과가 오기 전에 「조건 수정」을 눌렀다가 돌아와도 1위 자동 선택(링크면 지목한 상권)이 온다.**
  응답 처리(`handleRecommendationResponseOnce`)는 결과 뷰일 때만 응답을 소비한다
  (`isResultsView`). 조건 화면에 도착한 응답은 미뤄 두고, 결과 뷰로 돌아오는 순간 처리한다.
  리듀서가 뷰와 무관하게 선택을 받게 하는 방법도 있었지만, 그러면 조건 화면에서 결과 제목에
  포커스를 옮기는 부작용까지 따로 막아야 해서 소비를 미루는 쪽을 택했다.
- **결과 헤더의 조건 칩은 버튼이다.** 누르면 그 조건의 선택 뷰로 곧장 간다
  (`editRequested` + `step`, 업종 칩 → 업종 선택 뷰). 접근성 이름은
  「{조건} 바꾸기, 지금 조건 {값}」이다. 터치 대상 44px.
- 업종 하나 바꿔 다시 받기는 「조건 수정 → 업종 칩 → 업종 → 상권 추천받기」 4탭에서
  「업종 칩 → 업종 → 상권 추천받기」 3탭이 됐다. 업종을 고르는 즉시 자동 제출하면 2탭이지만,
  제출은 사용자가 누르는 한 번으로 남겨 둔다(조건을 둘 이상 고치는 동선을 끊지 않는다).
- 선택 뷰를 닫으면 조건 화면으로 간다(기존 규칙). 결과로 돌아가는 길은 「이전 결과로 돌아가기」다.
  포커스는 그 버튼(없으면 조건 화면 제목)으로 옮긴다([condition-selector D4-2](./condition-selector.md)).

### S3-6. 결과 시트 첫 화면 (#569, 2026-10-10)

모바일 결과 시트 첫 화면을 결과 헤더와 기준 상자가 먼저 차지해 375×667 에서 1위 카드는 위쪽
52px 만 보였다(이름·점수 줄이 잘림).

- **비교 바는 선택이 1개 이상일 때만** 그린다. 그때도 정원 문구와 「비교하기」 버튼을
  **한 줄**(버튼 44px)로 둔다. 정원 문구는 하나다(#559): 1개면 「비교할 상권 2개를 골라 주세요
  (1/2)」, 2개면 「비교할 상권 2개를 골랐어요 (2/2)」. 예전의 「2개 이상」·「2개까지」는 정원이
  정확히 2개라는 사실과 서로 모순이었다. 비교 화면의 잘림 안내도 「비교는 상권 2개씩 해요」로 맞췄다. 담기는 카드마다 있는 「비교」 체크가 시작한다. 1개면 버튼은 잠기고
  무엇이 필요한지 말한다(`aria-describedby`, 기존 규칙).
- **「이 순서를 정한 기준」은 기본 접힘**이다(disclosure 버튼, `aria-expanded`·`aria-controls`).
  접힌 줄에도 「공격형 · 기회도 우선」 요약을 남겨 무엇으로 줄 세웠는지는 바로 읽힌다. 펼침 상태는
  화면 안 일시 상태라 URL·리듀서에 올리지 않는다.
- **지표 행**은 이름 아래에 방향 문구, 오른쪽에 등급 배지 + 게이지를 둔다.
  - 방향 문구: 아는 지표 4종(기회도·거주수요 「높을수록 좋아요」, 위험도·혼잡도 「낮을수록
    좋아요」)은 `describeMetricPolarity`. **모르는 지표는 방향을 지어내지 않고 API 의
    `metricType.scoreDescription`(「점수가 높을수록 …」)을 그대로 옮긴다.** 아는 지표에는
    `scoreDescription` 을 쓰지 않는다 — 「점수가 높을수록 위험 요인이 큽니다」는 사실이지만
    좋은지 나쁜지를 독자가 다시 뒤집어 읽어야 한다.
  - 등급 배지: `getScoreQualityLabel` — 좋음·보통·**주의**. 「나쁨」은 상권을 단정해 「주의」로
    바꿨다(게이지의 스크린리더 문구도 같다). 면은 중립 회색, 등급색은 6px 점으로만 거든다.
    배지는 게이지의 접근성 이름과 같은 말이라 `aria-hidden` 이다. 방향을 모르는 지표는 배지가 없다.
- 실측(Playwright, `view=results` 링크, 역삼1동·커피-음료, 결과 시트 펼침):

  | 뷰포트     | 1위 카드 상단 | 보이는 1위 카드 높이 | 이름·점수 줄(72px)까지 보이는 카드 |
  | ---------- | ------------- | -------------------- | ---------------------------------- |
  | 375×667 전 | 608           | 52px                 | 0                                  |
  | 375×667 후 | 536           | 124px                | 1                                  |
  | 390×844 전 | 644           | 193px                | 1                                  |
  | 390×844 후 | 572           | 265px                | 1                                  |

  1위는 결과 도착 때 자동 선택돼 상세(배지·지표 4행·빈 업종)가 펼쳐진 채라 카드 하나가 약 900px
  이다. 그래서 둘째 카드는 첫 화면에 들어오지 않는다 — 「1.5장」을 원하면 1위 상세를 접힌 채로
  두는 별도 결정이 필요하다. 시트 안에서 비교 바는 패널 `Content` 를 스크롤 컨테이너로 삼아
  시트 바닥에 붙는다(#647 부터 `Content` 가 시트의 유일한 스크롤 칸이라 데스크톱처럼 고정된다.
  그전에는 `Content` 가 스크롤하지 않아 목록 끝에 붙어 있었다).

### S3-7. 추천 ↔ 시뮬레이션 링크 · 비교 공유 (#566 · #573, 2026-10-10)

- **추천 카드 보조 행동**에 「창업 비용 계산」을 「상권 분석 보기」 다음에 둔다. 시뮬레이션 조건은 자치구·업종까지라
  카드마다 같은 링크다(`RecommendResultList` 의 `simulationLink` — 함수가 아니라 값). 접근성 이름은 상권명이 아니라
  링크가 실제로 채우는 조건이다(「강남구 커피-음료 창업 비용 계산」, `describeSimulationLink` — 시뮬레이션이 모르는 업종이면
  업종을 뺀다). 링크 넷이 360 카드 한 줄에 다 들어가지 않아 `SecondaryActions` 가 줄을 바꾼다.
- **추천 비교 Actions**: 「이 비교로 글쓰기」 다음에 「창업 비용 계산」(같은 링크)과 「공유」(V2 `COMMERCIAL_COMPARISON`,
  분석 결과와 같은 흐름·토스트 — [share](../share/share.md) D3).
- 목적지는 `/analysis/simulation` 이 아니라 **`/simulation`** 이다. 앞쪽은 「분석 조건을 그대로 채워 뒀어요」 카드를 띄우는데
  추천에서 온 사람에게는 사실이 아니다. 입력 화면은 `parseSimulationConditionState` 로 두 칸을 채운다. 시뮬레이션이 다루지 않는
  업종(30종 밖)은 버리고 자치구만 채운다.
- **시뮬레이션 리포트 → 추천**: 「이 구에서 상권 추천받기」가 `createRecommendHrefFromCodes({districtCode, serviceCode})` 로
  조건 화면에 자치구·업종을 채운다. 행정동은 추천에서 고른다(리포트 조건에 없다). 시뮬레이션 30종은 전부 추천 카탈로그에도 있어
  업종이 빠지지 않는다(`recommend-url.test.ts` 가 30종 전부 고정).

### S3-8. 모바일 시트 스크롤 칸과 여백 (#647, 2026-10-10)

모바일 시트 안 목록(업종·자치구·행정동 선택, 추천 결과)이 휠·터치로 스크롤되지 않아 아래 항목을 누를 수 없었다.

- **원인**: 시트 본문(`RecommendMobileSheet` 의 `SheetBody`)과 패널 `Content` 가 **둘 다 스크롤 칸**이었다. 패널은 시트 본문
  안에서 내용 높이만큼 늘어나 스스로는 스크롤할 거리가 없는데 `overscroll-behavior: contain` 을 들고 있어, 스크롤 체인이
  그 칸에서 멈추고 실제로 넘치는 시트 본문으로 넘어가지 않았다(지도·드래그 손잡이는 무관 — 지도를 숨겨도, 손잡이 밖에서
  굴려도 같았다).
- **규칙 — 스크롤 칸은 단계마다 하나다.** 조건·결과 뷰는 패널 `Content`, 선택 뷰는 피커 `Body`(「← 30개」 머리 고정)가
  스크롤한다. 시트 본문은 스크롤하지 않는다 — 높이만 정하고(`overflow: hidden`, 여백 없음) 패널이 그 높이를 다 채운다
  (분석 시트의 `Layer > section { height: 100% }` 와 같은 구조). 바깥 `Content` 의 `overscroll-behavior: contain` 은
  **의도된 체이닝 차단**이다 — 피커 목록 끝에서 더 굴려도 지도·페이지로 새지 않는다. 그래서 그 바깥에 실제로 넘치는 스크롤
  칸을 두지 않는다.
- **여백**: 시트 본문 16px + 패널 22px 로 두 번 들어가던 좌우 여백을 패널 하나로 모으고 DESIGN.md 모바일 거터 **16px** 로
  맞췄다(데스크톱 패널은 22px 그대로). 시트 위 여백은 **8px** 이다 — 손잡이 줄(72px)이 이미 여백을 품고 있어 16px 이면 손잡이 줄과 첫 줄(「← 30개」·결과 제목) 사이가 벌어져 보였다. 시트 아래 여백은 홈 인디케이터(safe area)를 더한다. 값은 `Surface` 의
  `--recommend-panel-top`·`--recommend-panel-gutter`·`--recommend-panel-bottom` 이고 비교 바가 같은 변수로 여백을 덮는다.
- **비교 바**: `Content` 가 스크롤하므로 시트 바닥에 고정된다(S3-6). 바 안쪽 아래 여백은 `8px + safe area` 만 둔다
  (`--recommend-compare-bar-bottom`) — 아래 거터 16px 까지 더하면 바가 77px 이 되어 375×667 시트(본문 342px)의 4분의 1 가까이를
  먹었다. 지금은 61px(위아래 8px + 버튼 44px + 테두리 1px)이다. 끝까지 내리면 마지막 카드 아래끝이 바 위로 드러난다.
- **선택 뷰 제목 중복**: 손잡이 줄이 이미 「업종 선택 / 중랑구 · 중화1동」을 말하므로 시트에서는 안쪽 「업종 선택」 제목을
  화면에서 감춘다(헤딩·포커스 자리로는 남는다). 뒤로 가기와 개수(「30개」)는 보인다. 손잡이 줄은 접혔을 때 유일한 단서라
  그쪽을 남겼다(ux-followups C-1).
- 실측(Playwright chromium, 휠과 CDP 터치 드래그 모두 같은 결과, 좌우 여백은 화면 가장자리부터 목록까지 — 시트 테두리 1px 포함):

  | 뷰포트      | 단계               | 전: 끝까지 스크롤 / 마지막 항목 누름 | 후   | 여백 전 → 후 |
  | ----------- | ------------------ | ------------------------------------ | ---- | ------------ |
  | 375×667     | 자치구·행정동·업종 | 불가                                 | 가능 | 39 → 17px    |
  | 390×844     | 자치구·업종        | 불가(행정동 16개는 넘치지 않음)      | 가능 | 39 → 17px    |
  | 440×956     | 업종               | 불가                                 | 가능 | 39 → 17px    |
  | 375·390·440 | 추천 결과          | 불가                                 | 가능 | 39 → 17px    |

  첫 화면에 보이는 업종 항목 수는 그대로다(375×667 6개 · 390×844 10개 · 440×956 12개). 업종 목록은 이제 「← 30개」 줄을
  위에 남긴 채 그 아래만 스크롤한다. 회귀 테스트는 `e2e/recommend/sheet-scroll.spec.ts`(업종 목록 끝 도달·누름, 거터 16px·제목 중복, 결과 목록 끝 도달·비교 바 위치. BFF 는 `e2e/fixtures/recommend.ts`, CI 에서 돈다).
