## A. 업종 선택 UX

### A-0. 배경

| 항목              | 내용                                                                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 해결하려는 문제   | 업종 31개가 6그룹 세로 목록으로만 있어 원하는 업종을 **찾기 어렵다**. 항목 버튼의 모양도 선택지가 아니라 이동 링크처럼 읽힌다(A-1-1). 리뷰의 「버튼 UI」 지적은 조건 바 테두리였고 그쪽은 `8fa971df` 에서 처리됐다 |
| 기존 동작 (as-is) | `OptionPicker` `layout='list'` — 한 줄에 하나씩, 우측에 `ChevronRight`. 검색은 있다                                                                                                                                |
| 목표 동작 (to-be) | 자주 고르는 업종에 **먼저 닿고**, 항목이 「선택지」로 읽히게 한다                                                                                                                                                  |
| 구현 제외 범위    | 지역(자치구·행정동) 선택 — 칩 격자로 충분하다                                                                                                                                                                      |

### A-1. 지금 무엇이 잘못됐나

**1. `ChevronRight` 가 거짓말을 한다.** 목록 항목의 우측 꺾쇠는 「누르면 다음 화면으로 간다」는
관용 표현인데, 실제로는 그 자리에서 **선택되고 조건 바로 되돌아온다.** 선택지에는 라디오·체크
같은 선택 어포던스가 맞다. 선택된 항목만 `Check` 로 바뀌는 현재 방식은 **선택 전에는 아무 단서가
없다**는 뜻이기도 하다.

**2. 31개를 균등하게 늘어놓는다.** 「커피-음료」·「한식음식점」처럼 압도적으로 많이 고르는
업종과 「자전거 및 기타운송장비」가 같은 무게로 같은 거리에 있다. 스크롤 위치는 카탈로그 순서가
정하지 사용 빈도가 정하지 않는다.

**3. 세로 한 줄 배치가 화면을 길게 쓴다.** 지역 단계는 3열 칩 격자인데 업종만 1열이라, 같은
선택 뷰인데 밀도가 갑자기 달라진다.

### A-2. 방향 — 「인기 먼저, 그다음 전체」

```
┌─────────────────────────────┐
│  [ 업종 검색            ]   │
├─────────────────────────────┤
│  자주 찾는 업종              │
│  ☕커피-음료  🍚한식  🍗치킨 │   ← 6~8개, 큰 타깃
│  🍺호프-간이  💇미용  🏪편의 │
├─────────────────────────────┤
│  음식점                      │
│  중식음식점   일식음식점 …   │   ← 전체, 2열 격자
│  학원                        │
│  …                           │
└─────────────────────────────┘
```

- **인기 섹션**을 맨 위에 둔다. 검색을 치기 전에 이미 대부분이 여기서 끝난다.
- 전체 목록은 **2열 격자**로 바꿔 지역 단계와 밀도를 맞춘다. 이름이 긴 업종이 있으므로
  칩(1열 중앙정렬)이 아니라 좌측정렬 2열이다.
- 검색은 그대로 두되, 검색 중에는 인기 섹션을 숨긴다(중복 노출 방지).

### A-3. 착수 전 정해야 할 것

| #     | 결정                            | 선택지                                                                                                                                                                                                                        |
| ----- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-3-1 | **인기 업종을 무엇으로 정하나** | (a) FE 상수로 6~8개 하드코딩 (b) 백엔드에 「업종별 조회수/추천수」 요청 (c) 사용자 최근 선택 `localStorage`                                                                                                                   |
| A-3-2 | **아이콘을 넣을 것인가**        | 31개 전부에 의미가 통하는 아이콘을 붙이기는 어렵다. `lucide-react` 로 「커피·한식·치킨·미용·편의점」 같은 대표 업종은 되지만 「기타법무서비스」는 안 된다. **인기 섹션에만** 붙이고 전체 목록은 텍스트로 두는 절충이 유력하다 |
| A-3-3 | **선택 어포던스**               | (a) 좌측 라디오 (b) 선택 시에만 우측 `Check`(현행) + `ChevronRight` 제거 (c) 칩처럼 배경색으로만                                                                                                                              |

**권장**: A-3-1 은 **(a) 하드코딩으로 시작**한다. 백엔드 없이 오늘 되고, 나중에 (b)로 갈아끼울
때 상수만 바꾸면 된다. 다만 **무엇을 인기로 볼지는 사람이 정해야 한다** — 임의로 고르면 근거가
없다. A-3-2 는 **인기 섹션만**. A-3-3 은 **(b)** — `ChevronRight` 만 걷어내면 거짓말이 사라지고
변경 폭이 가장 작다.

### A-4. 주의사항

- `OptionPicker` 는 분석 패널도 쓴다. **2열 격자·인기 섹션을 기본값으로 만들면 분석이 함께
  바뀐다.** 새 `layout` 값(예: `'grid-wide'`)과 옵션 prop 으로 열고, 분석은 현행 그대로 둔다.
- 분석의 업종 단계는 **백엔드가 주는 `serviceType.name`** 으로 그룹핑하고 추천은 **정적
  카탈로그**를 쓴다. 인기 섹션을 공유 부품에 넣는다면 두 출처 모두에서 코드 매칭이 되는지
  확인해야 한다.

## B. 결과 지도 — 카메라와 상권 폴리곤

> **상태: 구현 완료** (2026-08-28). 아래 B-1~B-3 은 결정과 근거를 남긴 기록이다.
> 실제로 무엇을 만들었는지는 [B-4](#b-4-무엇을-만들었나)를 본다.

### B-0. 배경

| 항목              | 내용                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 해결하려는 문제   | 「상권 추천받기」를 누르면 **행정동으로 카메라가 이동**한다. 추천 결과가 없어도 이동하고, 결과가 있어도 개별 상권은 지도에 나타나지 않는다 |
| 기존 동작 (as-is) | `fitPoints` 가 선택 행정동 경계로 잡혀 카메라가 그리로 맞춰진다. 결과 상권 폴리곤은 **한 개도 그려지지 않는다**                            |
| 목표 동작 (to-be) | 결과가 없으면 카메라를 그대로 둔다. 결과 목록에서 항목을 고르면 **그 상권**이 폴리곤으로 표시된다                                          |
| 선행 조건         | **B-1 경계 조인** — 이게 안 되면 나머지가 무의미하다                                                                                       |

### B-1. 선행 — 상권 경계 조인 (condition-selector D8 과 동일 건)

Kakao SDK `Polygon` 생성자를 계측해 확인했다. 결과 단계에서 생기는 폴리곤은 컨텍스트 영역
**1개뿐**, 결과 폴리곤은 **0개**다.

백엔드 `GET /map/commercials/{code}/profile` 이 `centerLng: null, centerLat: null,
boundaryCoords: []` 를 내려준다(강남구 역삼2동 / CS100010 / 20233 재현). `buildRecommendationMapItems`
(`recommend-map-model.ts:100`)는 center 만 후보 목록에서 폴백하고 경계는 폴백하지 않아 빈
배열이 되고, `drawPolygon` 이 `points.length < 3` 으로 null 을 반환한다.

후보 목록 타입 `CommercialArea`(`types/recommend.ts:27`)에도 경계가 없다 — 경계는 뷰포트 질의
`GET /map/commercials?lngSW=…`(= `commercialAreas` prop)에만 있다.

**착수 전 정해야 할 것**: 뷰포트 밖 상권은 `commercialAreas` 에 없으므로 지도를 패닝하면
폴리곤이 생겼다 사라진다.

| 선택지                              | 내용                                                                | 비고                  |
| ----------------------------------- | ------------------------------------------------------------------- | --------------------- |
| (a) 뷰포트 목록에서 조인            | `buildRecommendationMapItems` 에 `commercialAreas` 를 추가로 넘긴다 | 싸다. 패닝 시 깜빡임  |
| (b) 결과 코드 경계를 따로 질의·캐시 | Top N 코드로 한 번 더 조회해 들고 있는다                            | 안정적. 요청 1회 추가 |
| (c) 백엔드 수정 요청                | profile 응답에 경계를 채워 달라고 한다                              | 근본. BE 선행         |

**권장**: **(b)**. 결과는 최대 5건이라 한 번 받아 두면 끝이고, 패닝 중 폴리곤이 사라지는 것은
사용자가 「버그」로 읽는 종류의 흔들림이다. (c)는 병행 요청하되 기다리지 않는다.

**결정: (b)로 갔다.** 다만 「코드로 경계 조회」 엔드포인트는 **존재하지 않는다** — 실측으로
확인했다. `GET /map/commercials/{code}/profile` 은 `centerLng: null` / `boundaryCoords: []` 를
주고(종로구 3110016 재현), 경계를 주는 것은 뷰포트 질의 `GET /map/commercials?lngSW=…` 뿐이다.
그 질의는 **중심점이 bbox 안에 있는 상권**을 돌려준다(중심점 ±0.001 bbox 로 1건만 나오는 것을
확인했다).

그래서 (b)를 **「결과 상권 중심점들을 감싸는 고정 bbox 로 뷰포트 질의를 한 번 더」** 로
구현했다. 결과가 1건이면 bbox 가 한 점으로 찌그러지므로 `RESULT_BOUNDARY_PAD_DEGREES`(0.004,
약 400m)만큼 넓힌다. **지도 뷰포트와 무관한 고정 bbox** 라서 패닝해도 폴리곤이 그대로 있다.

### B-2. 결과가 없으면 카메라를 옮기지 않는다

「추천받기」 결과가 0건인데 행정동으로 확대되면, 사용자는 **아무것도 없는 화면으로 끌려간다.**
제출 시점이 아니라 **결과를 받은 뒤** 카메라를 정한다.

| 상황         | 카메라                         |
| ------------ | ------------------------------ |
| 결과 ≥ 1건   | 결과 상권들을 모두 담는 bounds |
| 결과 0건     | **직전 카메라 유지**           |
| 결과 로딩 중 | 유지                           |

**「유지」와 「기본 카메라로 되돌림」은 다른 것이다.** 기존 코드는 「맞출 대상 없음」을 `null`
하나로 표현했고, `setMapBounds` 는 `null` 을 받으면 **서울 기본 카메라로 되돌렸다.** 그래서
`fitPoints` 를 `null` 로 두는 것만으로는 「직전 카메라 유지」가 되지 않는다. 카메라 결정을
`MapCameraTarget = { kind: 'fit' } | { kind: 'keep' } | { kind: 'reset' }` 로 나눠 세 상황을
구분했다.

**결과 1위 자동 선택과 부딪힌다.** 결과가 도착하면 `resultsLoaded` 가 1위를 자동으로 고른다
(목록·상세가 빈 채로 뜨지 않게). 그 선택을 그대로 카메라에 쓰면 **나머지 4건이 화면 밖으로
밀린다.** 그래서 상태에 `resultSelectionSource: 'auto' | 'user' | null` 을 두고, 자동 선택은
결과 전체에 맞추고 **사용자가 직접 고른 경우에만** 그 상권으로 좁힌다.

### B-3. 결과 항목을 고르면 그 상권을 표시한다

목록·마커에서 상권을 고르면 그 상권 폴리곤이 `selected` 상태(2.5px, 점수 농도 +0.20)가 되고
카메라가 그 상권으로 맞춰진다. 스타일 계약은 이미 있다(`getResultPolygonStyle`) — B-1 로 경계만
생기면 동작한다.

행정동 컨텍스트는 `8705ad5f` 에서 채움 없는 중립 외곽선으로 낮췄다. 그대로 둔다.

### B-4. 무엇을 만들었나

| 무엇                                                     | 어디                                                        |
| -------------------------------------------------------- | ----------------------------------------------------------- |
| 경계 폴백(profile 이 3점 미만이면 뷰포트 질의 경계 사용) | `buildRecommendationMapItems` 4번째 인자 `boundaries`       |
| 결과 경계 질의용 bbox                                    | `buildResultBoundaryBounds` + `RESULT_BOUNDARY_PAD_DEGREES` |
| 카메라 결정                                              | `resolveRecommendCameraTarget` / `MapCameraTarget`          |
| 떠 있는 패널을 피하는 카메라 패딩                        | `resolveCameraPadding` + `data-map-overlay="true"`          |
| 자동 선택 ↔ 사용자 선택 구분                             | `RecommendationState.resultSelectionSource`                 |

#### 패널이 지도를 가리는 문제 (명세에 없던 것)

결과 bounds 를 **지도 전체 폭**에 맞추자, 추천 상권이 왼쪽에 떠 있는 조건·결과 패널
(`left: 24px` / `width: 390px`) 뒤로 들어갔다. 「결과를 지도에 보여 준다」가 말만 남는다.
`/analysis` 는 좌측 **고정** 패널이라 이 문제가 없지만 `/recommend` 는 패널이 지도 **위에**
떠 있다.

카카오 `setBounds` 는 px 패딩 인자를 받는다. 떠 있는 패널에 `data-map-overlay="true"` 를 달고
**실제 크기를 재서** 패딩을 만든다 — CSS 폭을 상수로 베껴 두면 레이아웃이 바뀔 때 조용히
어긋난다. 세로로 긴 것은 옆 패널, 가로로 긴 것은 위아래 바로 보고 가까운 가장자리에 붙인다
(데스크탑 패널 → `left: 438`, 모바일 시트 → `bottom`). 한 축의 45% 를 넘지 않게 자른다 —
패딩이 지도 절반을 넘으면 맞출 공간 자체가 사라진다.

#### 사람 검증으로 확인한 것 (2026-08-28, dev 5173)

Kakao SDK 계측(`Polygon` 생성자 + `Map.prototype.setBounds` 래핑)으로 실측했다.

| 확인              | 결과                                                                        |
| ----------------- | --------------------------------------------------------------------------- |
| 결과 폴리곤 (B-1) | 강남구/역삼1동/한식음식점 → 컨텍스트 1개 + **결과 5개**(53·61·71·136·99 점) |
| 결과 카메라 (B-2) | `setBounds` **1회**, 패딩 `[24, 24, 24, 438]`, level 5                      |
| 결과 0건 (B-2)    | 강남구/세곡동/**여관** → `setBounds` **0회**, level·center 변화 없음        |
| 결과 선택 (B-3)   | 1위 클릭 → level 4, 해당 폴리곤 `selected` 스타일                           |

경계 질의가 끝날 때까지 카메라를 잡아 두므로(`isResultsLoading`) **중심점으로 한 번,
경계로 또 한 번** 움직이지 않는다 — 위의 「`setBounds` 1회」가 그 증거다.

4. 추천의 **최소 지도 높이 보장**은 살릴지 판단한다 — 분석에는 없는 로직이고, 지도가 주인공인

### D-1. ⚠️ 점수를 그대로 색에 매핑하면 정반대로 읽힌다

**이 항목에서 가장 중요한 제약이다.** API 의 `scoreDescription` 이 지표마다 방향을 다르게 말한다.

| 지표                                 | `scoreDescription`                          | 점수가 높으면 |
| ------------------------------------ | ------------------------------------------- | ------------- |
| 기회도 `OPPORTUNITY_SCORE`           | "점수가 높을수록 진입 기회가 높습니다"      | **좋다**      |
| 위험도 `RISK_SCORE`                  | "점수가 높을수록 위험 요인이 큽니다"        | **나쁘다**    |
| 혼잡도 `CONGESTION_SCORE`            | "점수가 높을수록 혼잡과 경쟁 체감이 큽니다" | **나쁘다**    |
| 거주수요 `RESIDENT_POPULATION_SCORE` | "점수가 높을수록 소비 수요가 높습니다"      | **좋다**      |

점수를 그대로 초록↔빨강에 매핑하면 **위험도 100(=매우 위험)이 초록으로 칠해진다.** 반대로
「위험도 낮음 0」은 빨강이 되어, 좋은 것을 나쁘게 표시한다.

**색은 점수가 아니라 「좋음/보통/나쁨」에 매핑한다.** 그 변환은 지표별 방향을 아는 함수가
맡는다:

```ts
type MetricPolarity = 'higher-is-better' | 'lower-is-better'

const METRIC_POLARITY: Record<string, MetricPolarity> = {
  OPPORTUNITY_SCORE: 'higher-is-better',
  RESIDENT_POPULATION_SCORE: 'higher-is-better',
  RISK_SCORE: 'lower-is-better',
  CONGESTION_SCORE: 'lower-is-better',
}
```

**도넛이 채우는 양(호의 길이)은 점수 그대로**여야 한다 — 「위험도 100」의 호는 가득 차되
색은 빨강이다. 호까지 뒤집으면 숫자(100)와 그림이 어긋난다.

모르는 `metricType.code` 가 오면 **중립색**으로 두고 색으로 판단하지 않는다. 백엔드가 지표를
추가했을 때 조용히 거짓말하지 않기 위해서다.

### D-2. 점수 색 토큰이 실재하지 않는다

`DESIGN.md` §Score Scale 에 `--score-high` / `--score-mid` / `--score-low` 가 적혀 있지만
**CSS 에는 정의돼 있지 않다.** `--color-primary-500` 과 같은 함정이다(이 PR 에서 실제로
당했다 — 정의되지 않은 토큰이 폴백으로 조용히 다른 색을 칠하고 있었다).

**착수 첫 단계는 `global-styles.ts` 에 이 토큰을 정의하는 것이다.** 값은 DESIGN.md 가 제안한
green500 / orange500 / red500 계열을 쓰되, 실제 팔레트에 있는 값이어야 한다
(`--color-green-500: #03b26c`, `--color-orange-500: #fe9800`, `--color-red-500: #f04452`).

**농담(진하기)을 점수에 따라 다르게** 하려는 요구는 토큰 3개로는 안 된다. 방법은 두 가지다.

| 방법            | 내용                                                          | 비고                                                |
| --------------- | ------------------------------------------------------------- | --------------------------------------------------- |
| (a) `color-mix` | `color-mix(in srgb, var(--score-high) ${강도}%, transparent)` | 저장소가 이미 `color-mix` 를 쓴다(`text-field.tsx`) |
| (b) 단계별 토큰 | `--score-high-strong` / `-soft` 처럼 2~3단                    | 예측 가능하지만 토큰이 늘어난다                     |

**권장은 (a)** — 호(arc)의 색은 등급색 원본을 쓰고, **트랙(빈 부분)만** 같은 색을 옅게 깐다.
색 자체의 농담으로 점수를 표현하면 **대비가 무너진다**(점수가 낮을수록 흐려져 안 보인다).
농담이 아니라 **호의 길이**가 점수를 말하게 두는 것이 안전하다.

### D-3. 도넛 게이지

**기존 `DonutChart`(`analysis/charts/donut-chart.tsx`)를 재사용하지 않는다.** 그것은 recharts
기반에 툴팁·범례를 갖춘 **구성비** 차트로, `GenderSegment[]` 를 받는다. 여기서 필요한 것은
**값 하나짜리 게이지**라 성격이 다르다.

- 새 부품: `src/components/ui/score-gauge.tsx` — 의존성 없는 **인라인 SVG**(`circle` +
  `stroke-dasharray`). 저장소에 SVG 차트 선례가 있다(`horizontal-bar-chart.tsx`).
- props: `score: number | null`, `polarity`, `size`(총점 `lg` / 상세 `sm`), `label`
- **가운데 숫자는 필수다.** DESIGN.md §Score Scale 이 「색상만 의존하지 말고 명도 차 + 숫자
  라벨도 함께 표시한다(컬러 블라인드 대응)」를 요구한다. 사용자가 제안한 「도넛 안에 점수」가
  바로 이 요건을 만족시킨다.
- `score === null`(산정 실패)이면 게이지를 그리지 않고 기존 「점수 없음」 표기를 유지한다.
  현재 `hasScore()` 와 `data-score-unavailable` 규약이 이미 있다.
- `aria-label` 에 「기회도 100점, 높음」처럼 지표·점수·등급을 함께 넣는다. 게이지는 그림이라
  스크린리더에 아무것도 남지 않는다.

### D-4. 비어 있는 업종 — 그래프와 아이콘

데이터는 `blueOceanCategories[]` = `{ serviceCode, serviceName, commercialStoreCount,
administrationStoreCount, storeRate }` 다.

**⚠️ 여기서도 방향이 뒤집힌다. `storeRate` 는 낮을수록 좋다**(「비율이 낮을수록 아직 자리가
비어 있다는 뜻이에요」). 막대 길이를 `storeRate` 로 그리면 **짧을수록 좋은 막대**가 되어,
바로 위 점수 게이지(길수록 좋음)와 같은 화면에서 의미가 충돌한다.

**해결: 「빈 자리」를 채운다.** `100 - storeRate` 를 막대로 그리면 **길수록 기회**가 되어
게이지와 방향이 맞는다. 숫자 라벨은 원본 비율(`11.11%`)과 `상권 0곳 / 행정동 8곳` 을 함께
남긴다 — 그림은 방향을, 숫자는 사실을 말한다.

`horizontal-bar-chart.tsx` 재사용 가능성을 먼저 확인한다. 항목이 5개뿐이고 축·툴팁이 필요
없다면 게이지처럼 얇은 인라인 막대가 더 가볍다.

### D-5. 업종 아이콘 — 범위가 함정이다

**`simulationCatalog` 31개로는 못 덮는다.** 추천 응답의 `blueOceanCategories` 에서 실제로
관측된 코드다:

```
CS200010 변호사사무소   CS200013 기타법무서비스   CS200012 법무사사무소
CS200034 여관          CS300035 인테리어        CS200030 피부관리실
CS100001 한식음식점     CS100008 분식전문점       CS300018 의약품
```

이 중 **카탈로그에 있는 것은 한식음식점·분식전문점·의약품·여관 정도**다. 나머지는 카탈로그
밖이고, 백엔드 서비스 코드 전체가 몇 개인지 FE 는 모른다.

**착수 전 정해야 할 것**

| #     | 결정             | 선택지                                                                                                                                                       |
| ----- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-5-1 | 아이콘 매핑 범위 | (a) 대분류(`CS1`=음식점 / `CS2`=서비스 / `CS3`=도소매) **접두사 3종**만 매핑 (b) 자주 나오는 20~30개 매핑 + 나머지는 대분류 폴백 (c) 백엔드에 아이콘 키 요청 |

**권장은 (b)** — **폴백을 먼저 만든다.** `serviceCode` 앞 3자리로 대분류 아이콘을 정해 두면
어떤 코드가 와도 빈칸이 없고, 그 위에 개별 매핑을 얹어 나간다. 매핑 없는 업종이 아이콘 없이

아이콘은 **장식이다.** 이름 옆의 보조 신호일 뿐 아이콘만으로 업종을 식별하게 하지 않는다
(`aria-hidden`).

### D-6. 착수 순서

1. `--score-high/mid/low` 토큰 정의 (D-2) — 없으면 아무것도 못 칠한다
2. `METRIC_POLARITY` + 「좋음/보통/나쁨」 변환 함수 (D-1) — **순수 함수, 테스트 먼저**
3. `ScoreGauge` 부품 (D-3)

5. 업종 아이콘 폴백 → 개별 매핑 (D-5)
6. 비어 있는 업종 막대 (D-4)

`--score-neutral`(grey400)을 하나 더 뒀다. 명세의 토큰 3개로는 **방향을 모르는 지표**를
표현할 수 없는데, 그때 아무 등급색이나 칠하면 백엔드가 지표를 추가한 순간 화면이 조용히
거짓말한다. 등급 문구도 `neutral` 은 **빈 문자열**이다 — 판단하지 않은 것을 「보통」이라고
말하면 그것도 거짓이다.

D-2 의 「색 농담으로 점수 표현」은 **하지 않았다.** 호의 길이가 이미 점수를 말하므로
농담까지 연동하면 정보가 중복되고 대비만 나빠진다(명세 D-2 의 판단 그대로다). 트랙(빈 부분)만
등급색을 `color-mix` 로 16% 깔았다.

### 사람 검증으로 확인한 것 (2026-08-28, dev 5173)

토큰이 실재하는지부터 확인했다 — 정의 전에는 네 토큰 모두 빈 문자열이었고, 지금은
`#03b26c` / `#fe9800` / `#f04452` / `#b0b8c1` 로 읽힌다.

강남구/역삼1동/한식음식점 1위 카드에서 실제 그려진 값:

| 지표     | 점수 | 호 길이  | 색                        |
| -------- | ---- | -------- | ------------------------- |
| 기회도   | 100  | 가득     | 초록 `rgb(3,178,108)`     |
| 위험도   | 100  | **가득** | **빨강 `rgb(240,68,82)`** |
| 혼잡도   | 100  | 가득     | 빨강                      |
| 거주수요 | 39   | 38.6%    | 빨강 (40 미만)            |

**위험도 100 의 호는 가득 차 있고 색만 빨갛다** — D-1 이 요구한 그대로다. 가운데 숫자와
그림이 어긋나지 않는다.

### ⚠️ 남은 문제 — 빈 자리 막대가 서로 구별되지 않는다

실측: 92.86% / 88.89% / 87.5% / 87.27% / 86.15% → 271px 막대에서 **폭 차이가 18px** 이다.

구조적인 문제다. 「비어 있는 업종」은 **정의상 `storeRate` 가 가장 낮은 5개**라 `100 - storeRate`
는 늘 85~100% 에 몰린다. 방향은 맞지만(길수록 기회) 다섯 개를 **비교하는 데는 거의 쓸모가 없다.**

차이가 드러나는 곳은 오른쪽 끝의 회색 꼬리(이미 찬 자리, 19px vs 38px)다. 지금은 그것이
`--color-surface-muted` 라 눈에 잘 안 띈다. 판단이 필요해서 그대로 뒀다:

- (a) 그대로 둔다 — 막대는 「거의 다 비었다」를 한눈에 말하고, 순위는 목록 순서와 숫자가 말한다
- (b) 찬 자리(꼬리)를 또렷한 색으로 칠한다 — 절대 눈금을 지키면서 변하는 쪽을 보이게 한다
- (c) 카드 안 상대 눈금으로 바꾼다 — **막대 길이가 절대량을 뜻하지 않게 되므로 권하지 않는다**
