# home — 4단계 스토리 · 듀얼 랭킹 · AI 리포트 승격 세부 명세서

> **작성일**: 2026-09-03
> **공통 명세**: [home 공통 명세](./home.md)
> **선행 명세**: [below-hero-scrollytelling](./below-hero-scrollytelling.md) — 이 문서는 그 명세의 ②·③부를 **개정**한다(대체하지 않는다. 3부 구조와 앵커·스티키 트랙은 그대로 유지).
> **대상**: 웹 (Next.js App Router)
> **작성자**: Claude Code
> **상태**: 구현 완료

히어로 하위 3부(앵커 → 스토리 → 벤토)와 그 사이의 「지금 많이 본 지역」 섹션이
**보여주기로 한 것을 실제로 보여주지 못하고 있다.** 네 가지를 고친다.

1. 스토리 CTA 가 선언(48px)의 2.5배(120px)로 렌더된다 — 그리드 행 stretch 버그.
2. 스토리 01단계가 히어로와 **같은 지도 컴포넌트를 재렌더**한다.
3. 랭킹 섹션이 422px 로 꺼지고, 순위인데 1위와 8위가 시각적으로 동등하다.
4. AI 리포트가 **분석의 산출물인데 「분석 이후의 기능」 칸**에 놓여 정보구조가 한 칸 밀렸다.

## D3. 아키텍처 / 시스템 설계

### D3-1. 시스템 구성

```
home-page.tsx
├ HeroSection                (변경 없음)
├ AnchorStatement            (변경 없음)
├ ProductStory               ← 개정
│   ├ story-steps.ts         ← 문구·CTA·데모 종류
│   ├ MetricRankingBoard     ← 신규 (01) ─┐
│   ├ AnalysisMiniDemo       ← 개정 (02)  │  useDistrictTopTen()
│   ├ RecommendPreview       ← 신규 (03)  │  공유 쿼리
│   └ CostWaterfall          ← 신규 (04)  │
├ PopularDistricts           ← 개정 ──────┘
└ FeatureBento               ← 개정
```

**핵심 설계 결정: 새 포맷팅 계층을 만들지 않는다.**
`/status` 가 이미 `top-ten` 응답 전용 뷰모델(`normalizeStatusTopTen`)과 포맷터
(`formatStatusValue`, `formatStatusChange`)를 갖고 있다. 홈은 그것을 **그대로 import** 한다.
홈에서 「1,842만 명」을 다시 포맷하는 코드를 쓰면 같은 숫자가 두 화면에서 다르게 보이는
날이 반드시 온다.

### D3-2. 데이터 흐름

| 쿼리 키                                    | 엔드포인트                                                                               | 쓰는 곳              | staleTime | 실패 시            |
| ------------------------------------------ | ---------------------------------------------------------------------------------------- | -------------------- | --------- | ------------------ |
| `['home','analysisRankings','DISTRICT',8]` | `GET /analysis-rankings`                                                                 | 랭킹 좌              | 5분       | 좌측만 제거        |
| `['home','districtTopTen']`                | `GET /districts/top-ten`                                                                 | 랭킹 우 **+ 01단계** | 5분       | 우측·01단계만 폴백 |
| `['home','recommendAdministrations',...]`  | `GET /regions/districts/{districtCode}/administrations`                                  | 03단계 + 카운터      | 30분      | 03 예시 폴백       |
| `['home','recommendCommercials',...]`      | `GET /regions/districts/{districtCode}/administrations/{administrationCode}/commercials` | 03단계 + 카운터      | 30분      | 03 예시 폴백       |
| `['home','recommendPreview',...]`          | `GET /commercials/recommendations/by-service`                                            | 03단계 + 카운터      | 30분      | 03 예시 폴백       |

홈의 백엔드 호출은 **1개 → 5개**가 된다. 다섯 다 GET·공개·비인증이다.
`/status`·`/analysis`·`/recommend`·`/simulation` 이 모두 비보호 경로임을 `middleware.ts`
의 `PROTECTED_PATHS` 로 확인했다(보호 경로는 `/community/register`·`/chatting`·`/profile` 뿐).

**다섯 개가 한 번에 나가지 않는다.** 앞의 둘(`analysisRankings`·`districtTopTen`)만 첫
페인트에 나가고, 03단계의 세 쿼리(연쇄)는 스토리 섹션이 뷰포트에 들어온 뒤에만 켜진다
(D5-7).

03단계 세 쿼리는 **연쇄**다(`administrations` 의 첫 행정동 코드가 `commercials` 의
인자, 그 응답의 상권 코드 배열이 `recommendations` 의 인자). 각 단계를 `enabled` 로
묶고 `staleTime` 을 30분으로 길게 잡는다. 예전엔 고정 시드라 이 길이가 자연스러웠는데,
이제는 선택이 바뀌면 쿼리 키 자체가 달라지므로(D5-6) 같은 선택으로 돌아왔을 때만
캐시가 재사용된다.

## D4. 상세 동작 정의

### D4-1. CTA 높이 복구

`product-story.tsx` 의 `PanelWithCta` 에 행 정의를 준다.

```
PanelWithCta {
  display: grid;
  grid-template-rows: minmax(0, 1fr) auto;   /* ← 추가 */
  gap: 16px;
}
```

**왜 이 값인가.** 부모 `StoryRow` 가 `height: 600px` + `align-items: stretch` 라
`PanelWithCta` 는 600px 로 늘어난다. 행이 `auto auto` 면 남는 216px 가 두 행에 분배되고
CTA 가 행 높이(120px)만큼 늘어난다. `minmax(0,1fr) auto` 는 남는 공간을 **패널이 전부**
가져가게 하고 CTA 는 자기 높이만 쓴다.

`align-self: start` 로도 높이는 잡히지만 그때는 패널이 늘어나지 않아 카드가 위로 붙는다.
`minmax(0, ...)` 의 0 은 필수다 — `1fr` 만 쓰면 최소 콘텐츠 크기가 하한이 되어 좁은 폭에서
패널이 넘친다.

> 이미 있는 `> a { justify-self: start }` 는 **지우지 않는다.** 그것은 가로축 담당이고,
> 없애면 주석에 기록된 「343px → 121px 찌그러짐」 사고가 되돌아온다.

### D4-3. 랭킹 섹션 — 듀얼 랭킹

```
┌─ Section (min-height: 100dvh) ──────────────────────────┐
│ eyebrow: 지금 많이 본 지역                                │
│ h2:      다른 사람들이 보는 곳과, 숫자가 좋은 곳은 다릅니다. │
│ ┌── 좌: 조회수 (최근 N시간) ──┬── 우: 실제 지표 TOP 5 ──┐ │
│ │ 1 강남구  ███████ 1,284회   │ [유동인구][매출][개업]   │ │
│ │ 2 마포구  ██████  1,102회   │ 1 강남구 ███ 1,842만 +3.2%│ │
│ │ … 8행                       │ … 5행                    │ │
│ └─────────────────────────────┴──────────────────────────┘ │
│ 인사이트 문장 (D5-1) — 없으면 렌더 안 함                   │
└──────────────────────────────────────────────────────────┘
```

- 좌측 8행 × 우측 5행 + 헤더 + 인사이트로 100dvh 가 **내용으로** 찬다. 여백으로 채우지 않는다.
- 막대 폭 = `value / max(values) × 100%`. 1위는 항상 100%다.
- `≤900px`: 2단 → 1단 세로 스택. `min-height: 100dvh` 를 해제한다(모바일에서 두 목록을
  한 화면에 넣으면 글자가 읽히지 않는다).
- 좌측 항목의 링크·`aria-label`·「N회」 표기는 **현행 그대로 유지**한다. 이미 접근성이 맞춰져 있다.

## D5. 비즈니스 로직

### D5-1. 인사이트 문장 생성 규칙

입력: `views`(조회수 순위, 최대 8) · `metric`(선택 지표 Top5). 둘 다 `districtCode` 기준.
**첫 번째로 걸리는 규칙만** 쓴다.

| 순위 | 조건                                                 | 문장                                                                     |
| ---- | ---------------------------------------------------- | ------------------------------------------------------------------------ |
| A    | 지표 Top3 중 조회수 목록(8곳)에 **없는** 첫 항목 `x` | `{지표라벨} {x.rank}위 {x.name}는 지금 많이 본 {N}곳에 들지 않았습니다.` |
| B    | 조회수 Top3 중 지표 Top5 에 **없는** 첫 항목 `y`     | `조회수 {y.rank}위 {y.name}는 {지표라벨} Top 5 밖입니다.`                |
| —    | 둘 다 해당 없음                                      | **문장을 렌더하지 않는다** (`null`)                                      |

A 가 B 보다 앞선다. 「아무도 안 보는데 지표가 상위인 곳」이 창업 후보를 찾는 사람에게
더 값진 정보이기 때문이다.

**문장은 집합 소속만 진술한다.** 「좋다/나쁘다/유망하다」로 해석하지 않는다 — 지표 상위가
곧 좋은 상권이라는 근거가 우리에게 없다. `highlightCode` 로 양쪽 목록의 해당 행을 함께
강조해 문장과 목록이 같은 것을 가리키게 한다.

### D5-2. 변화율 배지를 어디에 붙이는가

| 목록                          | 변화율   | 이유                                                                 |
| ----------------------------- | -------- | -------------------------------------------------------------------- |
| 조회수 (`/analysis-rankings`) | **없음** | 집계에 전기가 없다. 0 으로 채우면 「변동 없음」이라는 틀린 말이 된다 |
| 지표 (`/districts/top-ten`)   | **있음** | 응답이 `changeRate` 를 준다. `formatStatusChange` 로 그대로 쓴다     |

기존 `popular-districts.tsx` 주석이 남긴 판단을 그대로 승계한다. 이번에 변화율이 생긴 것은
**다른 API 를 붙였기 때문**이지, 기존 판단이 틀렸기 때문이 아니다.

### D5-3. 폐업 지표를 홈에서 빼는 이유

`top-ten` 은 4지표를 주지만 홈은 3개만 노출한다.

폐업 Top10 은 **상위가 나쁜 것**이다. 다른 세 지표와 방향이 반대라, 같은 토글에 섞으면
① 랜딩에서 「폐업 1위 자치구」를 순위표처럼 자랑하게 되고 ② D5-1 의 인사이트 문장이
정반대 의미가 된다(「아무도 안 보는데 폐업 1위」는 기회가 아니다).

`/status` 는 4지표를 전부 유지한다. 그 화면은 현황 조회가 목적이라 방향이 섞여도 된다.

### D5-4. 실패·빈 상태 분기

| 조회수 | 지표    | 랭킹 섹션 렌더                            |
| ------ | ------- | ----------------------------------------- |
| 성공   | 성공    | 2단 + 인사이트(규칙에 걸릴 때)            |
| 성공   | 실패    | 좌측 단독 1단. 인사이트 없음. 100dvh 해제 |
| 실패   | 성공    | 우측 단독 1단. 인사이트 없음. 100dvh 해제 |
| 실패   | 실패    | **섹션 전체 제거** (`return null`)        |
| 성공   | 빈 배열 | 실패와 동일 취급                          |

**인사이트 문장은 양쪽이 다 있을 때만 만들 수 있다** — 두 목록의 차이를 말하는 문장이므로.

| 03단계 시드/추천 | 렌더                                                   |
| ---------------- | ------------------------------------------------------ |
| 성공             | 실 응답 + `selectionReason`                            |
| 실패 / 빈 items  | 기존 하드코딩 5행 + `대표 예시 데이터` 라벨로 **폴백** |

03 은 섹션을 빼지 않는다. 스토리는 4단계가 다 있어야 「네 단계로 좁힙니다」가 성립한다.
로딩 중에는 스켈레톤을 쓰지 않고 **예시 데이터를 먼저 그린 뒤 실 응답이 오면 교체**한다 —
스토리 패널은 높이가 고정(600px)이라 교체가 레이아웃을 밀지 않는다.

01단계(지표 보드)는 `top-ten` 실패 시 **단계 전체를 예시 랭킹으로 폴백**한다.
스토리에서 한 단계만 사라지면 번호(01~04)에 구멍이 난다.

위 두 표는 **쿼리 단위**(요청 자체가 성공/실패했는가)의 분기만 다룬다. 최종 리뷰에서
드러난 두 가지는 **다른 축**이다 — ①은 쿼리가 200 을 줬을 때 그 안의 **지표 단위**
결손, ②는 두 쿼리의 **응답 시각 차이**다. 아래 D5-4-1·D5-4-2 로 분리해 적는다.

#### D5-4-1. 지표 단위 결손 — 「고른 지표만 빈 것」과 「지표 데이터 자체가 없는 것」

`top-ten` 은 하나의 요청이 3개 지표(유동인구·매출·개업) 배열을 한 응답에 담아 준다.
그래서 **요청은 성공(200)인데 그 중 한두 지표 배열만 빈 경우**가 있다 — 예를 들어
배포 직후 유동인구 집계만 아직 안 돌았고 매출·개업은 정상인 경우. 이 경우를 위 표의
「지표: 실패/빈 배열」과 같은 취급으로 두면 멀쩡한 두 지표까지 함께 사라진다.

그래서 **위치별로 다르게** 처리한다. 판단 기준은 「이 화면이 순위표인가, 서사인가」다.

| 위치                 | 판정 기준                                               | 처리                                                                                                                                                   | 근거                                                                                                                                         |
| -------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 랭킹 섹션 우측(D4-3) | 3지표 중 **하나 이상**에 데이터가 있다(`hasMetricData`) | 지표 토글 3개를 그대로 노출. **선택된** 지표가 빈 배열이면 그 자리에 `이 지표는 집계가 없습니다` 안내를 낸다(막대 대신)                                | 토글이 사라지면 멀쩡한 다른 지표로 넘어갈 방법이 없어진다. 랭킹은 **실제 순위를 보여주는 것**이 목적이라 없는 걸 지어내지 않고 없다고 말한다 |
| 랭킹 섹션 우측(D4-3) | 3지표가 **전부** 빈 배열(또는 요청 자체 실패)           | 우측 열 전체를 뺀다 — 위 표의 「지표: 실패」와 동일 취급                                                                                               | 사실상 API 가 죽은 것과 같다                                                                                                                 |
| 스토리 01단계(D4-2)  | **선택된** 지표가 빈 배열(요청 실패 포함)               | **단계 전체를 예시 폴백 세트로 전환**하고 `대표 예시 데이터` 라벨을 붙인다. 토글로 데이터가 있는 다른 지표를 고르면 그 지표는 다시 실데이터로 복귀한다 | 01단계는 「4단계가 다 있어야 네 단계로 좁힙니다가 성립」하는 **서사**다. 지표 자리를 빈 채로 둘 수 없다                                      |

같은 「지표 하나가 비었다」는 사실에 랭킹 섹션은 「없다고 말하고」, 스토리는 「예시로
메운다」로 반대로 반응한다. 목적이 다르기 때문이다.

#### D5-4-2. 두 쿼리의 응답 시각 차이 — pending 을 「없다」로 오판하지 않는다

위 표의 성공/실패는 **최종 상태**다. 그런데 조회수(`analysis-rankings`)와
지표(`top-ten`)는 서로 다른 네트워크 호출이라 **응답 시각이 다르고**, 한쪽만 먼저
도착하는 구간이 정상 로드마다 존재한다.

랭킹 섹션의 `min-height: 100dvh` 여부(`$dual`)는 **「지금 두 열이 렌더돼 있는가」가
아니라 「두 열이 최종적으로 있을 것인가」**로 정한다. 아직 `isPending` 인 쪽은
결론이 안 났으니 「있을 것」으로 가정한다. 결론이 난(성공이든 실패든) 뒤에만 실제
존재 여부로 판정한다.

```
viewWillExist   = rankingQuery.isPending || view !== null
metricWillExist = metricQuery.isPending  || hasMetricData
dual            = viewWillExist && metricWillExist
```

| 조회수(`analysis-rankings`) | 지표(`top-ten`)                | `dual` | `min-height`          |
| --------------------------- | ------------------------------ | ------ | --------------------- |
| pending                     | pending                        | —      | 100dvh(스켈레톤 고정) |
| 성공                        | **pending**                    | true   | 100dvh 유지           |
| **pending**                 | 성공(≥1개 지표에 데이터)       | true   | 100dvh 유지           |
| 성공                        | 결론 — 실패 또는 3지표 전부 빈 | false  | 해제                  |
| 결론 — 실패 또는 빈 배열    | 성공                           | false  | 해제                  |
| 결론(존재)                  | 결론(존재)                     | true   | 100dvh                |
| 결론(부재)                  | 결론(부재)                     | —      | 섹션 자체 제거(위 표) |

**왜 pending 을 「있을 것」으로 가정하는가.** 「지금 렌더된 열」 기준(`viewColumn &&
metricColumn`)으로 계산하면, 한쪽이 먼저 도착했을 때 아직 안 온 나머지 쪽을 「없다」로
오판해 100dvh → auto 로 수축했다가, 나머지 쪽이 도착하면 다시 100dvh 로 팽창한다.
이 깜빡임(스켈레톤 → 수축 → 재팽창)은 열화 경로가 아니라 **정상 로드마다** 발생해
아래 벤토 섹션이 밀렸다 당겨지고 스크롤 위치가 튄다. pending 을 「있을 것」으로 두면
전환은 스켈레톤(100dvh) → 최종 상태(100dvh 또는 해제) 한 번으로 끝난다.

### D5-5. 01단계와 랭킹이 같은 쿼리를 쓰는 법

둘 다 `useQuery({ queryKey: ['home','districtTopTen'], ... })` 를 호출한다.
React Query 가 같은 키를 dedupe 하므로 **네트워크 요청은 1회**다. 별도의 전역 상태나
props drilling 을 만들지 않는다.

`src/hooks/use-district-top-ten.ts` 로 훅을 하나 만들어 두 곳이 같은 키·`staleTime`·
`retry` 를 쓰게 고정한다. 키를 문자열로 두 번 적으면 언젠가 한쪽만 바뀐다.

### D5-6. 4단계 상태 승계와 카운터(S-1)

시안 S-1(「좁혀지는 후보 카운터」, D8-3)을 구현하며 두 가지를 함께 고쳤다 —
**02→03단계 상태 승계**(D8-4)와 **카운터 자체**다. 둘이 묶인 이유: 카운터의 03 노드
값(「상권 N 중 추천 M」)은 03단계가 02단계 선택을 실제로 이어받아야만 의미가 있다.
02와 03이 서로 다른 지역을 보고 있으면 카운터가 「좁혀지는 과정」이 아니라 두 개의
무관한 숫자가 된다.

**상태 소유.** 선택(`DemoSelection = { districtId, industryId }`)은 `ProductStory`
가 소유한다(`useState`, 스티키/스택 두 렌더 분기 **위**). 02단계(`AnalysisMiniDemo`),
03단계(`RecommendPreview`), 카운터(`FunnelCounter`)가 모두 이 값을 props 로 받는다.
분기 안에서 각자 `useState` 를 두면 스텝을 넘나들 때 서로 다른 값을 보게 된다
(`src/components/home/product-story.tsx`).

**데모 레코드의 실제 코드.** `src/data/home-demo.ts` 의 자치구·업종 레코드에 실제
코드를 직접 넣는다 — 이름 매칭은 자치구명이 개편되거나 표기가 흔들리면 조용히
깨지는 취약한 방식이라 쓰지 않는다.

| 자치구 | 코드    |     | 업종                | 코드       |
| ------ | ------- | --- | ------------------- | ---------- |
| 강남구 | `11680` |     | 카페                | `CS100010` |
| 마포구 | `11440` |     | 음식점              | `CS100001` |
| 종로구 | `11110` |     | 편의점              | `CS300002` |
| 성동구 | `11200` |     | 헬스장(스포츠 강습) | `CS200005` |

**이 값들은 dev 백엔드로 검증했다** — 마포구 서교동 기준 세 업종(카페·음식점·편의점) 전부
`success: true` 를 받았다.

**03 연쇄.** `fetchAdministrations(districtCode)` → 응답의 **첫 행정동** →
`fetchCommercials(districtCode, administrationCode)` → 그 상권 코드 배열로
`fetchCommercialRecommendations(...)`. 세 쿼리 키에 선택(자치구·업종 코드,
행정동 코드, 상권 코드 배열)이 전부 들어간다 — 예전엔 상권 코드 배열만 키였어서
지역이 바뀌는 순간 이전 지역의 캐시를 그대로 받는 결함이 있었다.

**강남구의 첫 행정동은 논현2동이다**(역삼1동이 아니다) — dev 응답 실측. 라벨은
이 응답에서 그대로 가져오고 하드코딩하지 않는다(`RecommendPreview`,
`src/hooks/use-recommend-preview.ts`).

**카운터 4노드 — 전부 화면에서 유도한다. 하드코딩 금지.**

| 노드               | 값                          | 출처                                                                                                  |
| ------------------ | --------------------------- | ----------------------------------------------------------------------------------------------------- |
| 01 현황 확인       | 자치구 수                   | `districts.length`(`src/data/districts.ts`)                                                           |
| 02 상권 분석       | 선택한 자치구·업종          | `selection`(`ProductStory` 가 소유)                                                                   |
| 03 후보 추천       | 상권 N 중 추천 M            | N=`commercials` 응답 길이(`commercialsCount`), M=`view.rows.length`                                   |
| 04 창업 시뮬레이션 | 1 · 선택과 무관한 고정 예시 | 승계 불가 — 04는 `POST /simulations/reports` 가 필요해 랜딩 방문자마다 쓰기 요청을 보낼 수 없다(D4-7) |

**`M` 을 5 로 하드코딩하면 안 되는 이유.** `topN=5` 는 백엔드가 돌려주는 상한이지
보장이 아니다. 실측에서 스포츠 강습(`CS200005`)은 `topN=5` 를 요청해도 추천이
**3건만** 왔다. `FunnelCounter` 는 `recommend.view.rows.length` 를 그대로 옮긴다
(`funnel-counter.tsx`).

**폴백 표기.** 03 이 폴백(`view.isSample === true`)이면 「상권 N 중」의 **N 을
생략**하고 「추천 M곳 · 예시」만 쓴다 — 폴백에는 실제 상권 개수가 없으니 지어내지
않는다(`step03Value`, `funnel-counter.tsx`).

**로딩 표기.** 아직 결론이 안 난 노드는 `—` 로 둔다. 03 노드는
`recommend.isLoading` 이 true 인 동안 `—` 다.

**모드별.** 스티키 모드는 활성 스텝 노드에 `aria-current="step"` 을 붙여 강조한다
(`active` prop, 0~3). 스택 모드(모바일/`prefers-reduced-motion`)는 "지금 보는 단계"
개념이 없으므로 `active` 를 넘기지 않고, 카운터를 스텝 목록 위에 강조 없이 **1회**만
그린다.

### D5-7. 03 연쇄를 언제 켜는가 — 스토리 도달 후 지연 발화

스토리 섹션은 y≈2880px 부근에 있어 **랜딩 첫 화면에 보이지 않는다.** 카운터
(`FunnelCounter`)는 01단계와 함께 스티키 모드에서 즉시 마운트되지만, "마운트됨"과
"화면에 보임"은 다르다. 마운트 시점에 03 연쇄(GET 3개, 직렬)를 곧장 쏘면 방문자가
스크롤을 한 번도 안 해도 행정동·상권·추천 요청이 나가 최종 리뷰가 지켜온 「데스크톱
첫 페인트 = GET 2개」가 깨진다.

그래서 스티키 모드는 카운터 앵커(`counterAnchorRef`)를 `IntersectionObserver` 로
관찰하다 실제로 뷰포트에 들어오는 순간(`storyInView`)에만 03 연쇄를 켠다. **한 번
켜지면 다시 끄지 않는다**(one-way latch) — 스크롤을 올렸다고 진행 중인 요청을
취소하지 않는다(`product-story.tsx`). 스택 모드(모바일)는 4단계가 전부 한 번에
마운트되므로 이 게이트가 필요 없다 — 즉시 켠다.

**실측.** 스크롤 0(랜딩 첫 화면)에서 `/api/bff` 로 나가는 요청은
`districts/top-ten`·`analysis-rankings` **2종뿐**이다
(`performance.getEntriesByType('resource')` 로 이 문서 범위(홈)만 측정. D0-2 참고).

**안전 성질.** `useRecommendPreview` 의 `enabled` 기본값은 `true` 이고,
`RecommendPreview`(03 패널 본체)는 스스로 게이트 없이 이 훅을 부른다 — 그 컴포넌트는
스티키 모드에서 사용자가 이미 03 스텝에 도달했을 때만 마운트되므로 지연이 필요 없다.
**지연되는 것은 카운터용 호출뿐이다.** 그래서 `IntersectionObserver` 콜백이 어떤
이유로든 발화하지 않아도, 사용자가 실제로 03단계에 도달하면 패널은 정상 동작하고
같은 쿼리 키를 쓰는 카운터도 그 캐시를 그대로 읽어 채워진다 — 카운터가 `—` 에
영구히 갇히는 경로는 없다.

> **미검증.** 이 세션은 브라우저 pane 이 숨겨진 상태라 `IntersectionObserver`
> 콜백이 한 번도 오지 않았고(대조군으로 `document.body` 관찰도 무응답), rAF 스로틀로
> 인한 스티키 스크롤 단계 전환도 재현되지 않았다. 따라서 **① 스토리 도달 시 03
> 연쇄가 실제로 발화하는지 ② 스크롤에 따라 카운터의 활성 노드 강조(`aria-current`)가
> 실제로 넘어가는지**는 사람 눈으로 확인이 남았다(D7 브라우저 실측 검증 B6·B7 참고).

## D6. 주의사항

1. **`justify-self: start` 를 지우지 말 것.** D4-1 의 수정은 세로축만 건드린다.
   가로축 규칙을 함께 지우면 기록된 찌그러짐 사고가 재발한다.
2. **`SeoulDistrictsMap` 자체는 지우지 않는다.** 히어로가 쓰고 있다. 스토리에서 참조만 뺀다.
3. **`formatStatusValue` 를 홈용으로 복사하지 말 것.** import 한다. 복사하면 같은 숫자가
   `/status` 와 홈에서 다르게 보이는 날이 온다.
4. **`RANKING_SIZE = 8` 을 유지한다.** 좌측 8행이 우측 5행 + 토글과 높이가 맞는다.
5. **로딩 스켈레톤은 랭킹 섹션에만 둔다.** 기존 코드가 이미 그렇게 하고 있고, 이유도 같다
   (뒤늦게 나타나며 아래 섹션을 밀지 않게).
6. **03 시드 코드는 상수 파일 한 곳에만** 둔다. `11680640` 이 언젠가 개편되면 폴백이
   동작하겠지만, 그때 고칠 자리가 한 곳이어야 한다.
7. `prefers-reduced-motion: reduce` 에서 막대 `width`·워터폴 `height` 트랜지션을 제거하고
   최종 상태를 즉시 그린다.
8. 새 색·radius·shadow 토큰을 만들지 않는다. 변화율의 상승/하락은 `DESIGN.md` 의
   `green500`/`red500` 시맨틱 토큰을 쓴다.
