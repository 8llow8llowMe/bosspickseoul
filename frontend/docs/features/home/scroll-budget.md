# home — 스크롤 예산 재조정 세부 명세서

> **작성일**: 2026-09-11
> **공통 명세**: [home 공통 명세](./home.md)
> **선행 명세**: [interaction-polish](./interaction-polish.md) — 이 문서는 그 명세의 **R1(랭킹 300dvh 트랙)을 철회**하고, R3 이 만든 헤더 오프셋과 D8-13 이 고친 pin 구간 매핑은 **그대로 계승**한다. [story-and-rankings](./story-and-rankings.md) · [below-hero-scrollytelling](./below-hero-scrollytelling.md)(트랙/스티키 패턴의 원형)
> **입력 문서**: [home UI/UX 감사 2026-09-11](./home-ux-audit-2026-09-11.md) §3 **P0-D**(스크롤 예산) · **P2-L**(앵커 구간의 빈 화면)
> **동시 진행 명세**: [contrast-tokens](../layout/contrast-tokens.md)(감사 C — 앵커 미채움 색 결정을 D8-7 에서 이 문서에 위임했다. D4-2 가 그 결정을 내린다) · [mobile-hero-first-screen](./mobile-hero-first-screen.md)(감사 A) · [ranking-minimum-sample](./ranking-minimum-sample.md)(감사 E) · [pretendard-subset](../layout/pretendard-subset.md)(감사 B)
> **대상**: 웹 (Next.js App Router)
> **작성자**: Claude Code
> **상태**: 초안 (미구현)

홈은 문서 높이 **11.7 화면**, 그중 **77%** 가 스크롤 구동 sticky 트랙이다. 히어로 다음 세 섹션
(앵커 200dvh · 스토리 400dvh · 랭킹 300dvh)이 연속으로 스크롤을 붙잡아 가입 CTA 가 **11.3 화면**
뒤에 있다. 이 문서는 그 예산을 네 가지로 다시 짠다.

1. 앵커 트랙 **200 → 130dvh**(모바일 190 → 125dvh) + 스티키를 100dvh 에서 **콘텐츠 + 여백**으로
2. 앵커 미채움 단어색 **`--color-border-200`(대비 1.23) → `--color-text-caption`(4.62)**
3. 랭킹 **300dvh 트랙 제거** → 이미 있는 클릭(세그먼트 토글) 폴백을 기본 경로로
4. 스토리 트랙 **400 → 300dvh**(스텝당 100 → 75dvh)

**새 백엔드 호출은 없다.** API 계약·데이터 흐름·섹션 순서는 바뀌지 않는다.

### D0-2. 설계 산식 검증 — 130 / 300dvh 는 계산값이다(취향이 아니다)

[interaction-polish D0-2](./interaction-polish.md) 와 같은 방식이다. 트랙 높이를 임의로 고르지
않고, **「단어 하나당 몇 px 을 칠할 것인가」와 「스텝 하나가 몇 px 버티는가」라는 하한에서 역산**한다.
전체 유도는 D5-2·D5-3, 여기서는 결론만 적는다.

| 항목                   | 산식                                                   | 데스크톱(vh 900)        | 모바일(vh 812)        |
| ---------------------- | ------------------------------------------------------ | ----------------------- | --------------------- |
| 앵커 스티키 실높이 `S` | 콘텐츠 + 상하 패딩                                     | 330 + 192 = 522         | 300 + 112 = 412       |
| 앵커 pin 구간          | `H − S`                                                | 1,170 − 522 = **648**   | 1,015 − 412 = **603** |
| 앵커 채우기 거리       | `(H − S) × FILL_PORTION(0.8)`                          | **518**                 | **482**               |
| 단어당 칠하는 거리     | 채우기 ÷ 46단어                                        | **11.3px**              | **10.5px**            |
| 앵커 트랙 하한         | `H ≥ S + 46 × 6px ÷ 0.8` (D5-2 의 6px/단어 하한)       | ≥ 867px = 97dvh         | ≥ 757px = 94dvh       |
| **앵커 채택**          |                                                        | **130dvh(1,170)**       | **125dvh(1,015)**     |
| 스토리 트랙 공식       | `calc(75dvh × STORY_STEPS.length)` = `calc(75dvh × 4)` | **2,700**               | 해당 없음(스택)       |
| 스토리 pin 구간        | `H − S`, `S = 100dvh − 65px = 835`                     | 2,700 − 835 = **1,865** | —                     |
| 스텝당 스크롤          | pin ÷ 4                                                | **466px**               | —                     |
| 스토리 트랙 하한       | 스텝당 ≥ 300px(휠 3노치) → `H ≥ 835 + 1,200`           | ≥ 2,035 = 226dvh        | —                     |
| 랭킹                   | 트랙 제거 → `Section min-height:100dvh`                | **900**                 | 816(변경 없음)        |

**채택값이 하한에 얼마나 붙어 있는가**: 앵커는 하한 97dvh 대비 130dvh(여유 33%p), 스토리는
하한 226dvh 대비 300dvh(여유 74%p). 하한에 바짝 붙이지 않은 이유는 D6 의 「스티키 높이가
줄바꿈으로 커지는 구간(769~1023px)」 때문이다 — 그 최악 조건에서도 하한을 넘긴다(D5-2 표).

### D0-3. R1(랭킹 300dvh)을 철회하는 근거

[interaction-polish D4-6](./interaction-polish.md) 은 「랭킹 섹션이 스토리처럼 스크롤로 지표를
넘긴다」는 일관성을 이유로 R1 을 **조건부 채택**했다. 그 판단에 대한 반론 다섯 가지다.

| #   | 반론                                                                                                                                                                                                                                                                                                |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **비용 대비 정보량이 어긋난다.** 2,700px(3.0 화면)으로 새로 드러나는 것은 지표 2·3의 10행뿐이다(첫 지표 5행은 진입 즉시 보인다). **행당 270px**. 같은 10행을 토글 클릭은 0px 로 낸다                                                                                                                |
| 2   | **세 번째 반복은 리듬이 아니라 지연이다.** 앵커(2.0) → 스토리(4.0) → 랭킹(3.0)이 연속 9 화면 동안 같은 제스처(「붙잡고 화면 하나를 바꿔치기」)를 요구한다. R1 이 얻으려던 일관성은 세 번째에서 관성으로 바뀐다                                                                                      |
| 3   | **랭킹은 서사가 아니라 대조다.** 스토리 01→04 는 순서 자체가 의미(단계)지만, 유동인구→매출→개업에는 인과가 없다. **순서 없는 것에 순서를 강제하면** 원하는 지표로 바로 갈 수 없다 — 정보 구조에는 토글이 맞다                                                                                       |
| 4   | **정답이 이미 코드에 있다.** 모바일·reduced-motion 이 쓰는 폴백 경로(`dual && !stacked` 의 else)가 **정보 손실 없이** 같은 15행을 1 화면에 낸다. 트랙은 같은 정보를 3배 비용으로 전달한다                                                                                                           |
| 5   | **미결 두 건이 함께 닫힌다.** [D8-9](./interaction-polish.md)(`dual` true→false 전이 시 2,700px 트랙이 auto 로 붕괴해 페이지가 점프) 와 [D8-4/B5](./interaction-polish.md)(769~900px 에서 1열 스택인데 트랙은 유지되는 조합, 3회 시도 모두 미검증) 는 **트랙이 사라지면 존재하지 않는 문제**가 된다 |

**유지하는 것**: R1 이 만든 부산물 중 `activeStepFromPinnedProgress` / `pinnedStepProgress`
(D8-13 의 매핑 수정)와 `useStackedMode` / `layout-constants` 추출은 **스토리가 계속 쓴다.**
철회 대상은 랭킹 섹션의 트랙 껍데기뿐이다.

## D1. 기능 개요

홈 문서의 세로 예산을 재배분한다. 섹션 **순서·개수·데이터 흐름은 바뀌지 않고**, 세 섹션의
트랙 높이와 스티키 기하, 앵커 단어색만 바뀐다.

```
앵커 트랙 200/190dvh → 130/125dvh (스티키 100dvh → 콘텐츠+여백, 중앙 정렬 유지)
      └ 미채움 단어색 --color-border-200(1.23) → --color-text-caption(4.62)
스토리 트랙 400dvh → 300dvh (스텝당 100 → 75dvh, 곱 공식 유지)
랭킹   300dvh 트랙 제거 → 기존 클릭 토글 경로가 기본 경로
```

섹션 순서(불변):

```
히어로 → 네 도구 보드 → 앵커 문장 → 판단 흐름 4단계 → 지금 많이 본 지역 → 더 많은 기능 + CTA
 835      545            1,800→1,170   3,600→2,700      2,700→900          900
```

## D4. 상세 동작 정의

### D4-1. 앵커 트랙 200/190dvh → 130/125dvh, 스티키를 콘텐츠 높이로

`anchor-statement.tsx` 의 `Track`·`Sticky` 두 스타일만 바뀐다. 컴포넌트 구조·카피·단어 분할은
그대로다.

```
Track  { height: ANCHOR_TRACK(130dvh); @media(max-width:640px){ ANCHOR_TRACK_SM(125dvh) } }
Sticky { position: sticky;
         top: 50dvh;                 /* ← 0 에서 변경 */
         transform: translateY(-50%);/* ← 신규. 제 높이의 절반만큼 끌어올려 중앙 정렬 */
         min-height: 0;              /* ← 100dvh 제거 */
         display:flex; align-items:center; justify-content:center;
         padding: 96px 20px;  (≤768: 72px 20px / ≤640: 56px 16px)  /* 그대로 */ }
```

**왜 `top: 50dvh` + `translateY(-50%)` 인가.** 스티키를 콘텐츠 높이로 줄이면 `top: 0` 에서는
문장이 화면 **상단**(헤더 아래)에 붙는다 — 지금의 「화면 가운데 멈춘다」 체감이 깨진다.
중앙에 세우려면 `top` 이 `(100dvh − 스티키높이) / 2` 여야 하는데, 스티키 높이는 폭·줄바꿈에
따라 달라져 CSS 상수로 못 박을 수 없다(D6 의 769~1023px 구간). `top: 50dvh` 로 **박스 상단을
화면 중앙에 세우고** 자기 높이의 절반만큼 끌어올리면, 높이를 몰라도 중앙 정렬이 성립한다.
핀 구간의 길이는 `H − S` 로 `top` 값과 무관하므로(D5-1 유도) 예산 계산도 흔들리지 않는다.

**`enter`/`fill` 단계 정의는 그대로다.** 다만 pin 구간 계산이 스티키 기하를 받아야 한다 —
받지 않으면 결함이 재발한다(D5-1 에서 px 단위로 증명).

| 상태                    | 데스크톱(1440×900)  | 모바일(375×812)     |
| ----------------------- | ------------------- | ------------------- |
| 트랙 `H`                | 1,170               | 1,015               |
| 스티키 `S`(콘텐츠+패딩) | 522                 | 412                 |
| 스티키 `top` `T`        | 450(50dvh)          | 406(50dvh)          |
| pin 구간                | 648px               | 603px               |
| 채우기(0.8)             | 518px (11.3px/단어) | 482px (10.5px/단어) |
| 다 칠한 채 유지(0.2)    | 130px               | 121px               |

### D4-2. 앵커 미채움 단어색 상향

`Word` 의 미채움 색을 바꾼다. 채워진 색은 그대로다.

```
- color: $filled ? var(--color-text-900) : var(--color-border-200)
+ color: $filled ? var(--color-text-900) : var(--color-text-caption)
```

**토큰 선택 근거.** 흰 배경(`--color-background: #ffffff`) 위 대비를 실제로 계산했다.

| 후보 토큰                  | 값        | 흰 배경 대비 | 채워짐(16.56)과의 구분비 | 판정                                                                       |
| -------------------------- | --------- | ------------ | ------------------------ | -------------------------------------------------------------------------- |
| `--color-border-200`(현재) | `#e5e8eb` | **1.23**     | 13.46 : 1                | ✗ 텍스트인데 읽히지 않는다. 감사 P2-L 의 지적                              |
| `--color-grey-400`         | `#b0b8c1` | 2.01         | 8.26 : 1                 | ✗ 큰 글자 기준 3:1 도 미달                                                 |
| `--color-grey-500`         | `#8b95a1` | 3.04         | 5.45 : 1                 | △ 큰 글자만 통과. `global-styles.ts` 주석이 이미 캡션에서 이 색을 기각했다 |
| **`--color-text-caption`** | `#6b7684` | **4.62**     | **3.59 : 1**             | ✅ **채택.** 모든 크기에서 AA(4.5) 통과                                    |

- **왜 텍스트 기준(4.5)을 적용하나.** 미채움 단어는 장식이 아니라 **읽히는 문장**이다.
  스크롤을 멈추면 그 상태로 정지한 채 남고, 스크린리더는 채움 여부와 무관하게 5문장을 낭독한다.
  「아직 안 칠해진 부분」을 못 읽게 두는 것은 인터랙션이 아니라 결함이다.
- **구분이 유지되는가.** 채워짐/미채움 구분비 **3.59:1** 은 WCAG 가 비텍스트 구분 요소에 요구하는
  3:1 을 넘는다. 현재의 13.46:1 보다 극적이진 않지만 「칠해졌다/아니다」는 명확히 보인다.
  극적임을 되찾으려고 굵기·크기를 바꾸면 단어마다 폭이 변해 줄이 출렁인다 — **금지**(D2 #7).
  **교차 참조 — [contrast-tokens](../layout/contrast-tokens.md) D6-4 와 결론이 갈린다.**

그 명세는 미채움 색을 「**의도된 장식**」으로 보고 `#e5e8eb` 를 예외 처리했고, 상한을
`--color-grey-300`(1.42)로 제안하면서 **최종 결정은 이 문서(scroll-budget)가 한다**고
자신의 D8-7 에 명시했다. 이 문서는 그 위임을 받아 **올리는 쪽으로 결정한다.** 근거:

| 그쪽 논거                                                                           | 이 문서의 판단                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「텍스트가 아니라 진행 상태의 표현이다. 반드시 채워진다」                           | **반드시 채워지지 않는다.** `prefers-reduced-motion` 에서는 트랙이 해제되고 `progress` 가 1 로 고정돼 전부 채워지지만, **스크롤을 멈춘 사용자·스크롤 없이 링크로 진입한 순간·트랙 진입 전 화면**에서는 미채움 상태가 정지 화면으로 남는다. 감사가 「스크롤 초반엔 화면이 거의 빈 것으로 보인다」고 적은 상태가 그것이다 |
| 「WCAG 1.4.3 의 비활성·장식 예외에 해당한다」                                       | 같은 DOM 노드가 스크린리더에 **문장으로 낭독**되고 시각적으로도 같은 문장이다. 「비활성 컴포넌트」는 버튼 같은 UI 컨트롤을 뜻하고, 본문 텍스트에는 적용하기 어렵다                                                                                                                                                      |
| 「진짜 문제는 대비가 아니라 레이아웃(P2-L)이다」                                    | **둘 다다.** 레이아웃(트랙·스티키 축소)은 D4-1 이 처리한다. 감사 P2-L 본문이 「미채움 색을 `--color-text-caption` 계열로 올리고 sticky 높이를 줄인다」로 **두 가지를 함께** 제안했다                                                                                                                                    |
| 「text-caption 까지 올리면 채움 전후 차이가 3.7배 → 1.5배로 줄어 눈에 띄지 않는다」 | **수치가 재현되지 않는다.** WCAG 명도 대비로 계산한 채움/미채움 쌍은 **13.46:1 → 3.59:1** 이다(grey300 은 11.3:1). 「3.7배 → 1.5배」가 어떤 지표인지 불명확하다 — **D8-4 에서 대조한다.** 3.59:1 은 WCAG 가 비텍스트 구분에 요구하는 3:1 을 넘으므로 「눈에 띄지 않는다」는 성립하지 않는다                             |

- **`--color-text-caption-on-band`(grey700)가 아닌 이유**: 앵커는 밴드가 아니라 **흰 배경**
  (`--color-background: #ffffff`) 위에 있다. contrast-tokens D4-6 규칙 5(「흰 배경 위에서는
  grey600 을 유지한다」)를 그대로 따른다.
- **후속**: contrast-tokens 의 **D6-4(예외)와 D8-7** 은 이 결정으로 닫힌다. 그 문서의 해당 절을
  「scroll-budget D4-2 가 `--color-text-caption` 으로 결정」으로 갱신해야 한다(D8-4).
  `#e5e8eb → #ffffff` 1.23 조합은 감사 §5 의 「AA 미달 18종 → 0」 집계에서도 사라진다.
- 참고: contrast-tokens 가 `--color-grey-300` 을 **1.42** 로 적었으나 이 문서의 계산값은
  **1.46** 이다(sRGB 상대 휘도 0.6677). 어느 쪽이든 1.23 과 구분되지 않아 채택 대상이 아니다.

### D4-3. 랭킹 300dvh 트랙 제거 — 클릭 토글이 기본 경로

`popular-districts.tsx` 에서 트랙 껍데기와 스크롤 지표 전환을 **삭제**한다. 폴백이었던 경로가
유일한 경로가 된다.

| 삭제                                                              | 남는 것                                            |
| ----------------------------------------------------------------- | -------------------------------------------------- |
| `ScrollTrack` · `ScrollSticky` styled 선언                        | `Section`(`$dual` 게이트 포함) 그대로              |
| `const useScrollTrack = dual && !stacked`                         | `dual` 계산은 `Section $dual` 이 계속 쓴다         |
| `useScrollProgress()` 호출과 `trackRef`/`trackElement`/`progress` | —                                                  |
| `activeStepFromPinnedProgress(...)` 호출과 `scrollIndex`          | `metric = pickedMetric`(로컬 state 가 유일한 정본) |
| `onChange` 의 `scrollToPinnedStep(...)` 분기                      | `onChange={next => setPickedMetric(next)}`         |
| `useStackedMode` · `HEADER_HEIGHT` · `scrollToPinnedStep` import  | —(스토리에서는 계속 쓴다)                          |

- **`dual` 게이트는 건드리지 않는다.** `$dual === false` 일 때만 `min-height:100dvh` 를 푸는
  기존 규칙([story-and-rankings D5-4](./story-and-rankings.md))을 그대로 둔다. 이 문서는 그
  결정을 재정의하지 않는다 — 다만 `dual` 일 때의 900px 을 더 줄일지는 **D8-1 미결**이다.
- **지표 전환 UX**: 토글을 누르면 스크롤 이동 없이 그 자리에서 우측 목록이 바뀐다.
  「클릭했는데 스크롤이 튄다」는 부작용과 [D8-9](./interaction-polish.md)(트랙 붕괴 점프)가
  함께 사라진다.
- **접근성**: `MetricToggleGroup` 의 `aria-label="지표 선택"`, 인사이트 슬롯의
  `aria-live="polite"`, `InsightSlot` 의 `min-height:74px` 예약(R2)은 전부 유지한다.

### D4-4. 스토리 트랙 400dvh → 300dvh

`product-story.tsx` 의 `Track` 한 줄만 바뀐다. 스티키(`top: 65px`, `min/max-height: calc(100dvh − 65px)`)와
스텝 매핑은 **손대지 않는다**.

```
- height: calc(100dvh * ${STORY_STEPS.length});
+ height: calc(${STORY_STEP_TRACK} * ${STORY_STEPS.length});   /* 75dvh × 4 = 300dvh */
```

**데모가 잘리지 않는다 — 트랙 높이와 무관하기 때문이다.** 데모의 세로 공간은 `Sticky` 의
`max-height: calc(100dvh − 65px)`(1440×900 에서 835px)와 `StoryRow` 의 `flex: 0 1 600px` 이
정한다. 트랙은 「스텝 하나가 몇 px 동안 유지되는가」만 정한다.

| 스텝 | 데모                  | 실측 높이  | 패널 가용(600px) | 400→300dvh 영향 |
| ---- | --------------------- | ---------- | ---------------- | --------------- |
| 01   | 지표 Top10 막대       | 384px      | 여유 216px       | **없음**        |
| 02   | 분석 미니데모         | 459px      | 여유 141px       | **없음**        |
| 03   | 추천 도넛             | 패널의 68% | 여유 있음        | **없음**        |
| 04   | 손익 곡선(플롯 296px) | 패널의 72% | 여유 있음        | **없음**        |

**하한은 데모가 아니라 스텝당 스크롤 분량이 정한다.** 스텝이 너무 빨리 넘어가면 제목·본문·데모를
읽기 전에 바뀐다. 휠 1노치 ≈ 100px 기준 **스텝당 ≥ 300px** 을 하한으로 두면 트랙 하한은
`S + 4×300 = 835 + 1,200 = 2,035px = 226dvh`. 채택값 300dvh 는 **스텝당 466px** 로 하한의 1.55배다.

## D5. 비즈니스 로직

### 처리 흐름

```
스크롤 ─rAF─> viewportProgress(top, H, vh) = progress
                       │
      ┌────────────────┼──────────────────────────────┐
      ▼                                               ▼
앵커: pinnedPhase(progress, H, vh, 0.8,          스토리: activeStepFromPinnedProgress(
        { height: S, top: vh/2 })                         progress, 4, H, vh)
      │  enter → opacity / translateY                     │
      └─ fill  → filledWordCount(fill, 46)                └─ active → 패널·CTA 교체

랭킹: (스크롤을 듣지 않는다) 토글 클릭 → setPickedMetric → metric
```

### D5-1. pin 구간 일반화 — `pinnedPhase` 는 「스티키 = 뷰포트 높이」를 가정하고 있다

`scroll-fill.ts` 의 `pinWindow` 는 지금 이렇게 계산한다.

```
start = vh / (H + vh)
span  = H / (H + vh) − start = (H − vh) / (H + vh)
```

**유도.** 트랙 높이 `H`, 스티키 높이 `S`, 스티키 오프셋 `top: T`, 트랙 상단의 뷰포트 좌표를
`top_t` 라 하면 스티키가 핀 되는 조건은

```
핀 시작:  top_t ≤ T
핀 종료:  top_t + H − S ≤ T   →   top_t ≥ T + S − H
핀 거리 = H − S            (T 와 무관)
progress = (vh − top_t) / (H + vh) 이므로
  start = (vh − T) / (H + vh)
  span  = (H − S) / (H + vh)
```

현재 구현은 **`T = 0`, `S = vh` 를 상수로 박아 둔 특수해**다. 앵커가 그 가정을 깨므로
(`T = vh/2`, `S ≈ 522`) 일반식으로 바꾼다. 기본값을 `{ height: viewportHeight, top: 0 }` 으로
두면 **스토리 호출부는 한 글자도 바뀌지 않는다.**

**일반화하지 않으면 무슨 일이 나는가 — px 로 계산한 결과**(1440×900, 앵커 트랙 1,170,
`S = 522`, `T = 450`, 트랙 문서 오프셋 1,445 = 헤더 65 + 히어로 835 + 보드 545):

| 사건                | 일반화 적용(정답) | 현행 산식 그대로 | 차이                                           |
| ------------------- | ----------------- | ---------------- | ---------------------------------------------- |
| 핀 시작 scrollY     | **995**           | 1,445            | 문장이 이미 가운데 멈춘 뒤 **450px 무동작**    |
| 채우기 시작 scrollY | 995               | 1,445            | 같은 450px                                     |
| 채우기 완료 scrollY | **1,513**         | 1,661            | —                                              |
| 핀 종료 scrollY     | **1,643**         | 1,643            | **현행은 완료(1,661)가 핀 종료보다 18px 늦다** |
| 채우기 거리         | 518px             | 216px            | 단어당 11.3px vs **4.7px**                     |

즉 현행 산식을 그대로 두고 트랙만 줄이면, [interaction-polish D8-13](./interaction-polish.md) 이
고쳤던 **「가운데 오기 전에 칠하기 시작 / 다 칠하기 전에 올라감」의 거울상**이 생긴다 —
**450px 동안 아무 일도 안 일어나다가, 46단어가 216px 만에 한꺼번에 칠해지고, 그 마지막 18px 은
이미 핀이 풀린 뒤다.** 모바일(375×812)은 더 나쁘다: 무동작 406px → 채우기 162px(단어당 3.5px).

### D5-2. 앵커 트랙 높이 역산

```
필요 채우기 거리 = WORD_COUNT(46) × (단어당 최소 px)
필요 pin 구간    = 필요 채우기 거리 ÷ FILL_PORTION(0.8)
필요 트랙 H      = S + 필요 pin 구간
```

**단어당 최소 px 의 근거**: 휠 1노치 ≈ 100px 에서 16단어를 넘게 칠하면 개별 단어가 칠해지는 것이
보이지 않고 문장이 「번쩍」인다 → **하한 6px/단어**. 읽으면서 따라가는 체감의 권장선은
**10px/단어**(현행 200dvh 가 15.7px/단어, 즉 과잉이었다).

| 조건                             | `S` | `H`(채택) | pin | 채우기 | px/단어  | 하한(6px) 충족  |
| -------------------------------- | --- | --------- | --- | ------ | -------- | --------------- |
| 데스크톱 ≥1024px, 1문장 1줄      | 522 | 1,170     | 648 | 518    | **11.3** | ✅ (하한 867)   |
| 데스크톱 769~1023px, 최악 줄바꿈 | 712 | 1,170     | 458 | 366    | **8.0**  | ✅ (하한 1,057) |
| 모바일 375×812, 감사 실측        | 412 | 1,015     | 603 | 482    | **10.5** | ✅ (하한 757)   |
| 모바일, 줄바꿈이 더 많을 때      | 530 | 1,015     | 485 | 388    | **8.4**  | ✅ (하한 875)   |

**네 조건 모두 하한을 넘는다** — 그래서 스티키 높이를 미리 못 박지 않고 실측에 맡겨도 안전하다.
만약 실측 `S` 가 표보다 커지면 규칙은 `H ≥ S + 345px`(6px/단어) 이고, 권장은 `H ≥ S + 575px`.

**`FILL_PORTION = 0.8` 유지 결정.** 남는 20% 는 「다 칠해진 문장을 그대로 두는 시간」이다.
130dvh 에서 그 값은 데스크톱 130px · 모바일 121px — 휠 1~2노치 분량으로 「다 읽었다」는 비트가
남는다. 0.9 로 올리면 유지가 65px 로 줄어 핀 해제와 구분되지 않고, 0.7 로 내리면 채우기가
454px(9.9px/단어)로 하한에 가까워진다. **0.8 이 두 제약 사이의 유일한 안전 구간이다.**

### D5-3. 스토리 스텝 매핑 — 300dvh 에서 균등한가, 눌림이 재발하나

스토리는 `T = 65px`, `S = 100dvh − 65px = 835px` 라 **`S = vh − T` 가 정확히 성립**한다.
이 경우 현행 산식과 실제 pin 구간의 **끝**은 일치하고 **시작**만 `T/(H+vh)` 만큼 어긋난다.

| 항목                           | 400dvh(현행)                                                   | 300dvh(채택)              |
| ------------------------------ | -------------------------------------------------------------- | ------------------------- |
| `H` / `denom(H+vh)`            | 3,600 / 4,500                                                  | 2,700 / 3,600             |
| 실제 pin 구간(progress)        | 0.18556 ~ 0.8                                                  | 0.23194 ~ 0.75            |
| 산식 pin 구간(progress)        | 0.2 ~ 0.8                                                      | 0.25 ~ 0.75               |
| 실제 pin 거리                  | 2,765px                                                        | **1,865px**               |
| 스텝별 스크롤(01~04)           | 290 / 1,125 / 1,125 / 225 … ❌ **whole-progress 로 나눌 경우** | 65 / 900 / 900 / 0 … ❌   |
| 스텝별 스크롤(현행 매핑, 채택) | 981 / 675 / 675 / 675                                          | **515 / 450 / 450 / 450** |
| 균등 편차                      | 1.45배                                                         | **1.14배**                |

- **눌림 결함은 재발하지 않는다.** 조건은 하나다 — **`activeStepFromPinnedProgress` 를 계속
  쓸 것**(whole-progress 의 `activeStepFromProgress` 로 되돌리지 말 것). 표의 ❌ 행이 되돌렸을 때의
  값이고, **트랙이 짧아질수록 피해가 커진다**: pin 구간이 progress 전체에서 차지하는 비중이
  0.614 → 0.518 로 줄기 때문에, 400dvh 에서 290/225px 이던 첫·끝 스텝이 300dvh 에서는
  **65px / 0px** 이 된다. 이 문서가 트랙을 줄이는 만큼 **D8-13 의 수정을 되돌리지 않는 것이 더
  중요해진다.**
- **남는 14% 편차**(스텝01 만 515px)는 산식이 `T = 65` 를 반영하지 않아 생긴다. 결함은 아니고
  「첫 스텝이 65px 더 길다」는 방향이라 사용자에게 유리하다. 스토리에도 D5-1 의 일반화를
  적용하면 4스텝 모두 466px 이 된다 — **이번 범위 밖, D8-2 미결**.
- **클릭 목표는 역함수라 자동으로 맞는다.** `pinnedStepProgress` 는 같은 `pinWindow` 를 쓴다.
  300dvh 에서 목표는 0.3125 / 0.4375 / 0.5625 / 0.6875, 클램프 경계 `[0.27, 0.73]`, 마진
  0.02(=72px)는 반스텝(225px)보다 작아 **어느 스텝도 클램프에 걸리지 않는다** ✅.

## D6. 주의사항

| 항목                                                      | 내용                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`prefers-reduced-motion` 은 트랙을 계속 해제한다**      | 앵커 `Track { height: auto }` · `Sticky { position: static; min-height: auto; padding: 120px 20px }` 는 그대로 유지한다. ⚠️ **신규 `transform: translateY(-50%)` 를 이 분기에서 반드시 `transform: none` 으로 되돌린다** — 안 그러면 정적 블록이 제 높이의 절반만큼 위로 밀려 앞 섹션과 겹친다. 스토리도 `useStackedMode` 로 스택 렌더를 유지한다                                   |
| **769~1023px 폭에서 문장이 2줄로 접힌다**                 | `Statement` 는 `min(980px, 100%)` 이고 문장 실폭이 806~850px 이라, 뷰포트 폭이 약 910px 아래로 내려가면 일부 문장이 2줄이 된다 → 스티키 높이가 522 → 최대 712px 로 커진다. `top: 50dvh` + `translateY(-50%)` 라 **중앙 정렬은 자동으로 따라오고**, pin 구간만 648 → 458px 로 줄어 단어당 8.0px(하한 6px 통과)이 된다. **고정 높이 상수를 쓰면 이 구간이 깨진다** — 쓰지 않는 이유다 |

| **매우 낮은 뷰포트(높이 ≤700px)**                         | `top: 50dvh` 에서 스티키 시각 상단은 `0.5vh − S/2` 다. `vh = 700`, `S = 522` → 89px 로 아직 양수지만, `vh = 600` 이거나 줄바꿈으로 `S = 712` 가 되면 **음수가 되어 문장 위쪽이 화면 밖으로 잘린다.** `@media (max-height: 700px)` 에서 `top: 0; transform: none` 으로 되돌려 상단 정렬로 떨어뜨린다. 그 구간에서는 pin 거리(`H − S`)는 그대로이므로 채우기 산식은 유지된다          |
