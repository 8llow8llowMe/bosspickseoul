# home — 인터랙션·가독성 2차 개선 세부 명세서

> **작성일**: 2026-09-04
> **공통 명세**: [home 공통 명세](./home.md)
> **선행 명세**: [story-and-rankings](./story-and-rankings.md) — 이 문서가 만든 히어로 하위 3부(스토리 4단계·듀얼 랭킹·벤토)의 **내용물을 2차로 개선**한다(대체하지 않는다). 형식(D0~D8)도 그 문서를 따른다.
> **대상**: 웹 (Next.js App Router)
> **작성자**: Claude Code
> **상태**: 구현 완료 (브라우저 사람 눈 검증 일부 대기 — D8-10)

`story-and-rankings.md` 구현을 dev 서버(1440×900)에서 실측한 결과 여섯 가지 개선 여지가
드러났다. 구조(섹션 순서·라우팅·API 호출)는 바뀌지 않는다. 스토리·랭킹 섹션
**내부** 컴포넌트만 바뀐다.

1. **R3(결함)** — 스토리 아이브로가 헤더 밴드(0–65px) 안에 완전히 들어가 100% 가려진다. h2 도 9px 여유뿐이다.
2. **R2** — 인사이트 문장이 없을 때 그래프 영역이 밀린다(자리 미예약).
3. **R4** — 01단계가 Top5 만 보여준다. 가용 높이는 10행도 여유 있게 들어간다.
4. **R6** — 카운터 4노드가 서로 무관한 4개의 박스처럼 보인다(연결이 없다).
5. **R5** — 「손익 워터폴」이 실제로는 워터폴이 아니라 독립 막대 5개라, 매출→비용→순이익의 **관계**가 화면에 없다.
6. **R1(채택·조건부)** — 랭킹 섹션의 지표(유동인구/매출/개업)가 클릭으로만 바뀐다. 스크롤 중심 섹션인 스토리와 이질적이다.

### D0-2. 설계 산식 검증 — 300dvh 와 62% 는 계산값이다(실측이 아니다)

R1(300dvh)과 그 비용(62%)은 새 숫자를 임의로 고른 것이 아니라, 스토리가 이미 쓰는 공식
(`height: calc(100dvh * 스텝 수)`, `product-story.tsx` 의 `Track`)을 랭킹 섹션의 지표 개수에
그대로 적용한 값이다. 1440×900 뷰포트(`100dvh = 900px`) 기준 산출이다.

| 항목                                      | 산출                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| 스토리 트랙 공식                          | `calc(100dvh * STORY_STEPS.length)` = `calc(100dvh * 4)` → 900×4 = **3600px**(실측과 일치) |
| 랭킹 트랙(신규, 같은 공식)                | `calc(100dvh * HOME_METRICS.length)` = `calc(100dvh * 3)` → 900×3 = **2700px**             |
| 랭킹 섹션 높이 변화(`dual` 상태일 때만)   | 900px(고정 `min-height:100dvh`) → **2700px**(스크롤 트랙)                                  |
| 스크롤 구동 스티키 총합(스토리+랭킹)      | 3600 + 2700 = **6300px**                                                                   |
| 홈 전체 문서 높이(추정)                   | 기존 8,389px + 순증 1,800px(2700−900) = **약 10,189px**                                    |
| 스크롤 구동 구간이 전체에서 차지하는 비중 | 현재 3600 / 8389 = **43%** → 6300 / 10189 = **62%**                                        |

이 계산은 랭킹 섹션이 **`dual`(좌우 두 열이 모두 있을 것)일 때만** 2700px 트랙을 쓴다는
전제(D4-6·D5-4)에서 나온 값이다. 솔로/제거 분기는 기존 방식(900px 또는 auto)을 그대로
써서 계산에서 뺐다. 실제 총 문서 높이는 구현 후 브라우저로 재실측한다(D7 B 계열).

## D1. 기능 개요

```
스토리(R2·R3·R4·R6 로 내용 개선) ── 듀얼 랭킹(R1: 100dvh 고정 → 300dvh 스크롤 트랙, dual 일 때만) ── 벤토(변경 없음)
```

### D3-2. 데이터 흐름

**새 백엔드 호출은 없다.** 6건 모두 기존 응답(`GET /districts/top-ten`,
`GET /analysis-rankings`)의 **표현 레이어**만 바꾼다. React Query 키·`staleTime`·성공/실패/
pending 분기(`story-and-rankings.md` D5-4·D5-4-1·D5-4-2)는 이 문서에서 손대지 않는다 —
R1 은 그 분기가 만든 `dual` 판정 위에 스크롤 트랙 하나를 얹을 뿐이다.

유일하게 "언제 부르는가"가 아니라 "어떤 스크롤 위치가 어떤 지표를 보여주는가"가 새로
생기는 것이 R1 인데, 이것도 네트워크 계층이 아니라 UI 상태(`activeMetric`) 계층이다.

## D4. 상세 동작 정의

### D4-1. R3 — 스토리 헤더 가림 해소 (결함 수정)

`product-story.tsx` 의 `Sticky` 를 고친다. `HEADER_HEIGHT` 는 **이미 같은 파일에 있는 상수다**
(`const HEADER_HEIGHT = '65px'`, `StackItem` 이 이미 쓰고 있다) — 새로 만들지 않고 그대로 쓴다.

```
Sticky {
  top: 0;                 → top: HEADER_HEIGHT;
  min-height: 100dvh;     → min-height: calc(100dvh - HEADER_HEIGHT);
}
```

**효과 계산(1440×900 기준).** `top` 이 0→65px 로 내려가면 pin 된 `Sticky` 박스의 상단
경계 자체가 화면 y=65 로 밀린다 — 박스 내부의 어떤 콘텐츠도 y=65 위로는 그려질 하한이
없어진다. `padding-top: 32px` 을 더하면 아이브로는 최소 y≈97 에서 시작해 헤더(0–65)와
겹치지 않는다. h2 는 그보다 아래이므로 더 여유롭다.

**주의(재검증 필요).** `Sticky` 는 `justify-content: center` 로 내부 콘텐츠를 세로
중앙 정렬한다. 콘텐츠 총 높이가 새 박스 높이(`calc(100dvh - 65px)`)에 육박하거나 넘으면,
중앙 정렬 특성상 콘텐츠 상단이 박스 상단보다 위로 밀려날 수 있다 — 이번 변경은 헤더
높이만큼의 **하한**을 보장하는 것이지 여유를 보장하는 것은 아니다. 정확한 잔여 간격은
D7 브라우저 실측(B1)으로 확정한다.

**주의(스텝 전환 재검증).** `top` 은 `Sticky`(자식)의 CSS 이고, `useScrollProgress` 가
측정하는 것은 `Track`(부모)의 `getBoundingClientRect()`다 — 수치상 `progress` 계산식
자체는 `top` 값을 참조하지 않는다. 그러나 `top` 을 바꾸면 브라우저가 실제로 `Sticky` 를
고정하는 스크롤 구간(핀 시작·종료 지점)이 이동하고, 사용자가 느끼는 "스텝이 바뀌는
체감 스크롤량"이 달라진다. `scrollToStep` 이 계산하는 `pinStart`/`pinEnd` 클램프도 같은
`Track` 기하를 쓰므로 수식은 그대로지만, **실제 화면에서 각 스텝 전환이 부드럽게
느껴지는지는 사람 눈으로 재확인**한다(D7 B2).

### D4-2. R2 — 인사이트 문장 자리 예약

`popular-districts.tsx` 의 `Insight` 를 `$visible` 여부로 테두리·배경만 바뀌는 하나의
컴포넌트로 바꾼다. **조건부로 마운트/언마운트하지 않는다** — 그러면 자리 자체가 없어진다.

```
InsightSlot(p) {
  margin-top: 20px;
  min-height: 74px;   /* 2×22px(line-height) + 상하 패딩 28px + 테두리 구조 2px */
  padding: 14px 16px;
  border: 1px dashed ${p.$visible ? 'var(--color-primary-600)' : 'transparent'};
  border-radius: var(--radius-card);
  background: ${p.$visible ? 'var(--color-primary-100)' : 'transparent'};
  font-size: 14px;
  line-height: 22px;
  color: var(--color-text-700);
}
```

`border` 를 지우는 대신 `transparent` 로 두는 이유: 테두리가 차지하는 2px 를 박스 모델에서
빼지 않아야 문장이 나타나는 순간 높이가 딱 2px 튀는 것도 막는다. 색이 투명이므로 화면에는
"빈 상자"가 보이지 않는다 — 요구사항의 "테두리·배경 없이"는 **시각적으로** 없는 것이지,
레이아웃 예약을 위한 구조적 두께까지 지우라는 뜻이 아니다.

**74px 산출 근거.** "가장 좁은 열에서 2줄"을 기준으로 잡는다 — 인사이트 문장(예: "유동인구
3위 동대문구는 지금 많이 본 8곳에 들지 않았습니다.")은 자치구명이 길거나 폭이 좁은
모바일(≤640px, `Section` 의 `padding: 48px 16px` 구간)에서 2줄로 넘어간다. 1줄
기준(44px)으로 잡으면 그 구간에서 여전히 밀린다. 이 값은 **모든 브레이크포인트에 동일하게**
적용한다 — 데스크톱에서 문장이 1줄로 끝나 74px 중 일부가 비어도, 브레이크포인트마다 다른
예약 높이를 계산하는 것보다 밀림이 아예 없는 편이 낫다.

`aria-live="polite"` 를 `InsightSlot` 에 붙인다. 항상 마운트돼 있으므로 지표 토글(R1 의
스크롤 전환 포함)로 문장이 바뀌거나 나타나거나 사라질 때 스크린리더가 그 변화를 읽는다.

### D4-3. R4 — 01단계 Top5 → Top10 (랭킹 우측은 Top5 유지)

`metric-ranking-board.tsx` 는 `toHomeMetricRankings(body, STORY_METRIC_TOP_N)` 을,
`popular-districts.tsx` 는 `toHomeMetricRankings(body, RANKING_METRIC_TOP_N)` 을 부른다
(D3-3). 이 둘을 갈라야 하는 이유는 두 가지다.

1. **레이아웃 결합.** 지금 두 소비자가 같은 상수(`HOME_TOP_N = 5`)를 공유한다. 하나만
   10으로 올리면 랭킹 우측도 10행이 되어 좌측 조회수 8행(`RANKING_SIZE`)과 높이가
   어긋난다.
2. **인사이트 규칙 B 의 발동 확률.** `buildRankingInsight` 의 규칙 B 는 조회수 Top3 중
   `metric.items` 에 없는 첫 항목으로 "조회수 N위 X는 {지표} Top {metric.items.length}
   밖입니다" 문장을 만든다. `metric.items.length` 가 5→10이 되면 문장이 "Top 10 밖"으로
   약해지고, **Top 10 밖에 들기가 Top 5 밖에 들기보다 훨씬 어려워** 규칙 B 자체가 걸릴
   확률이 크게 낮아진다. 랭킹 섹션의 핵심 논지("보는 곳과 숫자가 좋은 곳은 다르다")가
   조용히 무뎌진다. **랭킹 우측은 반드시 5를 유지한다.**

**높이 검증(1440×900 기준).** 01단계 패널 가용 높이는 536px 다. `RankBarList` 1행은
33px, 행 사이 `gap` 은 6px 이므로 N행의 높이는 `N × 39 − 6` 이다. 10행 = 384px 로,
536px 안에 **152px 여유**로 들어간다(D0-1). 별도 스크롤·축약 처리가 필요 없다.

`RankBarList` 의 `ariaLabel` 은 이미 `${active.label} 상위 ${rows.length}곳` 으로
행 수를 동적으로 읽으므로, 이 부분은 코드 변경 없이 "상위 10곳"으로 자동 반영된다.

### D4-4. R6 — 카운터 4노드 연결 (화살표만)

`funnel-counter.tsx` 의 `Node` 사이에 방향 화살표를 넣는다. `<ol>`/`<li>` 구조를 깨지
않기 위해 화살표는 **각 `Node`(마지막 제외) 안에 절대 위치로** 넣는다(별도 리스트
항목으로 추가하지 않는다 — `<ol>` 의 자식은 `<li>` 여야 유효한 마크업이다).

```
List {
  gap: 8px 20px;   /* row-gap 8px 유지, column-gap 만 20px 로 넓혀 화살표 자리 확보 */
  @media (max-width: 640px) { gap: 8px; }  /* 2열에서는 원래 간격으로 복귀 */
}

Node { position: relative; }  /* 비-마지막 노드만 */

Connector {
  position: absolute;
  top: 50%;
  right: -20px;
  transform: translate(50%, -50%);
  color: var(--color-border-300);
  @media (max-width: 640px) { display: none; }
}
```

`<Connector aria-hidden="true"><ArrowRight size={16} /></Connector>` — 의미는 이미
`<ol>` 순서와 `aria-current="step"` 이 나른다. 화살표는 순수 장식(시각적 흐름 강조)이므로
`aria-hidden` 이 **필수**다.

**모바일(≤640px)에서 숨긴다.** `List` 가 2열로 접히면(D4-4 위 미디어쿼리) 가로 화살표가
열 사이에서 방향이 깨진다(1→2는 오른쪽, 2→3은 아래-왼쪽, 3→4는 오른쪽 — 일관성이 없다).
4열일 때만 그린다.

**그라데이션·색상 단계화는 채택 불가.** 근거 셋:

1. [below-hero-scrollytelling D2 #8](./below-hero-scrollytelling.md): 「3D 아이콘·캡처
   이미지·gradient/blur 를 쓰지 않는다」
2. `DESIGN.md` 검증 체크리스트가 `home-page.tsx` 에 대해
   `linear-gradient|radial-gradient|backdrop-filter|glassmorphism` grep **무결과**를 요구한다
   (`DESIGN.md` 1368행)
3. `DESIGN.md` Don't: 「Don't add decorative elements to financial data displays —
   clarity is the aesthetic」

색상 단계화(노드마다 다른 색)를 쓰지 않는 이유는 그라데이션 금지와 별개다. 네 노드는
같은 흐름의 **국면**이지 서로 다른 범주가 아니다 — 색을 다르게 칠하면 없는 의미 차이를
암시하게 된다. 게다가 활성 노드 강조(`$active`)가 이미 `--color-primary-700` 테두리 +
`--color-primary-100` 배경을 쓰고 있어, 노드별 고유색을 더하면 "활성 강조색"과
"카테고리색"이 한 노드 위에서 충돌한다.

**모션(선택 사항, 이번 범위 밖).** 연결을 더 강조하고 싶다면 색이 아니라 모션에 예산을
쓴다 — 스텝 전환 시 화살표가 짧게 채워지는 정도. `active` prop 은 스티키 모드에서만 존재
하므로 이 모션도 스티키 모드 전용이다. `prefers-reduced-motion: reduce` 가드 필수. 이번
1차 실행 범위에는 넣지 않는다(D8-6).

### D4-5. R5 — 손익 그래프: 세로 막대 5개 → 가로 100% 스택 바

**진단.** 이름은 워터폴인데 렌더는 독립 막대 5개다(`CostWaterfall` 의 `STEPS.map`이
각 항목을 `Column` 으로 나란히 그린다). 워터폴의 정의적 특징 — 각 막대가 앞 막대가 끝난
지점에서 시작하고, 연결선이 잔액을 보여주는 것 — 이 없다. 그래서
`4,200 − 1,050 − 1,200 − 350 = 1,600` 이라는 **관계가 화면에 존재하지 않고 독자가
암산해야 한다.** 「보기 안 좋다」의 원인은 색이나 형태가 아니라 이 관계의 부재다.

**방향 B(채택) — 가로 100% 스택 바.** 「매출 4,200 이 어디로 가는가」를 한 줄로 보여준다.

```
매출 4,200만원
┌──────────────┬────────────┬──────┬──────────────────┐
│ 임차료 1,050  │ 인건비 1,200│기타350│    순이익 1,600    │
└──────────────┴────────────┴──────┴──────────────────┘
  25.0%           28.6%        8.3%       38.1%
```

- 세그먼트 순서(왼→오): 임차료 → 인건비 → 기타 → 순이익. 넷을 합치면 매출(4,200)과
  정확히 같다 — 이것이 세로 막대 5개와의 핵심 차이다(매출 자체는 막대의 "전체"이지
  또 하나의 세그먼트가 아니다. 캡션/헤더로 별도 표기).
- 색은 **두 가지만** 쓴다 — 비용 3항목(임차료·인건비·기타)은 `--color-border-200`
  (기존 `kind: 'cost'` 색을 그대로 계승), 순이익은 `--color-primary-600`(기존
  `kind: 'net'` 색 계승). 새 토큰을 만들지 않는다. 비용 3항목끼리는 색이 아니라
  세그먼트 사이 1px 구분선(`border-right: 1px solid var(--color-surface)`)과 아래
  범례 순서로 구분한다 — 카테고리 3개에 억지로 3가지 색을 배정하지 않는다
  (R6 의 "없는 의미 차이를 암시하지 않는다" 원칙을 여기도 적용한다).
- **라벨은 막대 밖(아래 범례)에 둔다.** 가로 바는 세로 방향 공간(카드 폭 전체, 400px
  안팎)이 넉넉해 4개 항목의 라벨+금액+비율을 한 줄 범례로 나란히 놓을 수 있다. 세로
  워터폴에서는 「기타」 막대 자체가 13px 로 얇아 그 막대 위에 값을 얹기 어려웠지만
  (D0-1), 가로 바는 막대의 폭(8.3%)이 얇아도 범례는 막대 바깥에 독립적으로 존재하므로
  영향받지 않는다. 범례 순서는 세그먼트 순서와 동일하게 둬 위치 대응이 깨지지 않게 한다.
- `role="img"` + `aria-label` 은 기존 문구를 그대로 쓴다: 「월 손익 구조 예시. 월매출
  4,200만원에서 임차료·인건비·기타를 빼면 순이익 1,600만원입니다.」 세그먼트·범례는
  `aria-hidden="true"` — 의미는 `aria-label` 하나가 전담한다(기존 패턴 유지, 변경 없음).
- **유지**: 만원 단위, 「대표 예시 데이터」 캡션, 실 API 미사용(랜딩 방문자당 `POST`
  회피 결정 — [story-and-rankings D8-2](./story-and-rankings.md)).

### D4-6. R1 — 랭킹 섹션 300dvh + 스크롤 지표 전환 (채택, 조건부)

`popular-districts.tsx` 를 `product-story.tsx` 의 Track+Sticky 패턴과 같은 모양으로
개편한다. 단, **좌측(조회수) 열은 스크롤과 무관하게 고정 콘텐츠**이고, **우측(지표) 열의
활성 지표만** 스크롤 진행도로 바뀐다.

```
Track { height: calc(100dvh * HOME_METRICS.length); }   /* = 300dvh, D0-2 */
Sticky { position: sticky; top: HEADER_HEIGHT; min-height: calc(100dvh - HEADER_HEIGHT); }
  Header(고정) + Columns(좌: 조회수 고정 / 우: MetricToggleGroup + 활성 지표 RankBarList)
  + InsightSlot(R2)
```

- `progress = useScrollProgress(trackRef)`(기존 훅, 그대로 재사용)
- `activeMetricIndex = activeStepFromProgress(progress, HOME_METRICS.length)`(기존 순수
  함수, 그대로 재사용 — **신규 스크롤 계산 함수를 만들지 않는다**. 이미 임의의
  스텝 수에 대해 제네릭하게 동작하도록 작성돼 있다)
- `metric = HOME_METRICS[activeMetricIndex]`

**적용 범위(스코프 한정 결정).** 300dvh 스크롤 트랙은 **`dual`(좌우 두 열 모두 있을
것, `story-and-rankings.md` D5-4-2 의 `viewWillExist && metricWillExist`) 상태일
때만** 적용한다. 실패·솔로·제거 분기(`story-and-rankings.md` D5-4·D5-4-1)는 **이
문서에서 재정의하지 않고 기존 렌더(비-스크롤, 클릭 토글, `min-height:100dvh` 또는
`auto`)를 그대로 쓴다.** 좌측 열 없이 우측 지표 하나만 300dvh 를 핀 고정하는 것은
비교 맥락(「보는 곳」)이 없어 서사가 성립하지 않고, 구현 범위도 커진다.

#### 조건① — 클릭이 스크롤 위치를 즉시 덮어쓴다

`MetricToggleGroup` 의 `onChange` 를 `setMetric(next)` 대신
`scrollToMetric(HOME_METRICS.indexOf(next))` 로 바꾼다. `scrollToMetric` 은
`product-story.tsx` 의 `scrollToStep` 과 같은 계산을 쓴다(같은 파일 함수를 복사하지
않고, 필요하면 공용 유틸로 뽑아 두 컴포넌트가 같은 클램프 로직을 공유한다 — pin 구간
클램프 공식이 두 곳에서 따로 틀리면 한쪽만 고쳐지는 사고가 난다):

```
target index → center = (index + 0.5) / HOME_METRICS.length
             → targetProgress = clamp(center, pinStart+margin, pinEnd-margin)
             → window.scrollTo({ top: ..., behavior: reduced ? 'auto' : 'smooth' })
```

이걸 따르지 않고 로컬 `useState` 로만 지표를 바꾸면, 클릭 직후에도 스크롤 리스너가
계속 `progress` 를 재계산해 다음 스크롤 이벤트(휠 관성, 리사이즈 등)에서 상태가
스크롤 위치로 되돌아간다 — 클릭이 무시된 것처럼 보인다.

**전이 지연은 선례와 같은 수준으로 받아들인다.** `scrollTo({ behavior: 'smooth' })` 는
애니메이션이 끝나기까지 몇 프레임이 걸리고, 그동안 `metric` 은 스크롤 이벤트에 맞춰
점진적으로 갱신된다. 이는 스토리의 `scrollToStep` 이 이미 갖고 있던 특성과 동일하다 —
이 문서가 새로 도입하는 결함이 아니라 인정된 선례다.

#### 조건② — 모바일/`prefers-reduced-motion` 폴백

`useStackedMode()`(스토리와 **동일한** 판정: `prefers-reduced-motion: reduce` 이거나
뷰포트 폭 ≤768px)가 `true` 면 300dvh 트랙을 쓰지 않고 **오늘 코드가 이미 렌더하는
것**(단일 화면, `min-height:100dvh`, `useState` 기반 클릭 토글)을 그대로 렌더한다.
`product-story.tsx` 가 `if (stacked) { … 스택 렌더 … } return … 스티키 렌더 …` 로
분기하는 것과 같은 모양으로 만든다. 이 분기 덕분에 오늘의 구현을 거의 그대로
"폴백 브랜치"로 재사용할 수 있다(추가 코드가 아니라 조건 분기 하나).

`useStackedMode` 는 현재 `product-story.tsx` 안의 비공개 함수다. R1 의 판정 기준이
스토리와 **정확히 같아야** 하므로(둘 다 ≤768px/reduced-motion), 이 훅을 공유 모듈로
추출해 두 컴포넌트가 import 한다(D8-3). 각자 다시 작성하면 두 판정 기준이 시간이
지나며 갈릴 위험이 있다.

**엣지 케이스(769–900px 폭).** `useStackedMode` 의 임계값(≤768px)과 `Columns` 의
기존 2단→1단 임계값(≤900px)이 다르다. 769–900px 폭에서는 "스크롤 구동 모드"(>768px)
이면서 "1단 시각 스택"(≤900px)인 조합이 생긴다 — 세로로 쌓인 좌/우 콘텐츠가 300dvh
동안 핀 고정된 채로 우측만 스크롤에 따라 바뀐다. 명세 오류는 아니지만 실제로 자연스러운지
사람 눈으로 확인이 필요하다(D7 B4, D8-4).

## D5. 비즈니스 로직

### D5-1. 300dvh 산식과 비용

D0-2 참고. 지표 3종 → `calc(100dvh * 3)` = 300dvh. 홈의 스크롤 구동 스티키 구간
(스토리 3600 + 랭킹 2700)이 전체 문서 높이(약 10,189px)의 **62%** 를 차지한다(현재
43%에서 증가).

### D5-2. `activeMetricFromProgress` — 재사용, 신규 함수 없음

```
activeMetricIndex = activeStepFromProgress(progress, HOME_METRICS.length)
metric = HOME_METRICS[activeMetricIndex]
```

`activeStepFromProgress(progress, stepCount)` 는 이미 `stepCount` 를 매개변수로 받는
제네릭 함수다(`scroll-fill.ts`). `stepCount=3` 으로 부르는 새 호출 하나만 추가한다.

### D5-3. `dual` 게이트와의 결합

```
useScrollTrack = dual === true && stacked === false
```

| `dual` | `stacked` | 렌더                                                     |
| ------ | --------- | -------------------------------------------------------- |
| true   | false     | 300dvh 스크롤 트랙(신규, D4-6)                           |
| true   | true      | 기존 단일 화면 + 클릭 토글(폴백, 조건②)                  |
| false  | —         | 기존 솔로/제거 렌더(`story-and-rankings.md` D5-4 그대로) |

### D5-4. R4 가 인사이트 규칙 B 에 미치는 영향(대조)

| 지표 목록 크기                 | 규칙 B 문장 예시                                  | 발동 난이도                                              |
| ------------------------------ | ------------------------------------------------- | -------------------------------------------------------- |
| Top5(랭킹 우측, 유지)          | 「조회수 2위 마포구는 유동인구 Top 5 밖입니다.」  | 조회수 상위 3곳이 지표 5위 밖이어야 함(비교적 자주 성립) |
| Top10(01단계, 만약 공유했다면) | 「조회수 2위 마포구는 유동인구 Top 10 밖입니다.」 | 조회수 상위 3곳이 지표 10위 밖이어야 함(성립 확률 급감)  |

랭킹 우측이 계속 Top5 를 쓰므로 이 표의 왼쪽 행만 실제로 렌더된다 — 오른쪽 행은 "분리하지
않았다면 벌어졌을 일"을 보여주는 대조 참고용이다.

### D5-5. R2 예약 높이 산출

```
min-height = 2 × line-height(22px) + padding-top/bottom(14px × 2) + border(1px × 2)
           = 44 + 28 + 2 = 74px
```

### D8-12 검증 환경에서 겪은 함정

2. **`pnpm dev -- -p 5173` 은 실패한다** — `--` 가 그대로 넘어가 `-p` 를 디렉터리로 읽는다.
   `PORT=5173 pnpm dev` 를 쓴다.
3. **dev 백엔드가 죽어 있으면 BFF 가 500 이다** — `ConnectTimeoutError
(api-dev.bosspickseoul.com:443, 10000ms)`. 이 검증 중 실제로 다운됐고, 그 상태로는
