# AI Service Strategy

## 목적

- `ai-service`의 조회 전략과 사용자 경험 기준을 정리한다.
- 분석 데이터 API와 AI 리포트 API를 어떤 방식으로 조합할지에 대한 운영 기준을 남긴다.

## 권장 조회 전략

- 상권 / 자치구 / 행정동의 원본 분석 데이터 API는 먼저 응답한다.
- AI 리포트는 별도 API로 분리해서 호출한다.
- 프론트는 분석 데이터 화면을 먼저 렌더링하고, AI 리포트 영역은 후행 로딩한다.
- AI 리포트 응답이 도착하면 카드나 섹션 단위로 점진적으로 갱신한다.

즉, 권장 UX는 아래와 같다.

1. 원본 분석 데이터 먼저 로딩
2. AI 리포트 API 별도 호출
3. AI 섹션은 skeleton / loading 표시
4. 응답 완료 시 AI 리포트만 교체 렌더링

## 왜 이렇게 가는가

- 로컬 LLM(Ollama)은 응답 시간이 길어질 수 있다.
- AI 리포트 생성은 캐시 miss 시 내부 데이터 수집 + LLM 추론이 함께 발생한다.
- 메인 분석 응답에 AI 리포트를 합치면 첫 화면 응답 시간이 과도하게 늘어날 수 있다.
- AI 리포트를 분리하면 메인 분석 UX를 해치지 않으면서도 AI 보조 기능을 제공할 수 있다.

## 현재 백엔드 전략

- `GET /api/v1/ai-reports/commercials/{commercialCode}`
- `GET /api/v1/ai-reports/districts/{districtCode}`
- `GET /api/v1/ai-reports/administrations/{administrationCode}`

현재 AI 리포트 API 자체는 동기 조회형이다.

- 캐시 hit: 빠르게 응답
- 캐시 miss: 내부 서비스 조회 + LLM 호출 후 응답

즉, 서버 구현은 동기지만 프론트 UX는 비동기 섹션 로딩을 권장한다.

## 캐시 전략

- AI 리포트는 Redis 캐시를 우선 사용한다.
- 동일한 입력 조건에서는 캐시 hit를 통해 응답 지연을 줄인다.
- 캐시는 사용자 자산 저장이 아니라 파생 결과 재사용 목적이다.

## 향후 확장 가능성

아래 조건이 생기면 비동기 작업형 API를 검토할 수 있다.

- 생성 시간이 길어 사용자 대기 시간이 과도할 때
- 고비용 모델 사용으로 미리 생성 / 재사용이 중요할 때
- 생성 상태 추적, 재시도, 실패 보상이 필요할 때

그 경우 예시는 다음과 같다.

- `POST /api/v1/ai-reports/.../generate`
- `202 Accepted`
- 작업 ID 기반 상태 조회 또는 폴링
- 완료 후 조회 API로 결과 반환

현재 단계에서는 이 구조까지는 과하므로, 동기 API + 캐시 + 프론트 후행 로딩 전략을 기본값으로 둔다.

## 게이트웨이 기준

- API Gateway는 `/api/v1/ai-reports/**`를 `ai-service`로 라우팅한다.
- Swagger aggregation 용으로 `/ai-service/**` 문서 경로를 추가한다.

## 권장 프론트 적용 방식

- 분석 페이지 진입 시:
  - 원본 분석 데이터 API 호출
  - AI 리포트 API 병렬 호출
- AI 리포트 실패 시:
  - 메인 분석 화면은 유지
  - AI 섹션만 fallback 문구 노출
- AI 리포트 성공 시:
  - 요약 카드, 강점/주의점, 추천 인사이트 순으로 렌더링
