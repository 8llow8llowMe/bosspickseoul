# Auth Account Frontend Guide — 가입 동의 · 비밀번호 재설정 · 계정 연결/전환

## Purpose

이 문서는 프론트엔드에서 **회원가입 동의(약관·처리방침·만 14세 이상 확인)**, **비밀번호 재설정**,
**일반↔소셜 계정 연결/전환** UX를 구현할 때 auth-service API를 어떻게 쓰는지 정리한다.
로그인/회원가입 기본 흐름은 기존 명세를 따르고, 여기서는 동의·계정 복구·연결 시나리오만 다룬다.

## 계정 모델 이해 (전제)

계정의 식별자는 **이메일**이며 DB unique 키다. 이메일 변경 기능은 의도적으로 제공하지 않는다.
한 계정은 두 로그인 수단을 가질 수 있다.

| 계정 상태 | password | provider | 가능한 로그인 |
| --- | --- | --- | --- |
| 일반 계정 | 있음 | null | 이메일 로그인 |
| 소셜 전용 계정 | null | KAKAO/NAVER | 소셜 로그인 |
| **연결된 계정** | 있음 | KAKAO/NAVER | **둘 다** |

`GET /api/v1/members/me` 응답의 `provider` + `hasPassword` 조합으로 FE가 상태를 구분한다:
`hasPassword=true, provider=null` → 일반 / `hasPassword=false, provider=KAKAO` → 소셜 전용 /
`hasPassword=true, provider=KAKAO` → 연결됨. **사용자 정보 화면의 비밀번호 메뉴는 이 조합으로 분기한다**
(소셜 전용 → "비밀번호 설정" 노출, 비밀번호 변경 숨김 / 연결됨 → "비밀번호 변경" + "소셜 전용으로 전환").

## 0. 회원가입 동의와 만 14세 이상 확인 (#494)

가입은 **이용약관 동의 · 개인정보 처리방침 동의 · 만 14세 이상 확인** 세 가지를 모두 받아야 성립한다.
백엔드는 가입에 성공한 순간 세 항목을 **동의한 문서 판(version)과 같은 시각**으로 동의 이력에 남긴다.
판은 서버 설정(`legal.terms-version` / `legal.privacy-version`)으로 정해지므로 **프론트가 판을 보내지 않는다.**
두 값은 `src/lib/legal/terms-of-service.ts` · `privacy-policy.ts` 의 `version` 과 같아야 한다(현재 `1.0` / `1.2`).
약관·처리방침을 개정하면 프론트 상수와 백엔드 설정을 같은 배포에 함께 바꾼다.

### 0-1. 일반 가입 (`POST /api/v1/members/signup`)

기존 바디에 boolean 필드 셋을 더한다. 개발용 즉시 가입(`POST /api/v1/members/signup/dev`, prod 미노출)도 바디가 같다.

| 필드 | 타입 | 필수 | 화면 |
| --- | --- | --- | --- |
| `termsAgreed` | boolean | `true` 여야 함 | "[필수] 이용약관에 동의합니다" (`/terms` 링크) |
| `privacyAgreed` | boolean | `true` 여야 함 | "[필수] 개인정보 처리방침에 동의합니다" (`/privacy` 링크) |
| `ageOver14Confirmed` | boolean | `true` 여야 함 | "[필수] 만 14세 이상입니다" |

```json
{
  "email": "user@example.com", "password": "P@ssw0rd!", "name": "홍길동", "nickname": "길동짱",
  "termsAgreed": true, "privacyAgreed": true, "ageOver14Confirmed": true
}
```

- 필드를 **빼고 보내면 `false` 로 취급**되어 400 이다. 세 체크박스가 모두 켜졌을 때만 제출 버튼을 활성화하되,
  서버 검증을 전제로 응답 코드도 처리한다.
- "전체 동의" 체크박스를 두더라도 서버에는 세 필드를 각각 보낸다.

**에러 처리** — 체크박스마다 코드가 다르다. 해당 체크박스를 강조하면 된다.

| 상황 | HTTP | resultCode | 프론트 처리 |
| --- | --- | --- | --- |
| 이용약관 미동의 | 400 | `MEMBER_114` | 이용약관 체크박스 강조 |
| 개인정보 처리방침 미동의 | 400 | `MEMBER_115` | 처리방침 체크박스 강조 |
| 만 14세 이상 미확인 | 400 | `MEMBER_116` | "만 14세 이상만 가입할 수 있습니다" + 해당 체크박스 강조 |
| (서버 가드) 동의 누락 / 만 14세 미만 | 400 | `MEMBER_010` / `MEMBER_011` | 정상 화면에서는 나오지 않는다. 각각 114·115 / 116 과 같게 처리 |

- 여러 항목이 함께 빠지면 `resultCode` 는 첫 오류(선언 순서 `termsAgreed` → `privacyAgreed` → `ageOver14Confirmed`)이고,
  `resultMessage.errors[]` 에 항목별 `{code, field, message}` 가 모두 담긴다. 필드별로 첫 오류만 표시하면 된다.
- 동의로 거절돼도 **이메일 인증은 소비되지 않는다.** 30분 안이면 체크 후 다시 제출하면 된다.

### 0-2. 소셜 첫 가입 (카카오/네이버)

소셜은 처음 로그인하는 이메일이면 그 자리에서 회원을 만든다. 그래서 동의를 **콜백이 아니라 인가 URL 을 만들 때** 받는다.
OAuth 인가코드는 1회용이라, 콜백에서 동의가 없다고 거절하면 같은 `code`·`state` 로 다시 시도할 수 없기 때문이다.

| API | 추가 파라미터 | 설명 |
| --- | --- | --- |
| `GET /api/v1/auth/{provider}/authorize` | `termsAgreed`, `privacyAgreed`, `ageOver14Confirmed` (쿼리, boolean, 생략 시 `false`) | 값은 `state` 와 함께 10분 보관되고 콜백에서 **신규 회원을 만들 때만** 쓰인다 |
| `GET /api/v1/auth/{provider}/login` | (변경 없음) `code`, `state` | 콜백. 동의를 다시 보내지 않는다 |

```
[회원가입 화면의 "카카오로 시작하기"]
세 항목 체크 → GET /auth/kakao/authorize?termsAgreed=true&privacyAgreed=true&ageOver14Confirmed=true
→ authorizationUrl 로 이동 → 콜백 → GET /auth/kakao/login?code=&state=
→ 신규면 가입 + 동의 이력, 기존 회원이면 그냥 로그인

[로그인 화면의 "카카오 로그인"] — 동의 없이 시작해도 된다
GET /auth/kakao/authorize → 콜백 → GET /auth/kakao/login
→ 기존 회원: 정상 로그인 (동의와 무관)
→ 신규: 400 AUTH_021 → 동의 화면(세 항목) → 동의 값을 실어 /authorize 부터 다시 시작
   (provider 는 앱 권한을 이미 승인했으므로 대개 곧바로 콜백으로 돌아온다)
```

| 상황 | HTTP | resultCode | 프론트 처리 |
| --- | --- | --- | --- |
| 신규 + 이용약관·처리방침 동의 없음/부족 | 400 | `AUTH_021` | 동의 화면을 띄우고, 동의 값을 실어 **`/authorize` 부터 다시** |
| 신규 + 문서 동의는 했지만 만 14세 이상 미확인 | 400 | `AUTH_022` | "만 14세 이상만 가입할 수 있습니다" + 체크박스 강조, 체크 후 `/authorize` 부터 다시 |
| 같은 `state` 로 콜백 재호출 | 401 | `AUTH_010` | 처음부터 다시 (state 는 한 번 쓰면 사라진다) |

- `AUTH_021`/`AUTH_022` 는 회원을 만들지 않은 상태다. 콜백의 `code`·`state` 는 이미 소비됐으므로 재사용하지 말고 반드시 `/authorize` 를 다시 부른다.
- 문서 동의와 만 14세 확인이 함께 비면 `AUTH_021` 이 먼저 나간다. 동의를 아예 싣지 않은 첫 시도가 여기에 해당한다.
- 일반 가입 코드(`MEMBER_114~116`, `MEMBER_010/011`)와 나뉘어 있는 이유가 이것이다 — 소셜 코드는 "폼 재제출" 이 아니라 "인가부터 다시" 를 뜻한다.

### 0-3. 기존 회원

- **소급 동의를 받지 않는다.** 이 기능 이전에 가입한 회원은 동의 이력이 없고, 그 상태를 "동의 도입 전 가입" 으로 본다.
  로그인·소셜 로그인·계정 연결 모두 동의와 무관하게 그대로 동작하며 재동의 화면을 띄우지 않는다.
- 약관 개정에 따른 재동의 흐름은 아직 없다(개정 시 별도 설계).

### 0-4. 배포 순서

- **이 BE 변경(#494)이 FE #495 보다 먼저 배포되면** 동의 필드를 보내지 않는 기존 가입 화면은 `MEMBER_114` 로 막히고,
  신규 소셜 가입은 `AUTH_021` 로 막힌다. 기존 회원 로그인은 영향이 없다. 가입 화면 동의 체크박스(FE #495)와 같은 릴리스로 낸다.
- 소셜 state 를 BFF HttpOnly 쿠키에 묶는 보강(**#527**)은 **#495 와 같은 릴리스 또는 그보다 먼저** 나가야 한다. 지금 state 는
  브라우저에 묶여 있지 않아, 남이 만든 `/authorize` URL 로 인가를 마치면 그 사람이 정한 동의 값으로 계정과 동의 이력이 생길 수
  있다(login CSRF). 상세는 `services/auth-service.md` 「소셜 state 와 login CSRF」.
- 동의 이력의 판·시각은 소셜이면 `/authorize` 를 부른 순간, 일반 가입이면 `signup` 을 처리한 순간의 서버 판 설정이다.
  프론트는 판을 보내지 않는다(이번 계약). 약관 개정 때는 프론트 `version` 과 백엔드 설정을 같은 배포에 올린다.

## 1. 비밀번호 재설정 (비밀번호를 잊은 사용자)

로그인 화면의 "비밀번호를 잊으셨나요?" 진입점에 연결한다. **일반/연결 계정 전용** —
소셜 전용 계정은 비밀번호가 없으므로 재설정 대상이 아니다(아래 응답 정책 참고).

| API | 인증 | 용도 |
| --- | --- | --- |
| `POST /api/v1/auth/password/reset/send-code` | 불필요 | `{email}` — 재설정 인증코드 메일 발송 |
| `POST /api/v1/auth/password/reset` | 불필요 | `{email, code, newPassword}` — 재설정 |

```
[화면 흐름]
이메일 입력 → send-code (항상 성공 응답)
→ "메일을 확인해주세요" 안내 (가입 여부를 화면에서 노출하지 않는다!)
→ 코드 + 새 비밀번호 입력 → reset → 성공 시 로그인 화면으로
```

- **send-code는 항상 200**이다. 미가입 이메일/소셜 전용 계정 여부는 **메일 내용**으로만 안내된다
  (계정 존재 여부를 응답으로 노출하지 않는 보안 정책). FE는 성공/실패 분기 없이
  "입력하신 주소로 안내 메일을 보냈습니다"로 통일해 표시한다.
- 소셜 전용 계정 사용자는 "카카오/네이버 로그인 이용" 안내 메일을 받는다. FE가 미리 걸러줄
  필요 없다 (걸러주는 것 자체가 계정 정보 노출이다).
- 재설정 성공 시 **전 기기 세션이 무효화**된다. "비밀번호가 변경되었습니다. 다시 로그인해주세요"로 안내.
- 새 비밀번호 규칙은 회원가입과 동일 (8~20자, 영문+숫자+특수문자, 공백 불가).

**에러 처리**

| 상황 | HTTP | resultCode | 프론트 처리 |
| --- | --- | --- | --- |
| 60초 내 재발송 | 429 | `AUTH_003` | "잠시 후 다시 요청해주세요" + 재요청 버튼 비활성 카운트다운 |
| IP 발송 상한 초과 | 429 | `AUTH_016` | "요청이 너무 많습니다" 안내 |
| 코드 불일치 | 400 | `AUTH_004` | 코드 입력란 오류 표시 (남은 시도 기회 있음) |
| 코드 만료/미발급 | 400 | `AUTH_005` | "코드가 만료되었습니다" + 재발송 유도 |
| 코드 5회 오입력 | 400 | `AUTH_017` | 코드 무효화됨 — 처음(발송)부터 다시 |
| 필드 검증 | 400 | `AUTH_101/102/104/106~108` | 필드별 오류 표시 |

## 2. 계정 연결 — 일반 계정 사용자가 같은 이메일로 소셜 로그인

**FE가 할 일은 없다. 자동으로 연결된다.** 일반 계정(비밀번호 있음)이 있는 이메일로
소셜 로그인하면 백엔드가 그 계정에 provider를 연결하고 그대로 로그인시킨다.
이후 이메일 로그인과 소셜 로그인 **둘 다** 사용 가능하다.

- 자동 연결이 안전한 이유: 소셜 쪽은 provider가 검증한 이메일만 허용(`AUTH_012`로 미검증 거부),
  일반 가입도 이메일 인증 필수 — 양쪽 다 메일함 소유가 증명된 상태다.
- 연결되는 순간 사용자에게 **"소셜 로그인이 연결되었습니다" 통보 메일**이 발송된다
  (본인이 아니면 비밀번호 변경을 유도하는 탈취 감지 수단).
- 반대 provider로 이미 연결된 계정이면 `409 AUTH_008` ("이미 카카오로 가입된 계정입니다") —
  resultMessage를 그대로 표시하면 된다.

## 3. 계정 전환/추가 — 소셜 전용 사용자가 이메일 로그인도 쓰고 싶을 때

소셜 전용 계정이 같은 이메일로 회원가입을 시도하면 `409 MEMBER_001`로 막힌다.
이때 "소셜 로그인 후 비밀번호를 설정하세요"로 유도하는 것이 정석 UX다.

| API | 인증 | 용도 |
| --- | --- | --- |
| `POST /api/v1/members/me/password/setup` | 필수 | `{newPassword}` — 비밀번호 최초 설정 |

```
[화면 흐름]
회원가입 시도 → 409 MEMBER_001 → "카카오로 가입된 이메일입니다. 카카오 로그인 후
설정에서 비밀번호를 만들 수 있어요" 안내 → 소셜 로그인 → 마이페이지 "비밀번호 설정"
→ setup 성공 → 이후 이메일 로그인도 가능
```

- 진입점: 마이페이지/설정에서 `hasPassword == false` 인 계정에 "비밀번호 설정" 메뉴를 노출한다.
- 이미 비밀번호가 있는 계정이 호출하면 `400 MEMBER_008` — "비밀번호 변경을 이용해주세요".
- 설정 후 세션은 유지된다 (로그아웃되지 않음).

## 4. 소셜 전용으로 전환 — 연결된 계정의 비밀번호 제거

연결된 계정(`hasPassword=true && provider != null`)이 이메일 로그인을 버리고
소셜 전용으로 전환한다. 비밀번호가 **완전히 제거(null)** 되어 이후 이메일 로그인이 불가하다.

| API | 인증 | 용도 |
| --- | --- | --- |
| `DELETE /api/v1/members/me/password` | 필수 | 비밀번호 제거 → 소셜 전용 계정으로 전환 |

```
[화면 흐름]
설정 → "소셜 전용으로 전환" → 확인 팝업
"카카오 전용 계정으로 전환할까요? 이메일 로그인을 더 이상 사용할 수 없고,
 모든 기기에서 로그아웃됩니다." [전환] [취소]
→ DELETE 성공 → 로그인 화면으로 (소셜 로그인 유도)
```

- **되돌릴 수 있는 결정이지만**(다시 "비밀번호 설정"으로 이메일 로그인 복구 가능) 전 기기
  로그아웃이 동반되므로 반드시 확인 팝업을 거친다.
- 성공 시 **전 기기 세션 무효화** + refresh 쿠키 제거 + "소셜 전용 계정으로 전환되었습니다"
  통보 메일 발송. FE는 로컬 토큰을 지우고 로그인 화면으로 보낸다.
- 전환 후에는 사용자 정보 화면에서 "비밀번호 변경" 메뉴를 숨긴다 (`hasPassword=false`).

**에러 처리**

| 상황 | HTTP | resultCode | 프론트 처리 |
| --- | --- | --- | --- |
| 소셜 미연결(일반 전용) 계정 | 400 | `MEMBER_009` | 메뉴 자체를 노출하지 않아야 함 — 방어적 안내 |
| 이미 소셜 전용 계정 | 400 | `MEMBER_007` | 메뉴 자체를 노출하지 않아야 함 |

## 5. 로그인 기기 관리 (세션 목록/해제)

설정 화면의 "로그인된 기기" 목록에 연결한다.

| API | 인증 | 용도 |
| --- | --- | --- |
| `GET /api/v1/auth/sessions` | 필수 | 기기 세션 목록 (마지막 사용 내림차순) |
| `DELETE /api/v1/auth/sessions/{sessionId}` | 필수 | 특정 기기 해제 |

- 항목: `{sessionId, deviceInfo(User-Agent 요약), createdAt(최초 로그인), lastUsedAt, current}`.
  `deviceInfo` 로 모바일/PC 표시를 가공하면 된다 (예: "Mobile" 포함 여부).
- `current=true` 항목이 이 요청을 보낸 기기다 — "현재 기기" 배지를 달고 해제 버튼 대신
  로그아웃으로 유도하는 것을 권장한다 (해제 자체는 가능).
- 해제된 기기는 access 토큰 만료 시점에 자동 로그아웃된다(즉시 끊기지 않음). 안내 문구에 반영할 것.
- 기기 상한(기본 5대)을 넘겨 로그인하면 가장 오래 사용하지 않은 기기가 자동으로 밀려난다.

## 흐름 요약

```
[일반 가입]
이메일 인증 → 회원 정보 + 세 항목 동의(termsAgreed / privacyAgreed / ageOver14Confirmed) → signup
→ 거절되면 MEMBER_114 / 115 / 116 에 해당하는 체크박스 강조

[소셜 첫 가입]
동의를 실어 /authorize → 콜백 /login → 가입 완료.
동의 없이 시작했다면 AUTH_021 / AUTH_022 → 동의 받고 /authorize 부터 다시.

[비밀번호 재설정]
로그인 화면 → "비밀번호를 잊으셨나요?" → 이메일 입력 → 메일의 코드 + 새 비밀번호
→ 성공 → 전 기기 로그아웃됨 → 재로그인

[일반 → +소셜 (연결)]
소셜 로그인 버튼만 누르면 끝 (자동 연결 + 통보 메일). 이후 두 방법 모두 로그인 가능.

[소셜 → +이메일 (비밀번호 설정)]
소셜 로그인 → 마이페이지 "비밀번호 설정" → 이후 두 방법 모두 로그인 가능.

[연결됨 → 소셜 전용 (전환)]
설정 "소셜 전용으로 전환" → 확인 팝업 → 비밀번호 제거 + 전 기기 로그아웃
→ 이후 소셜 로그인만 가능 (필요하면 "비밀번호 설정"으로 복구).
```
